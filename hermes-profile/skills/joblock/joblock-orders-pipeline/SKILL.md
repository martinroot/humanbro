# JobLock orders pipeline — правила и процедура

## Архитектура (не предлагать отступлений)
- **Стандартизированная база + коннекторы.** Под каждую биржу — тонкий коннектор: снимает ленту → нормализует в общую схему (source, external_id, title, description, price, url) → POST `/api/ingest` на портале. Классификация, стадии, постановка — только в портале. Fabra как приёмник исключена (`PARSER_SINK=joblock` в browser-automation/.env); Dagi удалён из контура.
- **Портал — единственный источник правды**: C:/sites/joblock/portal (app.py :8701; nginx :8080 с basic-auth). Автостарт — Scheduled Task `JobLock-Portal` (run_portal_task.cmd), НЕ через launch_portal.bat вручную.
- **Последовательный цикл** (portal/cycle.py, тред внутри портала): search (60 с) → chat (300 с) → execute (один фокус-заказ). Писатель mode.json — только `python reviews/mode.py переключить <режим>`; цикл переключает режимы через него, никогда руками.

## Пользовательский контракт
- Human-facing marketplace labels in the portal, Telegram cards and reply-draft context use full names (Workzilla, Kwork, FL.ru, Insolvo, Freelance.ru, Profi.ru); preserve the canonical `source` key and source-qualified ID in machine data. Do not force the platform name into client-facing draft text unless the saved reply prompt asks for it.
- Вкладки Chrome нативные и постоянные: одна вкладка на биржу (поиск по домену в URL) + вкладка мониторинга. Коннектор находит вкладку по домену, bringToFront, читает DOM на живой странице; полный reload ≤ 1 раз / 10 мин (timestamp-файл в out/). Никаких newPage/close на каждый тик и никаких about:blank-прыжков — «моргающая лента» была отклонена.
- Всё строго последовательно: один тик — одна биржа; каждое переключение режима — запись в журнал с триггером.
- Работаем только на видимой вкладке Chrome (CDP :9222, профиль C:/chrome-profile) — заказчик видит и может вмешаться.
- Профили клиентов извлекай только из проверенной публичной разметки конкретной биржи; отличай клиента от текущего исполнителя/шапки профиля. Идентичность связывай по стабильному ID аккаунта внутри source-qualified ключа, не по совпавшему имени; не собирай контакты, пароли, токены и платёжные данные. Нет стабильного ID — сохраняй только order-level факт либо `unknown`, не создавай клиента по имени.
- Customer RiskScore (скамность, 0–100, где 100 = явный скам; обязательное число, не null) отделён от score исполнимости заказа (0–100) и от `agentic` (агентская выполнимость, 0–100). Храни основания и confidence; при недостатке фактов ставь низкое 0–20 и confidence=low, а не null и не придуманную середину. Новый аккаунт или отсутствие отзывов сами по себе не доказывают скам и не должны автоматически отклонять заказ.
- Если Pass 2 должен выдавать текст отклика, включай `reply_draft` и customer RiskScore в проверяемый source-qualified JSON вместе с оценкой; показывай черновик в Ready-карточке вместо повторного списка рисков/плана/вопросов, но сохраняй эти поля в `analysis_json`. Кнопка отклика переиспользует сохранённый черновик; отправка остаётся только после явного владельческого approve и допустимого bidder mode. **Стиль владельца (финал, переопределяет все прежние редакции):** живой фрилансер, не менеджер по продажам. Одно-два коротких предложения, разговорным тоном. Схема: «Добрый день! Опыт <релевантный навык> есть — готов выполнить.» ПРЯМО ЗАПРЕЩЕНО пересказывать ТЗ и повторять то, что написано в вакансии — заказчик это уже знает; не описывать задачу, не перечислять этапы и стек, не хвастаться. Допустим один короткий вопрос, только если он реально нужен для старта. Прошлая редакция «5 / 10 / 15 слов + конкретный первый шаг + выделяться конкретикой» ОТМЕНЕНА владельцем как «слишком дохрена расписывает, люди так не делают» — не применять. Размытый заказ → «Добрый день! Нужно больше деталей, пока объём не понятен.»; скам → «Добрый день, не смогу помочь.» Опыт называть только из базы исполнителя (Python 5+ лет; парсеры; выжимки и панели; OpenRouter API; фотошоп; WordPress; тексты); нет релевантного — «Добрый день! Готов выполнить.» Размытый заказ («надо найти/продать/привлечь», без объёма и критериев) — не выдумывать решение, а спросить: «Добрый день! Нужно больше деталей, пока объём не понятен.» Вопрос — только реально блокирующий; если всё понятно, вопросов нет. Сроки владельца — предварительные, зависящие от ТЗ, не гарантия; для разработки с бюджетом <500 ₽ обозначить минимум 500 ₽ и условную вилку правок; ориентир 3–6 часов только «если всё пойдёт штатно»; Kwork — минимум 150 символов без воды. Не утверждать, что URL изучен без подтверждённой загрузки; при необходимости SSH просить доступ безопасно, никогда не просить пароль/токен/код в чате; не придумывать опыт, портфолио и гарантии. Разрешённые факты: Python 5+ лет; большой опыт парсеров; выжимки из данных и панели; OpenRouter API и подбор моделей.
- UI портала — светлая гамма: `data-bs-theme="light"` + светлые фон/таблица/пилюли (тёмные оттенки цветов статусов). Тёмную тему пользователь отклонил как нечитаемую.
- Для многоэтапных изменений веди сохраняемый checklist и отмечай только проверенные критерии. Если лимит инструментов прерывает работу, оставь точный checkpoint по готовому/незавершённому и состоянию сервиса; на «продолжай» возобновляй с первого незакрытого пункта, не повторяя завершённые шаги и не называя успешный patch готовым деплоем без проверки endpoint/фоновой задачи.

## Процедуры
- **После правок промпта/оценки/карточки — `scripts/verify_reply_scores.py`** (`PYTHONPATH=. python <skill>/scripts/verify_reply_scores.py`): ловит сохранённый-промпт-перебивает-дефолт, рассинхрон порогов меток с границами в промпте, потерю `agentic` в `prepare_pass2_item` и ложное «готов взять» на reject. Ничего не пишет в БД и не шлёт в Telegram; юнит-тесты на константы этого не ловят, живой прогон модели стоит 429 и минуты.
- Рестарт портала: kill python с app.py → `schtasks /Run /TN "JobLock-Portal"` → curl /portal/ до 200. Задача запускает venv-python (системный python без pymysql — частая причина падения после апдейтов).
## Переключение режимов (mode.py): не гасить Chrome
- **Перед закрытием вкладок проверь, что страховка РЕАЛЬНО открывает вкладку.** «Никогда не закрываем последнюю» работает только если хелпер открытия действительно что-то открывает; раньше «страховка» вызывала `_открыть_портал()`, которая давно возвращает `False` и ничего не делает — и режим отклика закрыл все вкладки, Chrome умер и не поднялся. Правило: страховка = `_открыть("about:blank")` через CDP `PUT /json/new`, и проверять её результат, а не вызывать вслепую.
- **Обязательная вкладка режима не открылась → падать с ошибкой, а не отчитываться «готово».** `применить_режим` должен бросать исключение с ID заказа, если в режиме `respond` нет вкладки задания; молчаливый «успех» с нулём/чужой вкладкой оставляет владельца с закрытым браузером и потерянным откликом. Вызывающий (tg_bot) по исключению возвращает черновик в `draft` и пишет `last_check_result='unknown'`, `last_check_note='mode_switch_failed'`. Бросать исключение нельзя и при мёртвом CDP — тогда переключатель честно падает, а не «собирается».
- **Режим поиска обязан сам возвращать авторизованные вкладки, которые парсеры НЕ открывают** (Profi.ru `/backoffice/n.php`, Freelance.ru `/task`): их читает коннектор из уже залогиненной вкладки, а `respond` их закрывает. Без восстановления две биржи молча выпадают из поиска при живом Chrome и зелёном `can-start-parser=allowed`. Восстановление делать идемпотентно (не плодить дубли, если вкладка уже есть).
- **Проверять переход на живом Chrome, а не только юнит-тестом:** `python reviews/mode.py переключить respond <id>` → `curl :9222/json/list` (ровно одна вкладка задания, процесс жив) → `... переключить search` → снова список вкладок (все ленты вернулись) → `python reviews/mode.py can-start-parser`. Юнит-тест на фейковом CDP ловит только то, что в нём описано.
- **Биржа, отдавшая антифрод («Кажется, включён VPN» и подобное), выключается тумблером, а не обходом:** `curl -X POST -H "Content-Type: application/json" --data-binary '{"profi_ru": false}' http://127.0.0.1:8701/api/settings/exchanges` (бэкап `mll_settings.json.bak-<ts>` рядом). Проверять по журналу: следующий тик пишет `поиск_<биржа> | биржа отключена настройкой` и ошибок больше нет. Не ротировать IP/профили и не «дожимать» страницу.
- Учёт вкладок: portal/tabs_http.py (чистый CDP HTTP, без playwright) — закрывает неучтённые и дубли ролей; цикл зовёт каждые 5 тиков. Роли: monitor, scraper; вкладки самих бирж не трогаются.
- При лежащем Chrome: CDP-чек `curl :9222/json/version`; если HTTP 200 но playwright висит на рукопожатии — Chrome завис, перезапуск: kill chrome → запуск с `--user-data-dir=C:/chrome-profile --remote-debugging-port=9222 --hide-crash-restore-bubble`. Цикл сам делает паузу 2 мин после 3 ошибок подряд, не спамя.
- Санитария в репо (github martinroot/worker): пароль БД только через `JOBLOCK_DB_PASSWORD` env, .env/логи/кэш в .gitignore; перед пушем grep по токенам.

## Статусы и MLL-воронка
- Канон статусов ленты: `new` (не оценён) → `white` (прошёл фильтр) / `black` (отказ) → `ready` (pass2 score ≥ порога); дубли помечаются `dublicate`. Старые каноны (в работе/ждём/сдано/сбой/блок/закрыто) из ленты убраны. `orders.status` — VARCHAR (enum убит), новые значения добавлять ALTER-ом не нужно.
- Двухступенчатая оценка (portal/mll_filter.py — pass1, portal/mll2.py — pass2): pass1 пакетно режет явный скам по чёрному/белому списку (`mll_settings.json`, `/settings`); pass2 оценивает только `white` и переводит score ≥ `min_score` в `ready`. При смене порога уже оценённые строки сами не пересчитываются: пересчитать сохранённые scores, `pass2.verdict`, статусы обеих таблиц и только нужные уведомления. Ставить `pass2.notified` лишь после успешного Telegram API ответа и сверять его после backfill. Score — суждение модели, не откалиброванная вероятность. Сохраняй пользовательский профиль Pass 2: цифровые агентские задачи не отклонять за нехватку материалов, доступов, бюджета или деталей; переноси пробелы во вопросы/риски, а низкий score оставляй принципиально неагентской, офлайн/физической, незаконной или мошеннической работе. Настройки Pass 1 находятся на `/settings`, Pass 2 — на `/mll`; валидируй model ID до записи и сохраняй обе стадии независимо. Перед сменой модели запроси OpenRouter `/api/v1/models/<author>/<slug>/endpoints` (слэш в model ID разделяет path-сегменты; не кодируй его как `%2F`, иначе endpoint может вернуть 404), выбери актуальный endpoint, его точные input/output rates и context length; закрепи провайдера через `mll_models.provider_for_model` и отключи fallback. При смене модели синхронизируй настройки обеих стадий и cost calculators. Проверяй обе стадии отдельными синтетическими пакетами через прямые batch-функции, не `прогон()` (он пишет статусы и может отправлять Telegram): используй несколько тестовых карточек, захвати request model/provider/fallback, проверь все IDs, verdict/score, usage и cost по выбранному endpoint. OpenRouter может вернуть HTTP 200 с JSON `{error:{code:429,...}}` без `choices`: проверяй `error` до чтения `choices`, логируй код/сообщение и применяй backoff вместо `KeyError('choices')`. После сохранения перезапусти Scheduled Task, прочитай настройки через оба API и проверь новые MLL-логи; если очередь пуста, синтетический smoke подтверждает путь модели, но не живую обработку. Лог вызовов Pass 2 — `mll2_log.jsonl`.
- Оценивай один пакет одним stateless-вызовом: каждый запрос содержит только фиксированный prompt и текущие карточки; не добавляй историю предыдущих пакетов или ответы модели — контекст между вызовами не накапливается. Парси ответ не срезом от первой `[` до последней `]` (вставной текст/несколько массивов ломают JSON), а поиском валидного JSON-массива, покрывающего все ожидаемые source-qualified IDs; числовой суффикс допускай только если он уникален в пакете. До любых DB-записей проверь полноту/уникальность IDs, допустимый pass1 verdict и score 0–100; отсутствующий результат не превращай в `ok` или score 0, иначе карточка будет неверно классифицирована или навсегда застрянет. Тестируй fenced/prose-wrapped вывод, несколько массивов и неполное покрытие; при невалидном ответе весь пакет остаётся без изменений. Делить batch cost на размер пакета только в per-order логах.
- API OpenRouter: ключ из ~/AppData/Local/hermes/.env (OPENROUTER_API_KEY); провайдера задавать через `mll_models.provider_for_model` и всегда отключать fallback: известные `z-ai/*` — `relace/fp4`, `openai/gpt-6-luna` — `openai/flex`, новые модели — проверить доступные endpoints и закрепить подходящий маршрут. Для оценки Pass 2 и `reply_draft` используй модель, выбранную владельцем (сейчас `tencent/hy4-flash`; провайдер и цены бери из OpenRouter, а не из памяти); Pass 1 оставляй на GLM, пока владелец явно не изменит выбор. Для reasoning-маршрутов оставлять `reasoning.enabled=true`, кроме `tencent/hy4-flash` с малым `max_tokens`: reasoning съедает выходной бюджет и ответ приходит с пустым `content`; в `pipeline_composer._ask_mll` reasoning включать только для `gpt*`/`claude*`. Короткие классификации ограничивать `max_tokens`.
- **Смена модели — это пять мест, а не одно.** Обнови `model.default` в каждом `profiles/<name>/config.yaml` (empty/video-shorts/pdf-edit-pro/slug), `model` в `profile_templates` портала, `mll2.model` И `mll.model` в `mll_settings.json` (верхний ключ `модель` — не тот, что читает `mll2.настройки()`), плюс `mll_models.MODEL_CHOICES` и `PRICE_PER_MILLION`. Цены бери из `GET https://openrouter.ai/api/v1/models` с поиском по id: одиночный `/api/v1/models/<id>` может вернуть пусто. Проверка: `mll2.настройки()['model']` и `grep default:`. **Профиль заказа, созданный после смены, наследует старую модель из шаблона** — после `provision` проверь его `config.yaml → model.default` и исправь расхождение вручную, само не наследуется.
- Фильтры всех стадий — вкладки одной страницы /orders: все / black / white / оценка_блек / оценка_вайт; оценка_* маппятся клиентски из `analysis_json.pass2.verdict` (ready/reject), не новыми статусами. Кнопка «подробнее» в строке разворачивает и ТЗ, и блок оценки pass2 (риски/время/план/стоимость/вопросы/score) — данные для этого /api/orders/{n}/details отдаёт вместе с pass2.
- Фон-циклы оценки (pass1, pass2) в портале: вызывай прогон сразу при старте; после непустого пакета немедленно вызывай следующий, интервалом спи только при пустой очереди; backoff оставляй только для реальной ошибки. Печать из фонового треда — ASCII-only: консоль Scheduled Task не cp1252, кириллический print после записи статусов может бросить UnicodeEncodeError и замаскировать успешно обработанный пакет длинной паузой. Используй проверенный ASCII-safe formatter (`encode('ascii','backslashreplace')`) и для success, и для exception сообщений; regression tests должны проверять ASCII-вывод и отсутствие сна при непустом пакете. После рестарта `JobLock-Portal` сверяй число `status='new'` и проверяй свежие MLL-логи на новые `charmap` ошибки.
- Полное ТЗ обязательно на всех стадиях: карточка ленты — обрезок, «по одному заголовку решения не принимает» (установка пользователя). Коннектор обязан дообогатить описание со страницы/деталей заказа и передать url в инжест:
  • WZ: DOM-заголовок `.text-wrapper`, цена `.param-title`, длительность `.time-title`; полное ТЗ — детальная вкладка, блок `.description-content`. ВАЖНО: детали — ОДИН раз на заказ за всю жизнь (кэш out/.wz_enriched, id добавляется после захода независимо от результата); «гонять <500 симв. каждый тик» — ошибочный дизайн, пользователь прямо жаловался на бесконечный обход: заказы с «ТЗ в файле» короткие навсегда и дёргали вкладку каждый тик. ВАЖНО: `/api/order|mass-order/v1/{id}` из контекста вкладки ЛЕНТЫ отвечает `{"result":102}` — API-обогащение не работает, только рендер деталей; из отдельной вкладки деталей API отдаёт `data.description`.
  • FL: budget-блок `.b-post__price` («по договоренности» → price=null); полное ТЗ — origin-fetch страницы проекта + DOMParser, блок `.fl-project-content__description-text`.
  • Kwork: коннектор kwork-demand.ts, карточки `.want-card`, бюджет «Желаемый бюджет»; полное ТЗ — fetch страницы проекта, `<meta name="description">`; URL заказа `https://kwork.ru/projects/<номер>` (external_id с префиксом KW- в url НЕ подставлять — кривые ссылки). Инжест-тело цикла обязано передавать `url` — его отсутствие даёт пустой project_url и битые ссылки в ленте и Telegram.
- Кэширование полного ТЗ и detail-fetch policy: см. `references/marketplace-enrichment-cache.md`; не повторяй свежие детали и не выдавай summary за полный brief.
- Обрезки в оценщике обесценивают полные тексты: Pass 1 ограничивает описание 1500 символами, Pass 2 — 4000; текущие пакеты обычно 30 и 5 карточек соответственно. Владелец на незапрошенный рестарт: «я думал ты просто подготовишь, не лезь!». Если рестарт согласован: `Get-CimInstance Win32_Process` с фильтром по `app.py` (родитель и ребёнок — оба), kill → `schtasks /Run /TN "JobLock-Portal"` → пауза ~25 с → проверить `200` на `/`, `/orders`, `/api/unified-orders` и что БД не пуста (`SELECT COUNT(*) FROM market_projects`). Задача запускает venv-python (системный python без pymysql — частая причина падения после апдейтов). Никогда не поднимать второй экземпляр: два poller'а одного токена дают вечный 409. Новый роут в `app.py` в старом процессе отдаёт 404 — пока портал не перезапущен, «сделано» не работает; когда владелец просит «сделай и проверь», рестарт входит в задачу.
- **Проверка «парсинг строго по настройкам» — это SQL-сверка, а не зелёные тесты.** Владелец: «оставить как есть — проверяй парсинг в соответствии с настройками». Порядок: (1) включённые биржи — `mll_settings.json` → `биржи` (kwork/insolvo/fl/freelance_ru/profi_ru должны быть `false`) + `responses.<биржа>.mode`; (2) фактический состав ленты — `SELECT source, COUNT(*) FROM market_projects GROUP BY source` — он обязан содержать только включённые; примеси чужих бирж = коннектор поднимает все ленты; (3) env `PARSER_MARKETS` парсера — пусто означает «все ленты», и один `bun parser.ts` без переменной натянет мусор; (4) `mll2.прогон()` и свежая карточка: три числа 0–100 и `take:`/`apply:` в клавиатуре. Отдельно смотреть `portal_run.log` на `missing ids` — после чистки это остаток старого лога, а не текущая ошибка; сверять по id, которых нет в БД. Старые cron-задачи выключены — «парсер сам поднимается» значит живой процесс-родитель, а не расписание.
- Цена карточки Workzilla — число СРАЗУ после длительности в шапке («1д 0ч 7000»), не «последнее число текста карточки»: в тексте после цены идёт описание, и последнее число — мусор (600 вместо 7000). При смене логики цены пересчитывать legacy по тому же паттерну и в market_projects, и в payload заказов (orders.number ≠ external_id — матчить через market_projects.order_number).
- Экранирующая `esc()` в JS страницы ленты должна быть типо-безопасной (typeof string → replace, иначе String(t)): число/объект в description роняет `.replace`, а `catch { a.textContent = ... }` молча откатывает кнопку — всегда `catch (e) { console.error(...) }` и после правки E2E-клик (bun+playwright: click → details-row появился).
- Дедуп (source + LEFT(title,120) + price, MIN(id) остаётся) гонять по ВСЕМ статусам — дубль уже оценённой карточки тоже дубль; пометка status='dublicate' до батч-оценки экономит токены.

## Изоляция профиля заказа (обязательно)
- **Переключать шлюз на профиль заказа ДО публикации карточки в топик.** Создание профиля (`order_profiles.provision`) само по себе НЕ изолирует агента: пока активен старый профиль (например `slug`), агент читает его `skills/` и `state.db` — оттуда берутся чужие `short-video-*`, `grok-image-workflow` и сессии других топиков. `start_order.dispatch` обязан вызвать `profile_switch.MANAGER.switch(profile, chat_id=owner_chat_id, user_id=...)` сразу после provision и до `cyberguse_orchestrator.run_sync`; при отказе switch — вернуть `ok:false` и НЕ публиковать заказ в чужом контексте. Порядок в тесте: `['provision', 'switch', 'orchestrate']`.
- **Сессия топика живёт в `state.db` активного шлюза, а не профиля заказа.** Проверять: `SELECT id FROM sessions WHERE session_key LIKE '%:group:<chat>:<topic_id>'` в `profiles/<slug>/state.db`. Один и тот же `[class*="skills"]` у профиля заказа чистый (только `joblock-active-order` и т.п.), а `'Reading skill short-video-…'` в логе означает, что шлюз не переключён. Ключ сессии уникален по `thread_id` — история разных заказов не смешивается, если шлюз правильный.
- **Тестировать это ТОЛЬКО на 1–2 заказах/агентах, не на двадцати.** Владелец: «аккуратнее тестируй — ты 20 профилей запустил и 20 агентов одновременно… если баг фикси, сливаем деньги». Каждый `dispatch` = реальный вызов модели и реальный агент. Для проверки изоляции достаточно: (1) юнит-тест порядка вызовов с моками, (2) один живой заказ с проверкой, что в логе нет чужих скиллов. Массовые прогоны по всем профилям/заказам без явной просьбы — не делать: это деньги и каша в топиках. Создание профиля на диске (`profile create`) — не запуск агента, денег не стоит; запуск шлюза/агента — стоит.
- **Последовательная работа: переключения достаточно; параллельная — `multiplex_profiles`.** Сначала прочитать `gateway.multiplex_profiles` и `gateway.profile_routes` в `~/.hermes/config.yaml`. При `multiplex_profiles: false` все топики обслуживает один активный gateway, и изоляция достигается только переключением перед каждым заказом; `switch()` останавливает текущий gateway, поэтому переключать можно только после сдачи текущего заказа, иначе оборвёшь работающего агента. Для параллельной работы нужны `multiplex_profiles: true` + `profile_routes`: `gateway/session.py::_session_key_namespace()` даёт именованному профилю префикс `agent:<profile>` (профиль с именем `main` помечается `agent:main~`), поэтому один и тот же топик в разных профилях не сталкивается. Не путать уровни: `thread_id` изолирует топики внутри профиля, `profile` в namespace — профили между собой.
- **Рабочая мультиплексная схема: закреплённые топики + переключаемый `default-chat`.** На боевом шлюзе `slug`: `gateway.multiplex_profiles: true`, `auto_multiplex_migration: false`, `profile_routes` в `profiles/slug/config.yaml` — два маршрута с `thread_id` под заказные топики (например `764 → pdf-edit-pro`, `641 → video-shorts`) плюс маршрут `default-chat` без `thread_id`. `profile_switch.MANAGER.switch()` в этом режиме НЕ останавливает общий шлюз: он меняет `profile` у `default-chat`, перезапускает только `slug` и ждёт реального `running` (~40 с) перед возвратом. Проверять маршруты парсером конфига и `match_profile_route`, а не по описанию. **В мультиплексе активный профиль — `profile` маршрута `default-chat`, а не имя живого процесса.** Шлюз `slug` обслуживает все профили, поэтому `Get-CimInstance` покажет `slug` при любом выбранном профиле; `profile_switch.MANAGER.active_profile()` обязан читать маршрут из `profiles/slug/config.yaml` и возвращать его `profile`. Watchdog и старые задачи (`Hermes_Gateway_Watchdog`, `Hermes_Gateway_<ord-…>` → Disabled) всё равно отключать: они перезапускают прежний профиль и перезаписывают `gateway_active_profile.json` между вызовами.
- **Удаление мусорных профилей: сначала остановить мультиплекс, иначе `state.db` заблокирован.** `slug` держит открытыми `state.db` ВСЕХ профилей: `rm -rf` падает `Device or resource busy` на `logs/.__agent.lock` и `state.db*`. Порядок: отключить watchdog и задачи старых профилей → `hermes -p slug gateway stop` → бэкап `profiles/` → `rm -rf profiles/<мусор>` → `hermes -p slug gateway start --force` → сверить живые процессы. Удалять только после явного подтверждения владельца.
- **Чистка профилей = диск + БД портала + тесты.** После удаления папок в `profile_templates`, `order_profiles`, `profile_sessions` остаются мёртвые строки, и `/api/profiles` продолжает показывать мусор. Оставлять только реальные шаблоны, обнулять `order_profiles`/`profile_sessions`, править тесты, ссылающиеся на удалённые `ord-*` каталоги, и сверять `/api/profiles` с диском.
- **Базовый каталог JobLock — три профиля:** `video-shorts`, `pdf-edit-pro`, `empty`; плюс служебный `slug` (мультиплексный шлюз) и корневой `default`. Остальное — промежуточные итерации.

## Меню бота: поток заказов (tg_bot.py)
- **Корневое меню бота — пользовательский поток КАК ПОСЛЕДОВАТЕЛЬНОСТЬ СВЕРХУ ВНИЗ, техника внутри.** Владелец отверг нумерацию: не `1️⃣/2️⃣/3️⃣/4️⃣`, а просто порядок кнопок без цифр — «не цифрами профил, а последовательность сверху внизу». Точный порядок в `меню_клавиатура()`: `📂 Заказы` (`orders:open:0`, пагинация по 5) → `🤖 Каталог агентов` (`agents:catalog`) → `▶️ В работу` (`orders:work`) → `✅ Закрыть` (`orders:history`) → `🔧 Техника` (`menu:tech`). Активный профиль, шлюз, топики и настройки в корне НЕ показывать — только в `menu:tech`. Карточка заказа сверху вниз: `📂 Заказы` → `🤖 Каталог агентов` → `▶️ Взять в работу` (`take:<pk>`) → `⚙️ Выполнение` (`handoff:`) → `✅ Закрыть заказ` (`order:close:<pk>` переводит `market_projects.status='closed'`) → `🔧 Техника заказа` (`order:tech:<pk>`) ПОСЛЕДНЕЙ строкой; в каталоге — `▶ Выполнить: <профиль>` (`take_catalog:`). Профиль заказа, шаблон, хендофф, топик и «Отправить результат» — внутри техники заказа. Все mutation-колбэки owner-only. Перекладывая кнопку между меню, сразу правь тест, который искал её в старом месте (например, активный профиль проверялся в корневом меню).
- **Выборки вынести в `order_views.py`, а не разносить SQL по меню.** `OPEN_SQL` = `status IN ('white','ready')` (black/dublicate не показывать вообще), `WORK_SQL` = `('active','running','dispatched','needinfo','queued','waiting')`, `HISTORY_SQL` = `('done','closed','paid','failed','blocked')`. При взятии в работу `order_views.mark_in_work(id)` переводит заказ `active`, и он уходит из «Открытых»; сдача — `mark_done(id)` в историю. `count_open()` для пагинации; если запрос счётчика упал, подстраховать `total = max(total, offset+len(rows))`, иначе кнопка «Далее» исчезает.
- **Пагинация — `nav.extend(_кн(...))`, не `nav.append(_кн(...))`.** `_кн()` уже возвращает ряд `[{...}]`: `append` даёт вложенный `[[{...}]]`, и Telegram отвергает такую inline-клавиатуру целиком, хотя меню выглядит собранным. Тест должен разворачивать callback'ы из всех рядов и требовать `orders:open:<offset>` на обеих страницах.
- **Каталог агентов — только реальные профили Hermes и понятные описания.** Владелец: «Весь каталог. Не выдумывай. Все реальные профили выводятся». Источник — `profile_switch.MANAGER.profiles()` (`tg_bot.real_profiles()`), а не выдуманные строки из базы; скрывать только служебные (`hermesworker`, `slug`) и одноразовые `ord-*` профили прошлых заказов. Описание — `agent_catalog._human_description()`: что умеет + число скиллов, для базовых профилей готовый словарь (`design` → «дизайн: логотипы, баннеры, листовки…»); обрезать по границе слова, чтобы не получить «превью для марке». `★` помечает профиль, выпущенный из заказа (есть в `profile_store`).
- **«В работе» → «Шаблон из сессии» — отдельная кнопка под каждым заказом** (`fromsession:<external_id>`): ForceReply на имя (`grad_name`), дальше штатный выпуск шаблона из сессии. Так замыкается цикл «сделал заказ → хорошо получилось → форматируем скиллы и пайплайн → новый агент в каталоге».

## Выпуск шаблона из выполненного заказа
- **Не переписывать наработки заказа из своей головы: сначала отдать папку с сессией.** Владелец: «Стоп — смотри внимательнее. Все есть, примеры, видео. И т.д.… Пришли папку с сессией». Пока человек не посмотрел сессию и не решил, что идёт в шаблон, не создавать свой `SKILL.md` и не менять каталог.
- **Сначала инвентаризация профиля, потом авторство.** Агент во время заказа САМ пишет рабочие скиллы (проверено: один видео-заказ оставил `skills/media/` с пятью связанными скиллами — workflow, scriptwriter, generators, editor с `scripts/*.py` и тестами, pipeline-view). Прежде чем писать хоть один `SKILL.md`, обойти `profiles/<slug>/skills/**/SKILL.md` и `ord-*/skills/` и посмотреть, что уже есть. Владелец на самодельный скилл поверх готовых: «Ты не то делаешь». Написанный с нуля скилл дублирует существующий, теряет реальные скрипты и грабли и отправляется в мусор. Если агент сам собрал пакет заказа (`SESSION.md`, `PIPELINE.md`, `COMMANDS.md`, `MANIFEST.json`, `skills/`, `work/<order>/` в отдельной папке) — использовать его как основу нового профиля: профильные скиллы копировать, обобщённую память написать заново. Это готовые наработки, а не черновик.
- **Сдача = папка с сессией, а не unilateral-дистилляция.** Владелец: «Это история + профиль заказа. Цель из его наработок сделать шаблон. Пришли папку с сессией». Порядок: собрать папку (`session.md` + `session.json`, `skills-*/`, `MEMORY.md`/`USER.md`, `config.yaml`, `SOUL.md`, `README.md` с картой) и отдать её — человек смотрит наработки и решает, что идёт в шаблон. Не переписывать каталог шаблонов из своей головы до этого: источник истины — сессия и скиллы заказа, а не реконструкция по ТЗ. `sqlite3.connect("file:%s?mode=ro" % db.as_posix(), uri=True)` для чтения чужой сессии без блокировок.
- **Сессии заказов лежат в `state.db` АКТИВНОГО ШЛЮЗА, а не профиля заказа.** `profiles/<slug>/state.db` (на этой машине `slug`) содержит `sessions`/`messages`; `state.db` самого `ord-*` профиля — 0 байт, потому что агент работал под шлюзом. Искать так: `SELECT id FROM sessions WHERE session_key LIKE '%:group:<chat>:<topic_id>' ORDER BY id DESC LIMIT 1`, ключ вида `agent:main:telegram:group:-1004489232913:631`. Без этого шага дистилляция получает «сессию не нашли» на полностью отработанном заказе.
- **Порядок выпуска** (`session_distill.py` + `profile_graduation.py`): сессия → чистка транскрипта → дистилляция одним вызовом модели → `hermes profile create <name> --clone-all --clone-from <ord-…>` → вычистить историю/память → записать скилл и ОБЩУЮ память → зарегистрировать шаблон. Кнопка «🎓 Собрать шаблон из заказа» (`graduate:<pk>`) спрашивает имя через ForceReply (`_start_profile_input` с action `grad_name`, не выдуманным `_клавиатура_force_reply`).
- **Регистрируя скиллы клона в БД, не импортировать всё подряд.** `profile create --clone-all` приносит 60+ базовых скиллов (`apple`, `devops`, `.archive/...`). Обход `skills/` без фильтра дал 69 записей вместо 5 профильных. Вести whitelist по именам из пакета заказа и сверять итоговый список; профильные скиллы без `SKILL.md` (только `scripts/`) записывать вручную с кратким телом, а не пропускать.
- **Базовые скиллы возвращаются в профили после рестарта шлюза/обновления.** Профиль, созданный с `--no-skills --no-alias`, через время показывает десятки чужих скиллов (включая `.archive/`). Проверять ТОЧНОЕ множество имён в конце работы, а не «скиллы есть»; образец — `tests/test_profile_isolation_final.py`. Вместе со скиллами возвращаются `memories/MEMORY.md`/`USER.md` шаблона, а `SOUL.md` остаётся копией роли шаблона (воркер-парсер) — переписывать роль и память вручную и требовать тестом отсутствия чужих маркеров. Перед чисткой — бэкап `skills/`, `SOUL.md`, `memories/`; синхронизировать и БД портала (`profile_store.skills()`), иначе `/api/profiles` показывает чужие скиллы при чистых файлах.
- **Шаблон — это обычный профиль Hermes.** Поэтому инструменты берутся клоном профиля заказа, а уникальность даёт только `skills/<slug>/SKILL.md` + `memories/MEMORY.md`. Память шаблона пишем ОБЩУЮ (без номера заказа, имени заказчика, ссылок и цен), иначе следующий заказ узнает про предыдущего клиента; `sessions/`, `plans/`, `pending_messages/` после клона удалять.
- **Ключевые слова подбирать по ОСНОВАМ, не по вхождению.** `«листовка» in «создать листовку»` ложно, и реестр шаблонов не срабатывает никогда. Сравнивать нормализованные основы (первые ~6 букв, `re.split(r"[^\w]+")` по тексту): совпадение основы ИЛИ префикс в любую сторону.
- **Дистилляция обязана уметь сказать «нечего переносить».** Сессия, выродившаяся в уточняющий диалог, даёт `skill_body = "НЕТ-ПОВТОРЯЕМОЙ-РАБОТЫ"` → `ok:false` с внятной причиной, а не вымученный скилл из воздуха. Транскрипт чистить от секретов (токен бота `\d{8,12}:[A-Za-z0-9_-]{20,}`, `sk-…`, `Bearer …`, `пароль=…`) и НЕ тащить в промпт вывод инструментов — только их имена и счётчики, иначе контекст распухает.
- **Ответ модели — один JSON-объект, а не batch-массив.** `mll_models.parse_batch_array` ждёт массив с `id` и падает `missing ids`; для одиночного объекта нужен сканер сбалансированных `{}`, который переживает ```fenced```-обёртку и текст вокруг.
- **Проверять весь путь живьём, а не только юнит-тестами.** Смоук: `session_distill.find_session(<topic>)` → `transcript` → `distill` → `ProfileFacade().graduate(...)` → проверить, что в профиле появился `skills/<slug>/SKILL.md` с шагами, а `match_template` находит шаблон по фразе из заказа. Дистилляция стоит один вызов модели и минуту; юнит-тест с мок-моделью не показывает ни мусорного JSON, ни пустой сессии. Контракты модулей, порядок вызовов и готовый смоук — `references/order-template-graduation.md`.

## Корневой сценарий качества (наследует КАЖДЫЙ профиль)
- **Универсальный пейплайн живёт в корне профиля, а не в скилле под нишу.** `root_playbook.py` ставит `skills/joblock-order-playbook/SKILL.md` в КАЖДЫЙ профиль через `clean_profile.sanitize()` — включая `empty` и профиль заказа. Иначе «чистый» профиль не знает про QA-гейты и начинает каждый заказ с нуля, а ошибки качества повторяются. Корневой скилл не зависит от ниши; профильные скиллы добавляют детали, но не отменяют шаги.
- **Пять проверок ДО старта заказа, а не разбор после:** полный ли вход (нет материалов — спросить, не выдумывать); инвентаризация активов (`ls` рабочей папки и `sources/` — поиск без неё съедает минуты на 403/404, пока пригодные файлы уже лежат на диске); замок скиллов (не редактировать и не перечитывать свои скиллы внутри заказа — это дрейф, а не работа); модель в `model.default`; формат сдачи. Подробный контракт — `references/universal-order-qa.md`.
- **QA — machine-readable, а не «проверил глазами» и не текст в чате.** Промежуточные проверки инструментом в `qa/checks.json`, три оценки 0–100 в `qa/score.json`, финальный `qa/deliver.json` с путём артефакта и `checks_passed`. Портал считает заказ сданным только по контракту; любая ось < 80 — возврат к шагу, её давшему. «Готово» в сообщении без `deliver.json` — не сдача.
- Синхронизируй счётчики скиллов в `profile_store` после установки корневого скилла: `/api/profiles` и тесты изоляции считают его обычным скиллом (базовый каталог становится 1 / 6 / 5 вместо 0 / 5 / 4).

## Внешняя база скиллов (отдельная сущность)
- **Внешняя база скиллов автономна: не связывать её с профилями без явной просьбы.** Источник — реестры (`hermes skills search ... --json`: clawhub, official, skills.sh, github и др.), а не `profiles/<name>/skills`. Хранить в `skill_catalog` + `skill_tags` с таксономией по тегам, поиском и группировкой; страница `/skills`. Не добавлять связи с `profile_templates`, пока владелец явно не попросит. Образец тестов — `tests/test_skill_library.py`.
- **Один модуль для MySQL и SQLite: `%s` → `?` адаптером курсора**, а не правкой каждого запроса — иначе тесты на SQLite падают `near "%": syntax error`. Идентификатор из `skills search --json` содержит `/` (`skills-sh/anthropics/skills/pdf`) — валидатор имени обязан разрешать слэш.
- **Внешняя база — справочник, а не источник готовых сборок.** Тела скиллов там пустые (только метаданные), теги выведены из слов в описании и часто неверны (`design` у скрейпинга, `seo` у грантов), `browse-sh/*` — рецепты под конкретные чужие сайты, есть дубли. Свой профиль с проверенными на диске скиллами и изолированной историей надёжнее: внешний скилл брать точечно (сначала прочитать его `SKILL.md`), 1–2 штуки как усиление к существующему профилю, а не тащить набор целиком. Перед «сборкой из базы» — пометить мусор, добавить `vetted`, подтянуть тела; число скиллов в теге — не мера пригодности.
- **Опции запуска из `empty`: «С нуля» и «Собрать из скилов из базы».** В `_меню_шаблонов` под профилем `empty` добавляются `fresh:<pk>` и `frombase:<pk>`; `pipeline_composer.py` подгоняет кандидатов из `skill_catalog` под ТЗ одним MLL-вызовом и собирает `skills/pipeline/SKILL.md` (шаги + проверки + три оценки). Гейт: любая ось < 80 блокирует сборку; детерминированный fallback обязан стартовать с 80/80/80 и помечать `source='fallback'`, иначе при недоступности модели профиль не соберётся никогда. Кандидатов искать на двух языках: русские `шортс/видео` не матчатся с английскими `shorts/video` — подставить синонимы ДО поиска, иначе MLL получает пустой список и честно ставит 0. `launch:fresh:<pk>` = `dispatch(template='empty')`; `launch:base:<pk>` = тот же dispatch + `build_profile` в созданный профиль.

## Питфоллы (дорого стоят)
- **Когда владелец говорит «всё работает, просто припиши в конфиге» — минимальная правка, без повторных smoke-проверок.** Он сам работает на этой модели; настаивать на долгой верификации после его подтверждения — трата времени. Достаточно одной сверки, что значение записалось (`mll2.настройки()['model']`, `grep default:`), и короткого отчёта.
- **Сверка файлов: папка `<SOURCE>-<id>`, не голый id.** `C:/sites/joblock/files/WORKZILLA-22547682`; поиск по числовому `22547682` покажет «файлов нет» при полностью укомплектованном заказе.
- **Доводить до работающего артефакта и проверять его, а не «докапываться».** Владелец ценит «реализовано» над долгим расследованием: минимальный working-результат + живая проверка (тест/endpoint) и короткий отчёт. Долгие догадки без проверенного результата — не работа.
- **Передачу внешнему агенту оформлять MD-файлом.** Владелец иногда ставит задачу внешнему Hermes и просит «дать задачу»: написать Markdown с фактами, путями, точными командами и ожидаемым выводом, без секретов; уточнить открытые вопросы и не начинать работу самому.
- **Делать ровно то, что попросили, в названном месте.** Владелец: «Я попросил просто в ТГ меню добавить выбор шаблона, куда ты полез?» и «почему так сложно? элементарные задачи по 30 минут делать». Если просят «в ТГ / в боте / под заказом» — править только `tg_bot.py`/`tg_notify.клавиатура_отклика`, не строить параллельную веб-модалку (она осталась отдельной историей) и не переделывать смежные подсистемы. Один заход = одно действие в одной плоскости; сначала минимальный working-результат, потом уже улучшения по просьбе.
- **Шаблон в JS внутри Python-строки: `{{ }}` только для f-строки.** Модалка была написана как f-строка, но вставлялась через `.replace()` в обычную строку — все `{{`/`}}` остались в JS, браузер получил синтаксическую ошибку, кнопка молча не работала, а `window.__openTemplatePicker` отсутствовала («Каталог шаблонов не загрузился»). Проверка: `python -c "... ' {{' in js_script ..."` → должно быть `False`, и `typeof window.__openTemplatePicker === 'function'` в консоли.
- Боты Telegram: ОДИН токен = один long-poller. Дубль процесса портала (schtasks /Run поверх автостарта) даёт вечный 409 Conflict: оба поллера друг друга выкидывают, команды копятся в очереди и не отвечают — лечится kill всех app.py и подъёмом ровно одного. Конфиг токена/чата выбирать по имени ПОТОКА (threading.current_thread().name, tg-exec → TG_EXEC_*), не по глобальной переменной: второй бот-поток, мутирующий глобальную роль, переключает токен и у первого потока — симптом «бот читает, но молчит».
- Тихий catch в long-poll цикле бота превращает ЛЮБУЮ ошибку обработки в «бот не отвечает»: падение на pymysql.connect(**DB, cursorclass=...) (в DB уже есть cursorclass → duplicate kwarg) глоталось catch-ем, апдейты съедались без ответа. Повторяющиеся connection-конфиги собирать через copy(DB)+setdefault; отладку молчания вести через лог входящих апдейтов (tg_<роль>.log), он сразу показывает — апдейт не пришёл ИЛИ пришёл и упал.
- Хранение JSON-объекта (mll/pass2) в текстовой колонке через `JSON_SET(..., %s)` кладёт ЗАКВЫЧЕННУЮ строку — `JSON_EXTRACT('$.x.y')` молча возвращает NULL, а фильтр падает в ноль. MariaDB НЕ поддерживает `CAST(x AS JSON)` (1064): при записи json.dumps-параметра перезаписывать колонку целиком из Python (json.loads → ключ → dumps), legacy-строки чинить тем же обходом.
- app.py подключение к БД — DictCursor: обращение `row[0]` киляет KeyError внутри тихого except (симптом — поле приходит None). Доставать значения по имени или `list(row.values())[0]`; отлаживая, звать функцию напрямую, чтобы except не глушил.
- Имя route-функции FastAPI затеняет импортированный модуль страницы (def mll2_page рядом с import mll2_page → 'function' object has no attribute) — route-функцию переименовывать, не модуль. POST-body `body: dict = Body(...)` требует импорта Body из fastapi; забытый импорт роняет ВЕСЬ app.py на импорте.
- Большой мульти-патчер, падающий по assert в середине, оставляет полу-состояние (routes без импортов, меню без файла страницы): правки — imports / routes / файл страницы / nav — отдельными шагами, каждый с ast.parse до записи; после любой серии правок — рестарт портала и curl каждого затронутого маршрута.
- git-bash curl портит кириллицу в JSON → запросы с русским телом всегда через файл в UTF-8 и `--data-binary @file`, не `-d '...'`. Симптом: пустые/дефолтные записи или `????` в БД.
- **Двойное экранирование `\d` в literal regex тихо выключает целые функции.** `/^\\d{4,}$/` в TS — это НЕ «цифры», а буквально обратный слэш + `d`; условие «id — число» не совпадает никогда, и код под ним (сбор вложений) не выполняется ни разу, без ошибок и без логов. Симптом: функция вызывается, но «ничего не находит», а в отладочном логе нет ни одной строки от неё. Проверять не глазами, а юнитом: `bun -e 'console.log(/^\\d{4,}$/.test("22540726"))'` → `false` при правильном `/^\d{4,}$/`. Правило: если guard выглядит очевидным, а ветка ниже «мёртвая» — сначала проверь regex в REPL, потом逻辑.
- **После полной очистки БД парсер всё равно пишет «этот проект уже был».** Собственный seen-set парсера живёт в его jsonl-логах (`feed-log.jsonl`, `kwork-log.jsonl`, `insolvo-log.jsonl`, `sandbox-log.jsonl`), а не в БД. Очистка `market_projects`/`orders` без очистки логов даёт нулевую обработку: карточки отфильтрованы ДО enrich и до POST. Для реального старта с нуля: бэкап логов в `~/backups/feed-logs-<ts>/` → обнулить все четыре → запускать парсер. Проверять по первой строке лога: «парсер: в логах 0 объявлений».
- **Chrome поднимать РОВНО той командой, которой его запустил владелец.** Рабочий вариант: `Start-Process -FilePath 'C:\Program Files\Google\Chrome\Application\chrome.exe' -ArgumentList '--remote-debugging-port=9222','--user-data-dir=C:\chrome-profile','--start-maximized','--no-first-run','--no-default-browser-check'`. Не запускать через bash-обёртку/`&`-фон/`cmd /c start` и не подставлять другой профиль (`C:\chrome-cdp-profile-2`, `agent-browser-*`, дефолтный) — тогда биржа отдаёт форму входа, и это выглядит как «слетела авторизация». Перед запуском проверить, что порт свободен (`curl :9222/json/version`), после — что вкладка показывает ленту, а не `/account/login`.
- **Не убивать `bun parser.ts` по шаблону командной строки.** Во время уборки «с нуля» поиск родителя через `Where-Object CommandLine -match 'parser\.ts'` + `taskkill` по каждому PID прошёлся по живому сборщику, и лента встала на 3 часа молча: `mode.json` = `search`, `can-start-parser: allowed`, а `SELECT MAX(created_at) FROM market_projects` показывает простой. Диагностика простоя ленты: (1) `MAX(created_at)` и `SUM(created_at > NOW() - INTERVAL 15 MINUTE)` — есть ли свежие; (2) `Get-CimInstance ... match 'parser\.ts'` — жив ли процесс; (3) mtime лога коннектора; (4) `curl :9222/json/list` — есть ли вкладка ЛЕНТЫ (без `/<id>`), а не только детали. Лечится подъёмом `PARSER_MARKETS=wz bun parser.ts` как tracked background + проверкой `+40 строк` в БД за 5 минут.
- **Chrome умирает, если закрыть ВСЕ page-табы через CDP.** Уборка detail-вкладок по одной — нормально; когда список page схлопывается до нуля, процесс Chrome завершается и `:9222` отдаёт connection refused. Порядок безопасной уборки: оставить хотя бы одну вкладку, закрывать остальные, затем открыть ленту заново `PUT http://127.0.0.1:9222/json/new?<url>` (именно PUT, GET вернёт 405/пусто) и проверить, что `title` показывает ленту, а не `/account/login`. Если Chrome всё же умер — та же команда запуска, что у владельца, без bash-обёрток.
- **Chrome остаётся только с вкладками включённых бирж.** Владелец: «только Workzilla, следовательно в хроме должна остаться только 1 биржа». Выключение биржи в `/settings` обязано сопровождаться закрытием её вкладок (`curl :9222/json/list` → закрыть не-Workzilla), иначе мёртвая лента висит и путает диагностику. Плюс парсер после сбора вложений оставляет вкладки деталей — держать правило «список лент + не больше одной вкладки заказа», лишние detail-вкладки закрывать. Проверка: `curl :9222/json/list` → только `client.work-zilla.com/freelancer...`.
- Python-патчи через bash-heredoc (`python - <<EOF`) ломают бэкслэши и вложенные кавычки — патчи с `\n`/кавычками в строках писать через write_file в отдельный скрипт и запускать, не heredoc-ом. Отдельная ловушка: `\\n` внутри такого heredoc разворачивается в НАСТОЯЩИЙ перевод строки, и запись `'...текст\n'` даёт синтаксическую ошибку `unterminated string literal` уже в файле. Многострочные литералы собирать через `repr(body)` одной строкой, а не конкатенацией с `\\n`.
- pymysql-запрос с литеральным `%` (LIKE '%...%') надо экранировать как `%%` — execute() форматит строку как %-шаблон; одиночный `%` даёт ValueError/AssertionError в рантайме, не на импорте.
- JS-обработчики страницы ленты держать на верхнем уровне скрипта: обработчик, случайно попавший внутрь функции автообновления, регистрируется только после первого тика — клик «работает, но не сразу», а каждый тик плодит дубли слушателя.
- Вставляя новую панель в страницу (settings/mll), не глотать существующую форму: сохранять её `</form>` и submit-кнопку; после правки UI гонять E2E через bun+playwright (browser-automation/settings-e2e.ts — клик, save, reload, checked) — curl видит HTML, но не мёртвую кнопку.
- Тёмная тема Bootstrap задаётся атрибутом `data-bs-theme`: светлую таблицу даёт `data-bs-theme="light"` на html, кастомного перекрашивания .table не нужно.
- Decimal-цены перед JSONResponse конвертировать float() (DictCursor отдаёт Decimal — сериализация падает 500 на /api/mll2/results).
- Ingest-контракт: поле цены — `price`, не `price_rub`; источник — `source`, не «источник» (ошибка ключа превращает всё в source=manual и плодит дубли MA-*).
- Коннекторная вкладка теряет «маркер» после навигации на домен биржи — переиспользование искать по домену, не по декоративному параметру URL.
- Фоновые пайплайны, спавнящие bun/playwright на каждый заказ (refresh_all и т.п.), на этапе теста поиска отключать — они мигают вкладками.
- Тест `test_start_agent_returns_dagi_error_expected` ожидает 503 при лежащем Dagi — с поднятой зависимостью он «падает» на 200: не регрессия, known-flake.
- **Тесты async API: `asyncio.get_event_loop()` не переживает закрытие цикла другим тестом.** В general-наборе тест падает `RuntimeError: There is no current event loop in thread 'MainThread'` только при запуске вместе с другими. Создавать свой цикл: `loop = asyncio.new_event_loop(); try: loop.run_until_complete(...); finally: loop.close()`.
- **Мёртвый хелпер внутри большого модуля ловится только живым прогоном.** Оркестратор вызывал `_topic_messages(...)`, которого в файле не было: `NameError` при каждом `dispatch`, при этом юнит-тесты (с мок-оркестратором) и `py_compile` зелёные. После правки модуля, вызываемого из живого пути, прогони короткий smoke именно этой функцией — компиляция не видит неопределённых имён в теле функции.
- **Вставка большого блока heredoc-скриптом может уехать не туда** (`return` вне функции, `SyntaxError`). Считать строки до/после вставки, а не «на глаз»; патчить именованный блок через `patch` с уникальным контекстом.
- **Тесты клавиатур в боте:** `_кн()` возвращает РЯД `[{...}]`, а `_кнопки_заказа()` — кортеж `(клавиатура|None, …)`. Итерировать надо `kb[0]['inline_keyboard']`, иначе `AttributeError: 'NoneType' object has no attribute 'get'` на первой же строке.
- **Тесты на моках должны проверять аргумент, а не его позицию.** `calls["args"][2] == name` ломается от любой вставки флага в команду; искать `args[args.index("create") + 1]` — тогда тест переживает безобидные правки CLI.
- **После правок тестов, мокающих оркестратор, сверять мок с реальным контрактом.** `dispatch` стал звать `cyberguse_orchestrator.run_sync(...)`; старый мок на `telega_post_order` остался, и тест падал на `NameError` из живого оркестратора — это устаревший тест, а не регрессия кода. Мокать ТОТ модуль, который вызывается сейчас.
- Полный прогон `python -m unittest discover -s tests` даёт ~37 падений на постоянных наборах (`worker_landing`, `separate_portal_pages`, `dagi_health`) — это фон, не твои правки. После правок фильтровать вывод по именам наборов (`| grep -vE 'worker_landing|separate_portal_pages|dagi_health'`) и смотреть только остаток; иначе каждая правка выглядит как регрессия.
- Новый крон-джоб на скрипт: путь должен быть в `~/AppData/Local/hermes/scripts/` и указываться именем, не абсолютом.
- Тест не патчит импорт внутри функции через `patch.object(tg_bot, 'skill_library')`: имя живёт в локальной области. Патчить `sys.modules` (`patch.dict('sys.modules', {...})`) или функцию-обёртку (`pipeline_composer.compose`), которая реально вызывается, — иначе мок не перехватывает вызов и тест падает только на живом прогоне.
