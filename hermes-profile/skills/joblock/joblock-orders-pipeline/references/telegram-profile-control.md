# Telegram control bot and Hermes profile switching

## Control-plane contract
- Keep the roles separate: `hermesworkertask_bot` in `-1004478446318` is the orders/control bot; `hermesworkerfreelance_bot` in `-1004489232913` is a plain native Hermes gateway.
- Put `/menu`, profile management, and per-order profile assignment only in the orders group. Do not add a custom echo/long-poll worker, menus, or preset commands to the executor gateway.
- Retire the old `presets.json`/`/use` model when profile controls are available. A profile is the actual Hermes home (its own config, model, memory, skills, sessions); a menu label or order assignment is not a profile by itself.

## Switching one shared executor bot between profiles (Windows)
This host uses the same executor bot token for the selected named profile, so only one named profile gateway may poll it at a time.

1. Validate the requested profile against the profiles discovered under Hermes' profile root; never interpolate arbitrary names into a shell command. Restrict profile mutations and switches to the owner in the orders-control chat.
2. Copy the executor Telegram settings into the target profile's `.env`; preserve its own model, SOUL, memory, and skills. Set a profile-local `TELEGRAM_ALLOWED_CHATS` for the executor group (and authorized owner), because inherited process environment can override YAML allowlists. Write `telegram.allowed_chats` as a JSON array string (for example `'["353169388","-1004489232913"]'`), not a Python-style single-quoted list; verify the adapter resolves the exact chat ID before relying on it.
3. Stop the current profile with `hermes -p <old> gateway stop`, disable its `Hermes_Gateway_<old>` Scheduled Task, enable the target task, and run it with `schtasks /Run /TN Hermes_Gateway_<target>`. Create the target task once with `hermes -p <target> gateway install --no-start-now --start-on-login` when missing.
4. Wait for `hermes -p <target> gateway status` to show a running PID, confirm the target log says Telegram polling is healthy, and only then persist the active-profile marker. If startup fails, disable the target task and restore the previous profile before reporting failure.
5. Verify the old profile reports no gateway process and its task is disabled. `State=Ready` alone is not proof of a running task or gateway.

The menu should display the profile's configured model and human description. Apply profile-default model changes with `hermes -p <profile> config set model.default <provider/model>`; a Telegram session that already exists may remain pinned to its earlier model, so start a fresh chat session with `/new` before comparing defaults.

## Profile lifecycle controls
- Create a fresh profile with `hermes -p <active> profile create <slug> --no-alias --description <text>`.
- Fork profile context/memory/skills without inheriting old chat transcripts or scheduled jobs with `hermes profile create <new-slug> --clone-all --clone-from <source> --no-alias --description <text>`.
- Rename the canonical profile ID with `hermes profile rename <old-slug> <new-slug>`. On Windows, also remove/disable the stale `Hermes_Gateway_<old-slug>` Scheduled Task and create/enable the new task if the renamed profile was active; the native rename helper's service cleanup is not a replacement for Windows task cleanup.
- After create/fork/rename, refresh the profile list from Hermes' profile directories rather than maintaining a second independent list. Dormant profiles may retain the executor token, but only one gateway task/process using that token may be enabled/running; never print the token.

## Per-order profile assignment and Hermes intake
- Persist the profile assignment by the stable `(source, external_id)` pair; marketplace IDs can collide across sources. Include the complete `description`, title, URL, price, and attachment names/paths/URLs in the intake event—never send only the title.
- Make intake idempotent: store a unique delivery ID and status before dispatch, refuse duplicate delivery while accepted/in-flight, and allow an explicit retry after a confirmed failure. Treat HTTP `202 accepted` as admission only, not proof that the model finished or the Telegram reply was delivered.
- A Telegram Bot API `sendMessage` from the orders bot to the executor group is only a visible bot-authored message; it does not create a Hermes user turn. Do not substitute an acknowledgement/echo for real agent input, and do not write synthetic user rows directly into Hermes' SQLite transcript.
- Hermes' native webhook adapter starts a separate, one-shot webhook-source session per delivery and can cross-deliver the result through that profile's Telegram adapter. It does not continue the persistent Telegram group conversation; if the requirement is to resume that exact chat session, verify a supported gateway admission mechanism before implementing it.
- Bind any internal intake webhook to loopback, require HMAC, use unique delivery IDs, and never place its secret in logs or command output. Completion gate: verify the profile route/config, ensure only one named gateway task is polling the shared token, submit a harmless signed smoke-event (not a customer order), read back its accepted status and delivery ID, then wait for and verify the actual Hermes reply in the executor group. After code changes, restart the single portal task and verify `/menu` plus a real callback in the orders group. HTTP `202` proves admission only, not task completion or Telegram delivery; do not report intake complete until the response arrives. Clean up any disposable profiles or smoke artifacts.

## "Run order" button: profile from template → topic → plan
- The per-order «▶ Выполнить» action (`portal/start_order.py`, `POST /api/orders/{number}/start`) is the automated counterpart of «Обучить профиль»: one click forks the template into `ord-<order_number>`, posts the order to the executor chat, and posts a plan. It never touches the exchange and never needs a second owner confirmation beyond the click.
- Pick the template by order semantics, not a hardcoded slug. Enumerate real templates via `profile_switch.MANAGER.profiles()`; plausible names are `browser`, `design`, `dev`, `retouch`, `text`. A hardcoded name that does not exist returns `Шаблон не найден` on every click. Keyword hints: design/макет/листовка/дизайн → `design`; парсер/автоматизация/бот → `browser`; текст/копирайт → `text`; сайт/api/сервер → `dev`.
- **`--clone-all` copies the template's memory too — sanitize after forking.** Verified live: a forked order profile contained the template's `memories/MEMORY.md` (unrelated project facts), so order context leaked between orders. `sessions/` is empty, but `memories/` is not. Call `clean_profile.sanitize(profile_dir, order=order)` right after `fork_profile` and before writing the order context: it wipes memory and sessions, keeps `skills/`, `config.yaml`, `.env`, and writes memory scoped to that order (id, title, brief, URL, budget). Assert `clean_profile.is_clean(profile_dir)` in tests — absence of foreign markers in memory and no session files.
- Keep the AUTHORIZATION chat and the DELIVERY chat as separate arguments. `fork_profile` validates the owner against the orders-chat ID, while the order itself is delivered to the executor group. Passing one `chat_id` for both fails with `Fork профиля разрешён владельцу только в чате ленты заказов`. Signature: `dispatch(..., chat_id=<delivery>, owner_chat_id=<orders chat>)`.
- Send through the GATEWAY token, not the orders-bot token. The two bots are in different groups and each sees only its own: the orders token gets `chat not found` for the executor group, the gateway token gets `chat not found` for the orders chat. Resolve `chat_handoff.gateway_token()` first and keep `.env` only as fallback; when `chat not found` appears with a live token, test both tokens with `getChat` before touching chat IDs.
- The plan layer (`portal/planner_layer.py`) is deterministic — it does NOT call a model. It reads the newly forked profile's `skills/` directory, buckets skills into stages (Подготовка → Разработка → Проверка → Сдача) by name, numbers the steps, and renders plain Telegram HTML (≤4000 chars, escaped, no code fences) with inline buttons. With zero skills it emits one honest generic step rather than an empty plan. Re-read skills from disk each run — a freshly forked profile is the whole point.
- Persist the profile row before posting (`order_profiles` → `ord-<order_number>`, status `ready`) so a repeat click reuses the profile instead of forking twice. Report `profile`, `template`, `message_id`, `plan_sent`, `plan_steps` and treat a failed post as a hard error (`ok: false`) with the profile left in place for retry.
- Verify end to end with a real click, not a mock: HTTP 200, the `order_profiles` row exists, and the executor chat received both the card and the plan (read back message IDs). Do not test against a live customer order without permission.

## Orchestrating through the human account (Telethon userbot)
Bots cannot read messages written by other bots. When a Hermes profile must ingest a topic's content, the message has to come from a **human** account — that is why the userbot is the orchestrator, not a bot.
- The orchestrator is the Telethon userbot session of `@ds_cyber` (user id 7525923034, `bot=False`), kept in `C:/sites/joblock/wintask_watch/`: `wintask_watch.env` holds `TG_API_ID`/`TG_API_HASH`, and the live session is the local `session.session`. The `TG_SESSION` value in that env points at a dead path (`/home/main/tguser/session`) — ignore it and use the file next to the script.
- Telethon belongs in the PORTAL's virtualenv (`.../hermes-agent/venv`), not the system python; the portal runs under that venv, and a missing module there means the button fails at runtime.
- Topic management calls live in `telethon.tl.functions.messages`, not `...functions.channels`: `CreateForumTopicRequest`, `GetForumTopicsRequest`, `DeleteTopicHistoryRequest`. Every one takes `peer=`, never `channel=`; passing `channel=` raises `TypeError` before any request goes out.
- Deleting a topic clears its messages but leaves the topic object; a later `find_topic_for_order` must still match by name prefix and reuse it, not create another. Keep the "manual topic" allowlist (`General` and similar) so the orchestrator never reuses or deletes human-created topics.
- `asyncio.run()` throws inside a running loop (FastAPI handlers). Route the coroutine through a worker thread with its own loop when a sync entry point (`run_sync`) is called from async code.
- Success proof is chat-visible, not an HTTP code: read back the topic's messages and confirm a `ds_cyber`-authored card and plan exist AND that the gateway bot (a different sender) is replying inside that same topic. Only then is the "human writes so the bot can read" loop actually closed.

- «Откликнуться» is an owner-only bot callback, never a URL shortcut. Generation is not a bid and must not change bid/order status.
