# JobLock: standard order base + thin connectors + sequential cycle

Use when adding an exchange connector, changing the order feed/status filters, working on the cycle engine (`portal/cycle.py`), exchange toggles, or publishing the code to GitHub. The legacy portal/parser detail lives in the user-owned skill `joblock-agent-portal` — read it, do not edit it.

## Architecture rules (owner-set, always-on)
- The standardized order base (joblock MariaDB) is the single truth. A connector is THIN: normalize feed cards to the common schema (`source`, `external_id`, `title`, `description`, `price`, `url`) and POST to `/api/ingest`. Classification, statuses, assignment are central — never in a connector.
- Keep status projections in sync: when deduplication marks `market_projects.status='dublicate'`, mirror that status to the linked `orders` row by `order_number` and render it as a duplicate, not `new`; map `needinfo` to waiting. Otherwise the portal reports already-handled duplicates or customer waits as fresh work. For backlog triage and safe reconciliation, follow `references/order-status-reconciliation.md`.
- Ingest card field is `price` — sending `price_rub` silently prices every order 0.00 (check `market_projects.price` by source after wiring a connector).
- `source=sandbox` cards go to `market_projects` only (demo queue), never to production `orders` — by design.
- Fabra is out: `PARSER_SINK=joblock` in browser-automation/.env; no Fabra toggle in settings.
- All active exchanges share ONE adapter: `portal/marketplace_adapter.py` owns market names, project/apply URL templates, the uniform notification keyboard and flow steps. `tg_notify.url_отклика` and the Telegram card must DELEGATE to it — a second hand-written switch silently omits a market when the owner enables it. `active_markets()` reads `mll_settings.json → биржи`; never hardcode the enabled set, and derive test expectations from the same settings so disabling markets does not break the suite.
- Hermes handoff is an explicit task dispatch: send the selected profile the full description, a readable plan, and attachment references; never rely on the owner forwarding order context manually. Fingerprint description + plan + attachments for idempotency so identical sends are blocked but a materially updated brief can be resent.
- A native Hermes webhook runs in a one-delivery session that closes after completion; it does not seed the profile's continuing Telegram conversation. Start work in that webhook turn, but never promise later free-form turns inherit its transcript. For continuation without manual forwarding, persist the active order as untrusted data at the selected profile's `joblock_orders/active_order.json`; atomically replace it on reassignment, include the readable plan and local attachment paths, and omit signed remote URLs. Install/load a profile-local `joblock-active-order` skill and include both that skill and `context_path` in the webhook prompt so later order-related turns can read the inbox. Never put raw customer instructions in trusted `MEMORY.md`/`SOUL.md`, and never edit Hermes session databases to fake continuity. Verify inbox readback, route skill binding, webhook acceptance, and assignment readback before claiming handoff.
- Distinguish webhook acceptance from task completion: after dispatch, read back the source-qualified assignment and verify gateway processing/delivery before claiming the profile completed work.
- In both order-assignment and training profile pickers, expose base-model changes per profile; derive choices from configured/approved model IDs, use short callback keys within Telegram's 64-byte limit, and gate save callbacks to the owner. Persist only with `hermes -p <profile> config set model.default <id>`, read the profile config back, state that the new default applies to new runs rather than the existing session, and return to the picker without dispatching the order.
- Exactly one state at a time: search (tick 60 s) → chat (tick 300 s, only if dialogs) → execute (focused order only). Strictly sequential — no parallel workers. Mode switches ONLY via `reviews/mode.py переключить X` (single writer of mode.json), each switch logged WITH its trigger.
- Owner reads state on /portal/collector: bold current mode + sequential journal with switch triggers (`portal/cycle_journal.jsonl`, `cycle_state.json`, exposed as `цикл` in `/api/collector-log`).
- Root `/` is the order feed with canonical-status filter tabs (all/new/active/waiting/done/failed/blocked/closed); kanban and Dagi were removed by owner order — do not resurrect without an explicit request (jobsy agent start 503s until Dagi is re-raised deliberately).

## Adding an exchange connector (procedure)
1. Probe the feed in the visible Chrome (CDP :9222) with a bun probe script: page URL, card selector, auth state. Workzilla feed is `client.work-zilla.com/freelancer` (cards `[data-order-id]`, price = trailing number); FL.ru is `fl.ru/projects/` (cards `[id^=project-item]`, goto timeout 60 s — 30 s flunks); Kwork seller URL `/my_services` 404s — find the current one before wiring.
2. Write `browser-automation/<x>-demand.ts`: attachToVisible → extract cards (id, title, price, replies, url) → print JSON. Test: run it, check count/median price.
3. POST a few cards to `/api/ingest` MANUALLY and read back `market_projects` by source: count > 0 AND price > 0 — then wire into `cycle.py` search tick (both feeds run inside the same tick, sequentially).
4. Add the exchange to `portal/settings_page.py` `БИРЖИ` tuple; restart the portal (kill python app.py processes, `schtasks /Run /TN "JobLock-Portal"`). Verify `GET /api/settings/exchanges`.

## Settings toggles
- Storage: `portal/mll_settings.json` key `биржи`; page `/settings`, API `/api/settings/exchanges` (POST merges over existing keys). FastAPI gotcha: the module must `from fastapi import Request` at TOP level — a Request imported inside the install function breaks annotation resolution and POST becomes a 422 on a phantom query param.
- The cycle does not yet filter its feeds by the toggles — wire `активные()` in before trusting the checkboxes as control.
- Starting the feed from scratch is a full procedure, not a single truncate: back up order rows, clear the order tables, set only the wanted exchange active in `mll_settings.json → биржи`, then RESTART the parser with `PARSER_MARKETS=<wanted>`. An already-running parser keeps logging found cards but does not refill the emptied table. Confirm `COUNT(*)` grows within ~30 s and close stale exchange tabs in the visible Chrome. Exact commands and the FK/backup pitfalls: `references/feed-clean-restart.md`.

## Portal page gotchas
- Page wrapper for root: fake `Request(scope={"type":"http","query_string":b""})` — missing `query_string` raises KeyError; a wrapper returning `orders_page(...)` directly nests HTMLResponse in HTMLResponse → 500, return `.body.decode("utf-8")`.
- The portal has ONE theme: `portal_theme.py` plus an `app.py` HTTP middleware injects the shared `<style data-portal-theme>` before `</head>` of every HTML response. Do not add `NAV_CSS` or a new palette to individual pages; concatenating CSS after a closing `</style>` renders it as visible text at the top of the page, and the owner rejects mixed light/dark themes and raw CSS in the body. Remove any old per-page `NAV_CSS` concat when adding the central theme. Pass the bare key to `render_nav` (`mll`, not `/mll`) so the active tab highlights. Verify the rendered page through the public nginx URL, not only `127.0.0.1:8701`, because only `/portal/` is proxied.
- When the middleware rewrites an HTMLResponse, consume `body_iterator` with `async for` and drop `content-length`/`content-type` from the copied headers before constructing the replacement, otherwise every page 500s with `Response content longer than Content-Length`.
- Every JS `fetch()` in a portal page must compute `const apiPrefix = location.pathname.startsWith('/portal/') ? '/portal' : ''` and call `apiPrefix+'/api/...'`. An absolute `/api/...` path through nginx returns an HTML 404 page, which the browser reports as `SyntaxError: Unexpected token '<' ... is not valid JSON`.
- `app.DB` sets `cursorclass=pymysql.cursors.DictCursor` globally; code that indexes rows positionally (`fetchone()[0]`) must open `conn.cursor(pymysql.cursors.Cursor)` explicitly, otherwise cleanup/statistics raise `KeyError` before any write executes.
- Inline-page edits with Cyrillic/escapes: build them as a patcher file via write_file, never inline heredoc (see windows-persistent-services pitfall), then `ast.parse` before restart. Backreference strings like `r"\1/"` can arrive on disk as a control character when passed through shell heredocs — use `lambda m: m.group(1) + "/"` in `re.sub` or the patch tool instead, and assert on a real input string.
- When simplifying a page control, delete every JS reference to the removed element in the same patch: a leftover `inp.value=''` throws after a successful fetch and the UI reports failure even though the operation already happened. Validate the rendered JS with `node --check` and exercise the real endpoint before claiming it works.
- The feed label «оценка_вайт» is status `ready`; «white list» is status `white`. A selector meant to show evaluated orders filters `status='ready'` with a non-null analysis, never `white` — mixing the two yields the wrong count and the wrong cards.
- Batch MLL evaluation runs in a loop until the queue drains. Sanitize every LLM-returned field (`quote_range_rub`, numeric scores, enums) into its expected shape BEFORE strict validation: one malformed field that raises leaves its row unprocessed, so the next tick selects the same batch and re-evaluates it forever, spending money. Cover it with a test that a string quote becomes `{min,max}` and garbage becomes null.
- Scoring and reply generation are separate calls. The scoring prompt judges only executability and price adequacy (0–100), lists why a project is good/bad, and never writes reply text; the reply call consumes the order material, the full model registry and the whole portfolio catalog, picks 2–3 models by context as a comma-separated list, and links exactly the matching portfolio subcategory. Keep the owner's editable examples block inside the scoring prompt — that is how he teaches «good/bad» from live feed cards.
- The operator reset on `/mll` is a single button with no confirmation field; its endpoint must match the `/api/mll2` prefix the page JS builds. Backup, cleanup and restore recipe: `references/feed-clean-restart.md`.

## Telegram order menu, profile catalog, and agent isolation
- When the owner asks for a change in the Telegram bot menu, change ONLY `portal/tg_bot.py` and its tests. Do not expand a bot-menu request into a web portal or catalog-page refactor; build web UI only on an explicit request for it.
- Populate the agent catalog from real Hermes profiles and real skills (profile list on disk, skills from the order's actual session). Never invent catalog entries, icons, skill names, or "template" descriptions — the owner rejects fabricated profiles and wants every listed agent to be one that really exists.
- Testing costs money: validate with mocks and at most 1-2 targeted real dispatches. Never create a profile per test fixture or launch many gateways/agents concurrently; no bulk profile/agent runs "for testing".
- `profile_switch.MANAGER.switch()` changes HERMES_HOME (skills, memory) but does NOT namespace session keys. Session keys get the `agent:<profile>` prefix only when `gateway.multiplex_profiles: true` (`gateway/run.py`, `build_session_key`). Sequential switching isolates skills, not conversation history; for genuine per-topic isolation enable multiplex and route by `thread_id`.
- Trust the process list (`CommandLine` containing `--profile X`) over `gateway_active_profile.json` when deciding which profile is live: watchdog tasks rewrite the state file and resurrect stopped gateways. Disable the watchdog task first, then stop the gateway, then fix the state file, then re-verify after one watchdog interval.
- Inline keyboard rows must be flat lists of button objects. Appending a list of buttons as a row yields nested JSON that Telegram rejects; assert the exact keyboard shape in tests (flatten recursively), not just button-text presence.
- Use the agent's own order-session bundle (session transcript, pipeline, real skills) when graduating a finished order into a catalog profile. See `references/hermes-profile-isolation.md` for the multiplex recipe and verification commands.
- `apply:` and `respond:` are different phases: `apply:` only prepares/shows a draft and must be labeled «Подготовить черновик»; `respond:` is the actual send. Mode `respond` is a dedicated phase: stop parser, detail collector, chat monitor and demand scripts, then re-enumerate command lines and abort the send if anything is still alive — one `mode.py` switch does not guarantee a full stop. Keep Chrome and the portal process alive while doing it.
- Owner-set menu format: the Telegram menu is a **top-to-bottom sequence of user steps** (`Заказы → Каталог агентов → В работу → Закрыть`), NOT numbered labels. Technical controls (профили, шлюз, топики, активный профиль, «отправить результат») belong at the end under `🔧 Техника`, never in the top-level flow. When the owner says «не цифрами, а последовательностью», remove numeric prefixes rather than renumbering.
- The three catalog profiles are exactly `video-shorts`, `pdf-edit-pro`, `empty`; intermediate `ord-*`/`flyer-*`/generic profiles are iteration garbage removed on the owner's command. Keep `profile_templates` in the DB in sync with the on-disk set and `skills_count`.
- Launching a new pipeline from `empty` offers two options: `fresh:` (isolated profile + topic + MLL evaluation + order files) and `frombase:` (MLL fits catalog skills to the brief → pipeline steps, checks, three 0–100 scores → `build_profile` gate blocks any axis < 80). The catalog base is a standalone reference; do not auto-load its skills into profiles or wire it into the technical skill set. See `references/profile-isolation-and-menu.md` for the full procedure.
- Every profile, including `empty`, inherits `joblock-order-playbook` through `clean_profile.sanitize`. Order execution writes `qa/checks.json`, `qa/score.json`, `qa/deliver.json`; any axis below 80 blocks the deliverable. Never prune the playbook out of a profile's skill set when cleaning iteration garbage.
