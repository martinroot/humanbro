# Экран статусов, который владелец реально смотрит

Владелец отверг канбан: его постоянный запрос — **таблица текущих заказов
с читаемыми статусами** (фильтры, живое обновление, читается с телефона).
Это главный экран витрины, а не доска задач.

## Устройство

- `portal/orders_view.py` → `/` (HTML) + `/api/orders` (JSON). Страница сама
  дёргает JSON раз в 30 с и перерисовывает строки без перезагрузки; под
  860 px строки складываются в карточки (`td:before` по `data-l`).
- Сверху — табы-счётчики (`Все / В работе / В очереди / Сдан / Отменён /
  Не сверено`), клик фильтрует по `exchange_status`.
- Строки несут ОБА id: `number` (`WO-…`) как ключ реестра и разрешённый id
  площадки для ссылки и опроса (ловушка хеш-номеров — в
  `references/order-status-registry.md`).
- **Фоновый сборщик** `portal/wz_pull.py`: раз в ~180 с обходит живые заказы
  (`exchange_status IN ('in_work','queued')`) через
  `bun task_status.ts <id> --json` и пишет `wz_cache.json` (заголовок, этапы,
  кнопки, счётчик сообщений, `fetched_at`). Портал НЕ ходит на биржу в запросе —
  он отдаёт реестр + кэш, поэтому витрина не виснет на медленной странице задания.
- Ошибка одного опроса пишется в кэш как `error` + время, а не выбрасывает
  строку: заказ остаётся в таблице с пометкой «не прочиталось». Удалённый
  клиентом заказ даёт именно такую ошибку, а не пропадает из вида.

## Живой слой над таблицей: бот, лог шагов, мгновенный статус

- **`/api/bot` — шапка «Бот», страница дёргает её каждые 5 с.** Режим и
  фокус — из `reviews/data/mode.json`; «что делает» — последняя строка `steps`
  по `ts` (пиши шаг в `steps` в МОМЕНТ события, не батчем: шапка читает
  только это); счётчик Workzilla-вкладок — `:9222/json/list`. Строки `mode.json`
  пишет конвейер — фокус на закрытом заказе там честный показ, а не повод
  подделывать файл руками.
- **`/api/orders/<id>/log` — лог степ-бай-степ по заказу**: шаги конвейера
  (`steps`, ✓/✗), события биржи (`flow_log`), приложенные файлы (`file_log`),
  отправки (`sent_log`). `?fmt=md` отдаёт готовый `.md` файлом — кнопка
  «лог по шагам» в строке таблицы, модалка с кнопкой «скачать .md»; формат
  сделан под заливку в LLM, когда заказ разбирают без модели. Формируй его
  из ФАКТОВ с таймстемпами, не из пересказа.
- **`POST /api/tabs/cleanup` → `tabs_cleanup.py` — это и есть «режим с одной
  вкладкой».** Читатели (`task_status`, `chat-read`) открывают вкладку задания
  и оставляют её, окно растёт и «бот хаотично перебирает вкладки». Уборка
  закрывает все Workzilla-вкладки, оставляя в режиме execute ровно вкладку
  фокус-заказа; кнопка «убрать вкладки» в шапке. Запускай после каждого
  прогона, а не «когда станет заметно».
- **`refresh_status.py <id> <этап> [примечание]` — мгновенная запись факта**
  (реестр + `wz_cache.json`), вызывается из `wz-check.ts` в момент сдачи,
  чтобы владелец увидел результат сразу, а не когда фоновый сборщик дойдёт
  до заказа (~3 мин).

### Ловушки живого слоя

- **Мгновенная запись сдачи обязана выкинуть заказ из очереди.** Карта
  «этап → статус» для сдачи даёт `state='submitted'` И
  `exchange_status='submitted'`. Вариант с `exchange_status='in_work'`
  оставляет заказ в `IN ('in_work','queued')`: табы показывают «В работе»,
  сборщик снова берёт его в обход — и сданный заказ возвращается в
  исполнение (это применение общего правила «обе строки статуса» к этой карте).
- **Тип из SQLite не тот, что в схеме.** Колонка с `1` приходит как INTEGER:
  сравнение `r["ok"] != "1"` истинно всегда, и шапка светит ⚠ на здоровом
  шаге. Сравнивай через `str(...)`.

## Откуда берутся статусы (и откуда НЕ надо)

- **Текущая правда — `reviews/data/registry.db`**, строго read-only
  (`file:…?mode=ro`): `state`, `exchange_status`, `status_note`,
  `published_url/count`, `asked/replied`, последнее событие из `flow_log`.
- **MySQL `joblock.orders` — история харвеста** (тысячи `new`/`needinfo`),
  НЕ текущая воронка, и по номерам она почти не пересекается с реестром
  (джойн `WO-<digits>` дал ОДНУ строку). Статусный вид на MySQL не строится —
  только `payload.external_id` для восстановления id и старые поля, которых
  в реестре нет.
- Если в дереве подключён второй статус-вид, оба обязаны говорить из одного
  канонического словаря (`references/order-status-registry.md`): два вида,
  разошедшихся в статусах, владелец замечает первым — и после этого не
  доверяет ни одному.

## Внешний доступ к витрине

- Точка входа владельца — `http://<публичный ip>:8080/portal/`, basic-auth,
  логин `admin`; nginx слушает `0.0.0.0:8080`, `location ^~ /portal/` идёт на
  `127.0.0.1:8701`.
- **Диагностика по коду: 502 = пароль принят, бэкенд мёртв; 401 = отвергнут
  пароль.** На «портал недоступен» сначала проверь, живёт ли python-портал,
  а не авторизацию.
- Смена пароля: `printf '%s' '<pass>' | openssl passwd -apr1 -stdin` →
  записать `admin:<hash>` в `C:/nginx/conf/.htpasswd`, старый файл сохранить,
  проверить ОБА исхода (верный → 200/502, неверный → 401). apr1 необратим —
  забытый пароль меняется, а не восстанавливается.
- `/backup/` — alias на домашнюю папку с `auth_basic off`: всё, что положено
  в отдаваемый корень, читается снаружи без пароля; архивы с ключами туда не
  класть.

## Правка портала

- Перед правкой роутов — бэкап `app.py` рядом (`app.py.bak-<дата>`).
- Hot-reload отсутствует: подхватить новый код можно только перезапуском
  процесса `python app.py`; `import` внутри обработчика кэширует модуль,
  поэтому «правка файла» без перезапуска ничего не меняет.
- Проверка после правки: `ast.parse` на изменённых файлах → перезапуск →
  HTTP 200 локально → тот же путь снаружи через nginx под basic-auth.
