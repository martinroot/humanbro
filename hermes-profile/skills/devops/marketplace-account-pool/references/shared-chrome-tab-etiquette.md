# Видимый Chrome общий: правила, без которых скрипты убивают друг друга

Проверено 21.10.2026 на мониторах чата.

## 1. browser.close() по CDP рвёт чужие вкладки

`chromium.connectOverCDP(...)` + `browser.close()` закрывает общий контекст
Chrome и обрывает вкладки ВСЕХ, кто к этому Chrome подключён. Скрипт,
отработав «как обычно», убивал монитор другого процесса:
`Target page, context or browser has been closed`.

Правило: скрипт, который работает с ВИДИМЫМ Chrome по CDP, **не вызывает
browser.close()** — выходит через `process.exit(0)`. `browser.ts`:
`closeVisible()` только сбрасывает ссылку, не закрывая браузер.

Это касается скриптов, работающих с общим окном (:9222). Скрипты с
собственными Dolphin-профилями (свой CDP-порт) закрывать могут.

## 2. Чистка вкладок съедает вкладку монитора

`closeInactiveTabs()` в `browser.ts` считает мусором всё, что не в списке
`shouldKeepMarketplaceTab`. Страница задания `/freelancer/<id>` туда не
входит — её закрывали, и опрос падал.

Решение — **замок чата**: монитор пишет `tab-guard-chat-<id>.json`
(`{ts, ids:[id]}`) и обновляет его каждый круг; `closeInactiveTabs` читает
все такие файлы и не трогает вкладки с этими id. TTL — 5 минут.

Тонкость: между `newPage()` и `goto()` вкладка выглядит как `about:blank`,
и её закрывала вторая фаза чистки. Поэтому при живом чат-замке фазу
закрытия `about:blank` пропускаем целиком.

## 3. Монитор должен восстанавливаться, а не умирать

Опрос не должен завершаться при первом сбое: вкладку могли закрыть.
Правильный цикл: сбой → переоткрыть вкладку → повторить. Ответ заказчика,
пришедший в пропущенный интервал, теряется иначе.

## 4. Не считать «нет сообщений» при неотрисованном чате

Ждать `.chat-message-row` перед чтением. Пустая страница ≠ «ответчика нет».

## 5. Правка browser.ts действует только после перезапуска парсеров

Модули импортируются один раз при старте процесса. Правка `browser.ts`
(замок чата, запрет `browser.close()`) НЕ действует на уже работающие
парсеры — они держат старый код в памяти и продолжают закрывать вкладку
монитора. После правки browser.ts парсеры надо перезапускать.

Запуск: `start-parsers.bat` (по одному процессу на биржу, `PARSER_MARKETS`
в ASCII: `wz`, `kw`, `is`). Проверка: три процесса `bun parser.ts` и
свежие строки в `parser-wz.log` / `parser-kw.log` / `parser-is.log`.

`cmd.exe /c "start ..."` из Git Bash зависает — запускать bat-файл целиком
через `cmd.exe /c start-parsers.bat` в фоне.

## 6. Признак отправленного отклика может не прийти

Слушатель `response` на `POST /api/order/v5/freelancer/accept` иногда не
ловит ответ (соединение переиспользовано, страница уже прогружена). Тогда
скрипт печатает «ответа accept не было», хотя отклик ушёл. Проверять по
странице: статус «В очереди» + наш текст в `.chat-message-row.self`.

## 7. Монитор не должен печатать старое заново

Монитор чата перезапускается (watchdog, истечение срока) и при этом
печатал в лог ВСЕ старые ответы заново — cron-доставка слала их в чат по
кругу, а пользователь получал одно и то же.

Правило: при старте монитор читает свой лог и запоминает уже напечатанные
сообщения; печатает только те, которых раньше не было. Сравнение — ПО
ТЕКСТУ сообщения, а не по позиции в списке: позиции сбиваются, когда
сообщений становится больше.

**Ключ дедупа обязан строиться одинаково при чтении лога и при добавлении.**
Строка в логе выглядит как «• 14:12 <текст>», и на одном пути из этой строки
убирали маркер «•», а на другом — ещё и время. Ключи не совпадали, и уже
доставленные ответы печатались заново по кругу. Снимать и маркер, и ведущее
время на обоих путях; ключ строим по тексту.

Второе правило: найдя ответ, монитор НЕ выходит — он печатает ответ и
продолжает ждать следующие сообщения. Выход означал бесконечный круг
«watchdog поднял → монитор напечатал → вышел → watchdog поднял».

**Один монитор — на все заказы, а не по процессу на заказ.** Каждый процесс
монитора держит своё CDP-соединение к общему Chrome; несколько таких
соединений перегружают порт 9222, и он перестаёт отвечать (`/json/version`
пустой), после чего ВСЕ мониторы падают с «goto: Timeout» и ответы
заказчиков не читаются вовсе. Один процесс с перечнем id через запятую,
одно соединение, одна вкладка, заказы опрашиваются по очереди. Детали и
схема запуска — в `references/review-loop-ops.md`.

## 8. Запуск через cmd /c с кавычками ломается

`cmd /c "C:\путь\к\bun.exe" скрипт` — cmd не понимает кавычки в пути и
падает с «не является внутренней или внешней командой». Запускать напрямую
с указанием stdout-файла:

    subprocess.Popen([BUN, "watch-chat.ts", id], cwd=AUT, stdout=файл, stderr=STDOUT)

Для фоновых процессов Windows — creationflags DETACHED_PROCESS | NO_WINDOW
(0x8 | 0x200), иначе процесс умирает вместе с вызвавшим.

Питфолл: `Start-Process -WindowStyle Hidden` из PowerShell даёт дочернему
процессу сломанный stdout — первый же `print()` падает
с `OSError: [Errno 22] Invalid argument` (на Windows print в скрытую
консоль). Демоны поднимать через Python `subprocess.Popen` с
`creationflags=0x8|0x200` и stdout/stderr в файл — как `запустить()`
в `reviews_watchdog.py`. `cmd /c start /MIN` из git-bash не детачит процесс.

## 10. Чат-ОТПРАВКА тоже обязана ставить tab-guard

`tab-guard-chat-<id>.json` защищает вкладку МОНИТОРА — но чат-ОТПРАВКУ
(`msg.ts <id> <file>`, `kwork-msg.ts`) чистка вкладок убивает точно так же:
`closeInactiveTabs` считает свежеоткрытую страницу задания «неактивной» и
закрывает её между `goto` и `fill` → массовый `fill: Target page has been
closed` / send-failed (авария 22.10: все ответы падали именно так).
Перед открытием вкладки писать замок `({ts: теперь})`, после — снять
(ts в прошлом, 2000-01-01) в `finally`. Тот же паттерн уже
в `bid-sender.ts`.

**Замок должен быть СВОИМ у каждого скрипта.** Один общий файл замка на
несколько скриптов — это не защита, а затирание: отправка вопроса и отклик
пишут в один и тот же `tab-guard.json`, второй перезаписывает первый, и
вкладку первого закрывает уборка — отправка падает с
`Target page, context or browser has been closed` ровно в момент ввода
текста. Имя файла замка — с идентификатором скрипта и/или заказа
(`tab-guard-msg-<id>.json`, `tab-guard-status-<id>.json`), а уборка
сканирует ВСЕ замки общим шаблоном (`tab-guard-*.json`) и берёт из них
и `ids`, и одиночный `id`.

## 11. Не ставить clarify_sent без проверки результата отправки

`sent` — это факт доставки, а не факт вызова. Скрипт-отправщик может
вернуть ненулевой rc (сломанная вкладка, чужой id) — флаг надо ставить
только при rc==0, иначе заказ «отвечен», а заказчик ничего не получил.
Ложный sent по Insolvo накопился потому, что send_waiting гнал ВСЕ биржи
через Workzilla-msg.ts и ставил sent безусловно. Канал тоже свой на биржу:
workzilla→msg.ts, kwork→kwork-msg.ts; нет интерфейса (insolvo) — skip и
пометить `clarify_skipped_no_channel`, не «отправлено».

## 9. Модуль нельзя импортировать ради проверки

У watchdog'а логика была на уровне модуля — `import` запускал всю проверку
и `sys.exit()`. Весь код перенесён в `main()` с `if __name__ == "__main__"`.

## 12. `page.goto` без таймаута убивает весь процесс

Навигация без явного `timeout` ждёт вечно, и непойманное исключение в
стартовом пути уносит процесс целиком: упала одна вкладка ленты — молчит
и эта биржа, и весь парсер. Правила: у каждого `goto` явный таймаут (45 с);
открытие вкладки ленты обёрнуто в `.catch(() => null)`; если вкладка не
открылась, следующий круг создаёт её заново. Проверка живости парсера — по
ПРОЦЕССУ И свежести лога одновременно: лог остаётся свежим несколько минут
после смерти процесса, и по нему одному мёртвый парсер выглядит живым.

## 13. Порядок: сначала живой контур, потом диагностика

Когда ломается чтение ответов заказчиков, первым результатом должен быть
работающий монитор, а не разбор причины. Поднять окно, поднять монитор,
проверить, что чат реально прочитан по одному заказу, — и только потом
докладывать причину в нескольких строках. Сессия, потраченная на диагностику
при непрочитанных ответах заказчиков, стоит денег: каждый опубликованный
отзыв ждёт того же чата.

## 14. Вкладка, которую не закрыли, — это утечка, а не мелочь

Хелпер вида `ctx.newPage()` → работа → `return` оставляет вкладку на каждом
вызове. Если хелпер зовётся по расписанию (отклик, чтение заказа, проверка
статуса), вкладки копятся десятками: общий Chrome доходит до десятков
вкладок и десятков процессов, память кончается, и CDP-порт перестаёт
отвечать. Выглядит ровно как перегрузка порта клиентами, но клиентов там
один — и искать нечего.

Правило: `try { … } finally { await page.close() }` в хелпере, который
работает с общим окном. Проверять вкладки, а не соединения: утечка идёт
по вкладкам, перегрузка порта — по соединениям.

## 15. Замок должен прикрывать свою вкладку, а не выключать уборку

Замок от отклика (`tab-guard.json`) существует, чтобы чистка не закрыла
вкладку с формой посреди заполнения. Если свежий замок заставляет чистку
**вообще ничего не делать** (`return 0`), то при откликах каждые несколько
минут замок всегда свежий — и уборка не выполняется НИ РАЗУ, вкладки растут
неконтролируемо.

Правильно: свежий замок добавляет свой id в список защищённых, а чистка
продолжает работать по остальным. Плюс имя файла замка должно
**совпадать с шаблоном, который чистка сканирует**: замок, записанный под
именем, не подпадающим под glob, не защищает ничего — и его вкладку закрывают
на ровном месте.

## 16. Уборка вкладок — одна точка, один лимит

Владелец просит централизованного управления контуром. Значит уборка вкладок
имеет один вход, один лимит и вызывается из трёх мест: из цикла парсера,
из cron-задачи и из сторожа.

Хелпер уборки: закрывает неактивные вкладки до лимита, **удаляет дубли
одного адреса** (обычная чистка «неактивных» их не ловит — дубли выглядят
активными), умеет режим «только показать счётчик» для диагностики и печатает
итог. Пол вкладок задаётся аргументом, а не константой в трёх местах.

Порядок вызова: парсер чистит каждый круг; cron-задача чистит по расписанию
(даже если парсер мёртв); сторож проверяет счётчик и чистит, если превышен.

## 17. Монитор жив, но опрашивает не те заказы

Монитор с устаревшим списком id выглядит здоровым: процесс жив, логи свежие.
При этом новый заказ не опрашивает никто, и ответ заказчика не будет
прочитан. Поэтому сторож сравнивает перечень id в командной строке запущенного
монитора с текущим множеством заказов, ждущих ответа, и перезапускает монитор,
если перечни разошлись.

## 18. Учёт откликов — отдельным реестром

Автоматический контур откликов должен знать, куда он уже откликнулся. Без
такого учёта он откликается повторно (дубль) и, хуже, неудачную попытку
помечает как отказ и убирает заказ из мониторинга — ответ заказчика теряется.

Правила:
- учёт отправленных откликов — **отдельным файлом по внешнему id биржи**,
  не путать с таблицей заказов;
- **закрывает заказ только биржа** («задание больше недоступно»); отказ по
  нашему гейту (не наш бизнес, нужен телефон, невыгодно) заказ **не** закрывает —
  он живой, его стоит пересмотреть позже;
- после успешного отклика заказ сразу заводится в реестр в состоянии
  «ждём ответа» — иначе монитор его не подхватит.

## 19. Дедупликация вкладок должна оставлять СВЕЖУЮ, а не старую

Уборка удаляет дубли одного адреса. Если из группы дублей закрываются все,
кроме ПЕРВОЙ, то под нож попадает вкладка, которую только что открыл живой
процесс: отклик на задание открывает страницу, а уборка по расписанию
успевает её закрыть — и клик по «Согласиться» падает с
`Target page, context or browser has been closed`. Признак: падает не
«страница недоступна», а именно клик, и падает у живых заказов.

Правила уборки дублей:
- из группы одинаковых адресов оставляем **последнюю** (самую свежую) — она
  открылась позже всех и принадлежит текущей работе; старые уходят;
- вкладку, помеченную занятым флагом, не трогаем вовсе.

Занятость помечается изнутри: хелпер, открывающий вкладку в общем Chrome,
ставит на ней маркер (`window.__hermesBusy = true`), а уборка проверяет его
на каждой вкладке перед закрытием. Маркер снимается вместе с вкладкой
(`finally`), поэтому «залипший» флаг не блокирует уборку навсегда. Это
дешевле, чем файл-замок на каждый запуск, и работает между процессами.

## 20. Уборка вкладок — по часовому поясу процесса, а не по факту открытия

Проверка «вкладка занята» не должна опираться на время её открытия: часы
процессов в контейнере идут с разным смещением, и «свежая» вкладка
окажется старой. Помечать занятость явным флагом в самой странице — тогда
решение не зависит ни от часов, ни от порядка событий.

## 21. Уборка не должна закрывать вкладку, ОТКРЫТУЮ СЕЙЧАС

Флаг занятости (раздел 19) защищает вкладку, но только если его успели
поставить. Между `newPage()` и первой командой скрипта вкладка ещё никем не
помечена — и уборка по расписанию успевает её закрыть. Симптом узнаваем: падает
не «страница недоступна», а именно клик по элементу, и падает у живых
заказов; в логе `Target page, context or browser has been closed`.

Два заслона, оба обязательны:

- **помечать занятость сразу после открытия вкладки** — но НЕ через
  `page.evaluate`: метка ставится в текущий документ, а первый же
  `page.goto` внутри рабочей функции уничтожает его навигацией, флаг
  теряется, и уборка снова считает вкладку свободной и закрывает её посреди
  работы (симптом всё тот же: `Target page ... has been closed` на
  `evaluate` внутри `fn`, и он возвращается после «фикса» evaluate-вариантом).
  Правильная механика — **`page.addInitScript(() => { window.__hermesBusy = true })`**:
  init-script выполняется на КАЖДОМ новом документе вкладки, поэтому метка
  переживает любую навигацию и защищает вкладку всё время работы `fn`;
  `evaluate` на пустой (`about:blank`) вкладке вдобавок не имеет контекста
  исполнения и падает с `Execution context was destroyed`, обрывая операцию;
- **уборке дополнительно пропускать вкладки моложе нескольких секунд** —
  возраст считается ВНУТРИ страницы (`Date.now() - performance.timeOrigin`),
  а не по часам процесса, иначе снова всплывает смещение часов из раздела 20.
  Уборка должна проверять И свежесть, И флаг `__hermesBusy`: одна свежесть
  не спасает долгий отклик (форма заполняется минуты, порог сырости уже
  прошёл), а флаг с `addInitScript` живёт всю навигацию.

Третий заслон — **повтор попытки**: скрипт чтения должен переоткрыть вкладку
и повторить заход, а не падать после первой потери.

## 22. Дубли одного адреса: решает свежесть открытия, а не порядок в списке

Две вкладки одного адреса — это утечка, но закрывать надо правильную: из
группы одинаковых адресов уходит СТАРАЯ, а свежая остаётся работать. Если
закрыть свежую — падает живой отклик (раздел 21). Порядок «оставляем
последнюю в списке» работает только при условии, что список отражает
время открытия; при параллельной работе это не гарантия, поэтому свежесть
проверяется по времени жизни страницы, а не по позиции.

## 23. Читающий скрипт ПЕРЕИСПОЛЬЗУЕТ вкладку заказа, а не создаёт свою

Правило «закрывай вкладку в finally» ломается, когда вкладку **специально**
не закрывают — чтобы рабочая вкладка заказа жила весь цикл. Тогда
read-only скрипт (`chat-read.ts`, `task_status.ts`), вызываемый по кругу,
начинает **создавать новую вкладку на каждый вызов** и оставлять её: за
одним заказом накапливаются десятки одинаковых вкладок, и общий браузер
упирается в лимит.

Правильное разделение:
- **вкладка заказа** — одна на заказ, переиспользуется всеми, кто читает
  этот заказ (искать по URL среди уже открытых, а не открывать новую);
- **своя временная вкладка** — если вкладки заказа ещё нет, скрипт создаёт
  её и закрывает **с задержкой** (минуты), чтобы результат успел увидеть
  и человек, и модель.

Проверка: количество вкладок одного и того же URL в списке CDP не должно
расти; если растёт — ищи `ctx.newPage()` без закрытия.

## 24. `/json/new` открывает вкладку только методом PUT

Открытие вкладки по CDP: `GET /json/new?<url>` отвечает 405, и скрипт молча
не открывает ничего — режим остаётся без вкладки задания, и владелец видит
«статус не переключается». Метод — **PUT**, тело пустое.
