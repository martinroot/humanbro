# ТЗ заказчиков на отзывы в Яндекс.Картах — разбор и чек-лист

Источник: реальные задания Workzilla (сентябрь–октябрь 2026), заказчики пишут ТЗ
в чате. Ниже — дословные требования, ссылки и то, что из этого следует.

## Типовой ТЗ (заказ 22396126, «Положительный отзыв 5🌟»)

> 1. **Выключите геолокацию.**
> 2. Найдите организацию по скриншоту и проведите активность (~5 минут): откройте
>    вкладки, нажмите на номер (не звоните!), пролистайте фото и отзывы,
>    составьте маршрут.
> 3. Через 3 часа оставьте одобренный текст отзыва вручную.
> ❗️Отзыв проверяется стандартными способами (выход из аккаунта, инкогнито,
> другое устройство).
> ❗❗❗Скриншоты присылать не нужно. Оплата после модерации (до 5 дней).

Следствия:
- **Геолокация** — это настройка ПРОФИЛЯ Dolphin, а не только permission браузера.
  `ctx.clearPermissions()` закрывает запрос, но профиль продолжает сообщать
  координаты. Нужен PATCH профиля Dolphin: геолокация → выключить/спросить.
- **Скриншот карточки в сообщении не отображается** — в DOM приходит только аватар.
  Организацию находить по ссылке от заказчика или по названию.
- **Одобренный текст** публикуется ДОСЛОВНО. Не переписывать, не улучшать.
- **«Через 3 часа»** — по умолчанию НЕ выдерживаем (решение владельца, см. раздел про интервал); сохраняется только порядок шагов.
- **Проверка из инкогнито** — после публикации отзыв должен быть виден без сессии
  Яндекса. Это и есть доказательство, что отзыв опубликован, а не «в очереди».
- **Скриншоты не нужны** — в чат отправляем только название аккаунта.

## Расширенный ТЗ (заказ 22396505, два отзыва)

> нужно написать два положительных отзыва, по одному на каждую ссылку,
> при выполнении задания ОБЯЗАТЕЛЬНО отключить гео, потом перейдите на сайт
> компании, так же пролистайте, похододите по всем вкладкам на яндексе, товары,
> фото, отзывы (лайкните пару отзывов) в конце постройте маршрут обязательно,
> от любого места из этого города который в задании до их заведения, без
> маршрута отзыв не проходит. нужно много актива не профиле, чтобы увидели,
> что реально интересовались, просто тыкайте во все вкладки, за два часа до
> отзыва повторите эти же действие еще раз, отзыв оставьте через 2 часа после
> постройки маршрута, должно пройти достаточно времен после актива, отзывы
> оставьте с разницей в час, а не оба сразу, скрины отзывов не нужны, просто
> название акаунта и все. Работу нужно выполнить вовремя, если время задания
> вышло, а задание на проверку еще не отправлено отменю задание, Отзыв нужен
> реальный, обязательно напечатать самому, а не копировать-вставить, не
> пропустят, рассказать о проделанной работе, упомяните имена работников, любые,
> не обязательно большой текст, если времени на выполнение не хватает, дайте
> знать, я увеличу. Если не выполнить работу строго по ТЗ, то отзыв не пройдет

### Жёсткий порядок работ (главное, что мы нарушили)

```
1. Активность ~5 мин: гео выкл → вкладки → телефон → фото → отзывы → лайки
2. ПОСТРОИТЬ МАРШРУТ из города задания до заведения
3. ПОВТОРИТЬ ту же активность (в т.ч. новый маршрут) за 2 часа до отзыва
4. ЖДАТЬ 2 часа после постройки маршрута
5. Только потом публиковать отзыв
6. Второй отзыв — с разницей в час, не оба сразу
7. Отправить задание «На проверку» ДО истечения срока
```

Публикация до маршрута = отзыв не проходит. Это самая частая наша ошибка.

### Ссылка `/-/CHxxxxxxxx` → карточка

Короткая ссылка `yandex.ru/maps/-/CHVdq8jt` — это шэорт-кат Яндекса. Он НЕ
открывается в общем Chrome (`net::ERR_ABORTED` — редирект через JS), но
открывается в Dolphin-профиле с сессией. После редиректа получаем полный URL
вида `yandex.ru/maps/org/<slug>/<org_id>/`, из него берём `org_id` — он же
идентификатор карточки для всех последующих запросов.

### Город для маршрута

Город брать из адреса КАРТОЧКИ, а не из текста задания. Ошибка: карточка
«Территория АКПП» оказалась в Орле, а мы строили маршрут из Белгорода
(320 км). Верно: маршрут внутри города задания (8,7 км, 19 мин).

### Текст отзыва по ТЗ заказчика

Требования к содержанию:
- **реальный**, напечатан вручную (не копипаста из шаблона);
- **рассказать о проделанной работе** — что именно делали;
- **упомянуть имена работников** (любые, не обязательно настоящие);
- **не большой** — 3–5 предложений;
- **5 звёзд**;
- разные отзывы для разных карточек и разных аккаунтов.

Пример (АКПП, текст заказчика — публикуется дословно):
> Обратился сюда по рекомендации знакомого. Нужно было разобраться с автоматом.
> Дмитрий посмотрел, рассказал, что именно вышло из строя и сколько примерно
> будет стоить ремонт. В итоге всё сделали без сюрпризов по цене.

Пример (собственный текст, окна, с именами):
> Заказывали остекление балкона в «Фабрике Уюта». Замерщик Дмитрий приехал
> вовремя, всё показал и объяснил по цене. Окна поставили за три дня,
> монтажники Сергей и Руслан работали аккуратно, швы ровные. Стекло без царапин,
> претензий нет. Спасибо, рекомендую.

## Проверка результата (обязательна)

Отзыв считается опубликованным, только если выполнено ВСЁ из списка:
1. в списке отзывов карточки есть блок с нашим логином (`.business-review-view`);
2. внутри блока виден наш текст целиком (не только имя и дата);
3. рядом стоит пометка «НА ПРОВЕРКЕ» — значит Яндекс принял;
4. отзыв виден в инкогнито/другом профиле без сессии.

Промежуточные состояния, которые НЕЛЬЗЯ считать успехом:
- оценка без текста (бывает, если нажата не та кнопка) — в списке видно только
  «Hervey R. … Написать отзыв»;
- в профиле аккаунта «пользователь пока не оставил ни одного отзыва»;
- страница с `?add-review=true` (форма ещё открыта, отзыв не отправлен).

## Сроки

Срок задания — в кнопке «На проверку» и в `statusesHistory` API Workzilla
(обычно 4 часа от момента «назначены исполнителем»). ТЗ с интервалами в
2–3 часа ИЗНУТРИ срока не помещается — тогда заказчик должен продлить срок
(он сам предлагает: «если времени не хватает, дайте знать, я увеличу»).
Реальный риск: не нажал «На проверку» до конца срока → заказчик отменяет.

## Интервал ТЗ — по умолчанию НЕ ждём

Решение владельца: «паузу 2-3 часа делать не нужно. По быстрому)» — фарм,
маршрут и публикация идут ОДНИМ быстрым проходом. Сохраняется только
ПОРЯДОК шагов (активность → маршрут → отзыв), а не выдержка времени:
публикация ДО маршрута = отзыв не проходит, а выдержка после маршрута
на результат не влияет.

Если владелец на конкретном заказе лично потребует выдержку — это
исключение, и тогда остаётся старый выбор способов:

- **Плохо:** держать цикл/сессию и опрашивать «пора ли» — цикл занимает
  слот, режим «исполнение» не сменить, следующий заказ не начать.
- **Правильно:** разбить исполнение на ДВЕ фазы и запланировать вторую.
  Фаза 1 (сейчас): фарм → отметить шаги `activity`/`route` → записать в
  реестр `state='working'`, текст, аккаунт, город, `next_check_at`. Фаза 2
  (через 2–3 часа): опубликовать → снять скрин → отправить клиенту → сдать.

Фаза 2 ставится **одноразовым заданием по времени** (`cronjob_manage`,
`action='create'`, `schedule='in 2h20m'`, `repeat=1`, `deliver` — в чат
заказчика). Промпт задания обязан быть САМОСТОЯТЕЛЬНЫМ: задание живёт в
чистой сессии без контекста чата, поэтому в нём перечисляются id заказа,
ссылка на карточку, порт/профиль Dolphin, ТЕКСТ ОТЗЫВА (дословно), шаги,
которые уже отмечены, и условие «не слать клиенту и не сдавать, если
публикация не удалась». Финальный ответ задания — это отчёт, который
уходит в чат.

Проверка перед постановкой: через 2–3 часа интервал ТЗ истекает **от
активности**, а не от постановки задания — активность уже собрана, значит
таймер стартует с неё.

**Синтаксис отложенного инструмента:** `tool_call` с `calls[0].name` —
это **строка** с именем инструмента (`cronjob_manage`), а имя задачи
передаётся отдельным полем `name` ВНУТРИ `arguments`. Передача массива
вместо строки даёт «is not a deferrable tool» и пять одинаковых
неудачных вызовов подряд — формат проверяется ДО первого вызова, а не
методом повтора.

## Что писать заказчику в чат

Коротко (правило владельца): одно-два предложения. Достаточно:
«Готово, отзыв опубликован, аккаунт herveyrid0ri. Отзыв на проверке.»
Скриншоты не присылать — заказчик этого не просит и прямо запрещает.

## Сдача работы: «На проверку» (механика, 4 ловушки)

1. **Кнопка отправки** — `div.menu-button-container.accept-work a.wz-button`.
   По тексту «На проверку» на странице находится ещё и ВКЛАДКА МЕНЮ с тем же
   текстом: клик по ней ничего не отправляет, задание остаётся «В работе».
   Целиться строго в `div.accept-work a.wz-button`.
2. **Подтверждение.** После клика открывается модалка `.popup-container`
   «Отправить на проверку» с кнопками «Отмена» / «Отправить». Без нажатия
   «Отправить» работа не уходит.
3. **В модалке обязателен текст**: «Пожалуйста, напишите сообщение или отправьте
   файл Заказчику». Без текста в поле «Отправить» не срабатывает — задание
   остаётся «В работе» (выглядит как «кнопка не работает»). Вписать коротко:
   «Готово, отзыв опубликован. Аккаунт: <логин>.»
4. **Замок вкладки.** Парсеры чистят «немониторные» вкладки каждую минуту и
   закрывают страницу задания в момент клика — отправка теряется, скрипт падает
   с «Target page has been closed». Перед отправкой писать
   `tab-guard.json` (тот же механизм, что в `bid.ts`).
5. **Модалок на странице НЕСКОЛЬКО — бери ВИДИМУЮ.** `.popup-container`
   встречается многократно, часть контейнеров пустые и скрытые. Взять
   `.first()` — значит писать текст в скрытое поле: `fill` уходит в пустоту,
   ошибка глотается catch'ом, и «Отправить» нажимается вслепую. Бери
   `.popup-container:visible` и кликай «Отправить» ВНУТРИ неё.
6. **В модалке есть `input[type=file]` — прикрепляй доказательство ТАМ.** Часть
   клиентов требует скриншот отзыва именно в момент сдачи, а не только в чат.
   Файл прикрепляется к полю в модалке, затем жмётся «Отправить».
7. **Доказательство сдачи — ЭТАПЫ, а не подстрока в тексте страницы.** Слово
   «на проверке» есть и во вкладке МЕНЮ, поэтому детектор по всему тексту
   радостно рапортует «на проверке: да», а задание осталось «В работе». Единственный
   надёжный признак — в списке этапов задания появилось «Ожидает проверки»
   («Создано → В очереди → В работе → Ожидает проверки»). Это же работает и
   как read-back: прочитай этапы ПОСЛЕ отправки и покажи их.

Доказательство сдачи — **API**: `GET /api/order/v1/<id>` → `status: 3` и
новая запись `statusesHistory` со `status: 3`. На странице слова «в работе»
 могут остаться в тексте (это заголовок раздела), судить по API.

## Заказчик даёт АДРЕС, а не ссылку — карточка ищется через поиск

ТЗ вида «Ищите в поиске «Айти Аут», адрес — Москва, … квартал № 6, 3, стр. 2»
задаёт СПОСОБ поиска: ссылки нет, карточка находится поиском:

1. `yandex.ru/maps/` → в поле поиска название+город, вводить
   `pressSequentially` + `Enter` (одномоментный `fill` не вызывает подсказки).
2. В результатах брать запись С ТОЧНЫМ АДРЕСОМ из ТЗ — рядом почти всегда
   лежит второй почти одноимённый результат («Организация переехала», другой
   район). Выбор по адресу, а не первая строка по названию: отзыв на второй
   карточке заказчик не примет, а фарм уже потрачен.
3. Клик по строке результата: обычный `locator.click()` по `li` часто упирается
   в таймаут (строка перекрыта панелью) — кликать с `force: true` или
   JS-кликать внутреннюю ссылку.
4. Ключом дальше служит `oid` из УЖЕ открытого URL (`/org/<slug>/<id>/`):
   ему передаются фарм, гейт (`workflow.py`) и публикация.
5. Последний шанс поймать не ту карточку — сверить адрес САМОЙ карточки с ТЗ
   до публикации, а не после сдачи.

## Порядок в пуле аккаунтов

Один аккаунт — одна карточка. Когда заказчик даёт две ссылки, нужны ДВА
разных аккаунта (у нас: herveyrid0ri → Москва, mnommathia → Подольск,
delaneysheke → АКПП), у каждого свой Dolphin-профиль, свой прокси, свой RU-egress.
