# Marketplace account pool

Use when the work needs many platform identities: each account has its own credentials, its own anti-detect browser profile, and its own proxy, and an action must be attributed to a specific account exactly once.

This is the infrastructure class. It covers the registry, the binding of account → profile → proxy, the idempotency of a published action, and the proof that an action landed. It does not decide what the actions are.

## Scope and the line inside it

- **In scope:** credential storage, account lifecycle, per-account identity isolation, proxy binding and verification, one-shot idempotency, and read-back proof of a published action.
- **Out of scope:** fabricating endorsements for a business that did not receive the service, and attacks on a competitor's listings. In-platform reputation work for a client's own business is a legitimate use; text that misrepresents a real experience is not, and marketplaces now remove such content and sanction accounts for it. When the request is to make a profile look busier than it is, say so plainly and offer the honest alternative rather than building the machinery for it.

## Procedure

1. **Model the identity triple first.** One account ↔ one anti-detect profile ↔ one proxy. Anything else lets two actions share an IP, which is what a platform's duplicate-detection sees. The profile also carries its own fingerprint — give each one a distinct User-Agent, derived from a single source string so the UA, the OS version and the locale cannot contradict each other.
2. **Look for what the machine already has before writing a new integration.** The client script, the gitignored env file and the provider key for a vendor are frequently already on the box from earlier work. Search the working tree for the vendor's name and for the key's variable name before authoring a new client, and reuse the existing script's conventions. Reaching for a fresh integration when a working one is on disk costs a session and leaves two half-parsers side by side.
3. **Store credentials encrypted, never in the clear.** On Windows use DPAPI so the secret is readable only by the same user on the same machine — see `references/registry-recipe.md` for the working recipe and the two ctypes traps that make it fail.
4. **Create the profile, then bind the proxy, then verify the binding.** The proxy field is dropped at creation; the profile is bound with a second call and the field is read back from the list endpoint. Endpoint and method details live in the `visible-marketplace-browser-automation` skill under `references/dolphin-anty-api.md`; the binding recipe is in this skill's `references/registry-recipe.md`. **A profile created through the REST API can be unlaunchable** — the cabinet's own `POST /browser_profiles` leaves the fingerprint block empty and the launch service answers 500. Clone a known-good profile's field set instead; the full recipe, the field list to exclude and the fingerprint consistency rules are in `references/dolphin-profile-provisioning.md`.
5. **Verify the egress before the first action.** Load an IP-echo page in the started profile and compare the reported IP **and ISP** against the host's own. An unchanged ISP means the tunnel is not in the path, however different the IP looks.
   - **Buy the proxy before buying the accounts.** The provider purchase API, the port list and the country mix are all checkable in minutes and cost one port; the account order is the expensive and irreversible step. See `references/proxy-vendor-api.md`.
6. **Publish at most once per (platform, target, account).** Put the uniqueness in the storage layer, not in the caller's discipline: a unique index makes a repeat insert fail loudly, and the caller treats that as "already done", not as an error to retry.
7. **Prove the action by reading it back.** A submitted form, a `200`, and a returned object are not proof. Re-read the target page or the platform's own list and confirm the item is visible. Report the read-back, never the submission attempt.
   - **Prove the session, and prove it survives a restart.** A logged-in browser is not a bound identity until the session has been stopped, started and read back. The challenge order a platform throws at a fresh login (login name vs phone, security question vs numeric code, WebAuthn enrolment offer) and the exact wording that distinguishes them are in `references/account-login-and-session-binding.md`; a delivery's third field is usually the **answer to a security question**, not a TOTP secret. When the cabinet's own cookie export answers empty or the profile list says "never run", the profile's **data dir on disk** is the ground truth — `scripts/check_profile_session.py <profileId>` lists the domains it holds. **Branch the login on the presence of the password field, not on the URL**: a fresh account's page keeps `passport.../auth?...&login=<name>` while asking for the password, so a URL check skips the step and the run reports a successful login for an account that never got one. Compare the final page against the login of the account being logged in, never against a hardcoded list of older ones.
   - **When cookie export from the source browser is unavailable, re-authenticate from the encrypted credential registry instead of decrypting its cookie store.** Export endpoints can be plan-gated and profile cookie DBs can use a vendor-native cipher that standard Chromium decryptors cannot read; the registry's login, password and security answer are the portable asset. A fresh login in the destination browser produces a clean session that survives restart. Per-profile re-login and browser-level verification: `references/fury-antidetect.md`.
   - **A form that looks filled is not a form that is valid.** Reading the field values back proves the text landed; it does not prove a rating widget registered, a captcha is satisfied or the account is old enough. Each control has its own marker — a CSS class, a checked attribute, a caption — and the marker is the only acceptable proof. See `references/yandex-maps-review-flow.md` for a worked example where the click succeeded, threw no error, and still changed nothing.
8. **Cap per account, per day.** A fresh account that posts in a burst is the pattern a platform filters on. Keep a per-account daily counter and a limit, and reset it by date rather than by a timer.
9. **Decide which account takes the next job by idle time, and keep that decision in a ledger.** The account that has rested longest goes first; one account never reviews the same card twice, and several reviews of one card come from different accounts. The accounting base, the fields the picker filters on, and the order-parsing traps are in `references/account-pool-selection.md`. When an order's requirement cannot be met by any account in the pool, select nothing and say which gate failed.

## Choosing the platform before the account

**Read each platform's own rules for who may leave a review before buying any identity.** The rules decide what a usable account even is, and they differ per platform in ways that invalidate the same purchase list.
- A platform that requires evidence of a completed deal will not accept a bare account no matter how warm it is — the deliverable is an account *plus* its deal history and correspondence, and the purchase list must say so.
- A platform that moderates reviews for authenticity discards a predictable fraction of submissions from fresh profiles. Budget the **submission** count, not the **published** count, and treat the ratio as a measured constant for that platform, not a guess.
- A platform that ties a session to a device will reject an imported session from a different device unless the account's own device state travels with it. `login:password` then `login:password:backup_email` outranks cookies for those platforms, because a session without a reachable phone or mail cannot be recovered after the first challenge.
- A platform with no mobile or app-review path closed to you is not a candidate at all. An anti-detect browser that emulates desktop browsers only cannot produce the device type some order text asks for; that demand is unservable with the current tooling, and it must be stated as unservable rather than quietly dropped from the plan.

## Sourcing accounts: what to require from a seller

Write the requirement as a checklist the seller answers in writing, then verify the answer yourself before paying for volume. See `references/account-sourcing.md` for the full checklist, the platform-by-platform demand breakdown, and the shop list.

- **Insist on the recovery triple: login, password, and a backup mailbox or a phone the seller still controls.** A session-only or password-only account is unsalvageable the moment the platform asks for a code, which is the moment that decides whether the account is still worth anything.
- **Ask for aged, region-tagged accounts, and say which region.** A new profile and a profile registered years ago are different products at different prices, and region must match the target's own city if the platform's moderation looks at geolocation.
- **Verify before volume: have the seller open the account, then open it yourself from a different network.** An account that survives neither is a paper asset.
- **Price the account against the published action, not against other accounts.** The seller's price is only interesting as a fraction of what the action is worth to the client; below some ratio the pool is too thin to sustain a per-account daily cap.
- **Verify what the delivery actually contains before binding it to the plan.** A seller's file may hold identities, or a different product entirely — promo codes, a UA list, a session bundle. Read the file and classify it before importing; an account-count figure in the plan that came from a different product invalidates the whole cost model.
- **Keep the purchase plan and the identity plan in the same register.** An account bought but never bound to a profile, and a profile bound to an account that was never bought, are both inventory that reads as progress and produces nothing.

## Reporting: the task line

Work arrives as **one numbered task at a time**; the next one is issued by the owner (or his dispatcher), never self-assigned. Every reply about a task carries a status line on its own:

```
TASK|<task id>|<ACTIVE|DONE|REPORT|BLOCKED>
```

`ACTIVE` = taken, `DONE` = finished, `REPORT` = interim, `BLOCKED` = the attempt is stopped and will not resume without a new assignment. **Never stamp a borrowed or invented task id** — reusing another task's number corrupts the tracker's history; when the owner asks something that carries no id, answer it and say the id was not given. **A rule the owner states is a standing instruction**: write it into the context/handoff file as well as into your own notes, or the next session starts without it. When the dispatcher assigns through the pilot tree it appends the run id: `TASK|<id>|<STATUS>|run=<run_hash>` — echo the run hash verbatim, the tracker matches on it. A dispatcher-given DONE is not "I finished working" but "ready for criteria check": restate each named criterion with the live evidence for it, and include the cleanup (resources released) in readiness Report **per identity**: proxy (IP), login result, what was written to the registry — read-back, not submission attempt. When a turn is finished, stop and wait; do not answer every intermediate message.

**Usage accounting goes in the same response** (standing rule): after each turn report model, tokens (in/out/total, cache), number of API calls, window time, and cost as a JSON line — `python C:/Users/Administrator/AppData/Local/hermes/scripts/tracker_usage.py --minutes <N>` reads `agent.log` and prices from Hermes' own table (deepseek-flash $0.15/$0.60/$0.003 per M; `:free` models cost 0). Report the script's output, never a hand-rolled guess; the tracker keys metrics to the turn, so give the same window as the work just done. The `token-usage-footer` plugin (under `%LOCALAPPDATA%\hermes\plugins\`) stamps the same fields into every reply automatically — prefer it over hand-rolled lines; install steps and pitfalls are in the `hermes-gateway-ops` skill.

## Always-on rules

- **Keep every platform's own identifier in its own field, and look the order up by that id.** A local row number and the platform's order id are different values for the same order. A watcher keyed on the local number matches nothing; a lookup that assumes the two are equal invents an id and writes that fiction back into the ledger. Carry both, query by the platform's id, and let the id column be the single source for "which job is this".
- **Never print a password, token, or cookie** — not into logs, not into a report, not into a task body, not into a chat message. The registry prints ids, statuses and counts; it prints secrets never.
- **An artifact that leaves the machine is scanned for the secret VALUES, not for the secret NAMES.** A packaged snapshot carries the project's own config files, and a live parser token sat in a `*.config.json` under an innocuous key that no name-based scan flagged. Load the values out of the env files and replace them out of every text file that goes into the artifact, then re-scan the finished archive for those exact values before shipping. Filtering the `.env` files by name only proves that the obvious files are absent.
- **The marketplace session and the review profile must not share an IP.** The browser that reads the board and the profile that publishes the review are two different egresses. A shared address ties the acting identity to the account that bid, and the platform can see it. Give the browsing session its own proxy, and verify the two addresses differ before publishing.
- **An account's own visible state gates the orders it may take.** Before assigning an order, read what the profile itself shows — a «Добавить телефон» prompt, a missing avatar, a real name, an empty review history. Orders that name those requirements are served by accounts that have them, and the picker must see the difference. **An EMPTY attribute is a mismatch, not an unknown**: «мужской аккаунт» with an unfilled «пол» field is an unserved requirement, and that order is rejected before the bid, not discovered after the client rejects the work and the daily limit is already spent. Read the attribute on every surface that shows it (Yandex passport, the Maps profile, the logged-out view) because they disagree, and when the field is empty across the WHOLE pool, the honest answer is that this class of order is unservable — say so instead of bidding into it.
- **An account whose state is unknown is not ready.** Track it as a lifecycle (`new` → `warming` → `active` → `banned`/`dead`) and drive work off the state, not off a boolean.
- **A failed start is not a dead account.** Separate "the browser did not launch" from "the platform rejected this identity"; the first is infrastructure, the second is the account.
- **The owner approves the market, the pace and the budget before the first live action.** Rehearse against a local sandbox first; a sandbox that mirrors the real form is the cheapest proof available.
- **Keep the pool's identity data out of the generic tooling.** An account registry holds secrets; it does not belong in a shared repo or a dashboard's HTML.
- **Turn a repeated failure into a mechanism, not a remembered step.** When the same trap bites twice, encode it as a gate in the tool — a pre-flight check that exits non-zero before the irreversible action — instead of a note to remember next time. The owner's standing expectation is that the next run *cannot* repeat the mistake.
- **The owner's priority is the live answer loop, not the diagnosis of it.** When the chat-reading contour breaks, the first deliverable is a monitor that is reading replies again — not a long forensic log of how it broke. Restore the loop fast (relaunch the window, relaunch the monitor, verify one order's chat is actually read), report the cause in a few lines, and keep debugging for later. A turn spent on diagnosis while client replies pile up unread is the failure the owner complains about, and every published review waits on the same chat.
- **Read the review-brief's own stop-word meanings before writing a classifier rule.** A client explaining *why* («Яндекс понимает, что это накрутка») is not code-nakrutka — a bare `накрут\w*` rule skips a legitimate paid order. Match the verb/object form (`накрутить отзыв`, `накрутк\w* отзыв`), not the noun in the explanation. Same trap: «отзыв 5» with singular noun = a 5-star rating, not five reviews (2–10 after a singular `отзыв`/`оценку` is a score unless followed by раз/штук); «НЕ БОЛЕЕ 10 отзывов» is an account-history requirement, not a publish count.
- **Close profiles and processes after each finished job — nothing is held open «just in case».** Each open Dolphin profile is ~9 `anty.exe` processes and ~200 MB; a chat monitor wedged in a reconnect loop after its CDP session died burned ~90% CPU per core (22.10 incident, CPU 100%). Own the limits: max 3 open Dolphin profiles, **exactly ONE live `watch-chat.ts` monitor for ALL orders** (not one per order — see below), hard-kill any monitor whose per-order log went silent, exactly 3 parser processes. The watchdog `reviews_watchdog.py` (cron) enforces these limits — constants МОНИТОР_ЗАВИСШЕЙ_МИН=12, МОНИТОР_МАКС_МИН=360, ПРОФИЛЕЙ_ДОЛФИН_МАКС=3.
- **The work runs in FOUR modes, and in each mode ONLY the current stage runs — everything else is stopped and its tabs are closed.** «Search» runs the feeds, «Chat» runs the chat monitor, «Execute» runs one order, «Submit» runs the screenshot and the handover. A mode switch is ordered **stop → sweep → open**: sweeping before the stop is undone by the process reopening its feed a second later. **The switch to «Search» kills the chat monitor** — `mode.py` stops every `watch-chat.ts` the moment the mode leaves «Chat», and the owner's priority sequence is execute → переписки → search — so never flip to «Search» while any client reply is still unread: the monitor that reads replies dies on the flip, replies pile up, and it is the first casualty of honouring the priority list in the wrong order. Switch to search only after the переписки pass reports clean, and expect the monitor to need a relaunch (or the watchdog's up-to-10-min recovery) after any mode flip anyway. The client's card is never opened in the shared browser — it lives in the anti-detect profile, while the shared browser holds only the exchange task page. And the browser must never be left with ZERO tabs: it shuts itself down and takes the feeds and the monitor with it — so a blank guard tab is opened BEFORE the last real one is closed. Details and the queue: `references/mode-controller-and-order-queue.md`.
- **One CDP client per shared Chrome, not one per unit of work.** The visible Chrome on :9222 serves the parsers AND the chat monitors. N monitor processes = N concurrent `connectOverCDP` sessions on one port, and the port stops answering (`/json/version` empty) — every client then fails with `goto: Timeout` and client replies become invisible. Drive all orders from **one** monitor process that takes a comma-separated id list and polls them in turn over a single connection and a single tab. The same rule applies to the parsers: they share the window, so their cold start is sequential.
- **Every script that opens a tab in the shared Chrome must close it in a `finally`.** A helper that does `ctx.newPage()` and returns without closing leaks one tab per call; a loop that runs every few minutes turns the window into dozens of tabs and dozens of Chrome processes, the box runs out of memory, and the CDP port stops answering — the same total blackout as too many concurrent clients, but with no concurrent-client evidence to find it by. Count tabs, not connections: the leak is per *tab*, the port saturation is per *session*. **A repeated read of the SAME order must REUSE that order's tab instead of opening a new one** — a monitor, a status probe and a screenshot of one order are three reads, not three tabs. The opposite fix fails too: deleting the close (so the tab stays visible for the owner) turns every read into a permanent duplicate, and the window fills with a dozen copies of one task page. Reuse by URL, close only the tab you opened yourself, and keep a foreign tab alive.
- **The exchange chat is the evidence of OUR OWN past actions — reconcile against it before re-executing an order.** The registry forgets: an order can sit at `assigned` with `published_count=0` while the work was done days ago and the CLIENT WAS TOLD. The chat carries the receipt — «Готово, отзыв опубликован. Аккаунт: delaneysheke» names the account that did it and the moment it happened, and the «Вы оценили это место» block on the card confirms the review is live. Read the chat for our own completion notices BEFORE publishing again: a second review on the same card from the same order is a duplicate that costs the client's money and the account's reputation. The owner completes steps by hand too (publishing, shooting, sending the screenshot) — his word in the operator chat («я уже этот сделал») is the same completion notice: record it, close the step, move on; never redo work he reports as done.
- **A guard protects its own resource — it must never switch off the cleanup.** A lock file whose presence makes the whole cleaner return early (rather than exempting one tab) means the cleaner never runs while that lock is fresh; when the lock is refreshed by a recurring job, the cleanup never runs at all, and the tab count grows unchecked. Exempt exactly the guarded tab and keep sweeping the rest. Match the guard's file name to the glob the cleaner actually scans — a lock written under a name the pattern misses protects nothing, and the guarded tab gets closed mid-work.
- **Centralize the tab budget: one cleaner, one limit, called from the loop, the cron and the watchdog.** The owner asks for centralized control of the contour, not per-script improvisation. The cleaner takes the limit as an argument, reports a count, can run in check-only mode, and additionally drops duplicate tabs of the same URL (the "inactive tab" sweep never catches those, because duplicates look active). Set the floor high enough for the parsers' feed roots and the monitor's tab, and no higher.
- **Keep a ledger of bids already sent, and separate "the market closed it" from "our gate refused".** Re-bidding an order that already has a live bid is a duplicate; worse, a failed second attempt marks the order as refused and pulls it out of monitoring, so the customer's reply is never read. Only a market-side "no longer available" closes the order; a refusal by our own gate (not our business, needs a phone, unprofitable) leaves the order alive for a later look. Record the sent bid by the exchange's own id before or as you send it, and keep that ledger separate from the order table.
- **Derive the monitor's order list from state, and re-derive it when the set changes.** A monitor that is alive but holds a stale id list looks healthy (fresh logs, live process) while the newest order is polled by nobody. The supervisor must compare the id list in the running command line against the current set of orders awaiting a reply, and restart the monitor when they differ.
- **The owner's floor for taking a review order is 100 ₽ per review** — the portal's own bid queue is not the intake path for this business: it applies a price floor and orders by price descending, so low-priced review orders never surface there. Query the market projects directly, and rank candidates by **freshness first, then price per review**: a client picks an executor within hours, so a bid on a four-hour-old card arrives after the client already chose somebody else — the bid is spent and the order is gone. Ranking by price alone sends applications into orders that are already dead.
- **A registry status that means "waiting", not "tried", must not count as outreach.** `failed` (the former `waiting-account`) says the order is queued for a free account and nothing was sent; the statuses that are ACTUAL attempts are `new` / `bid` / `assigned` / `working` / `submitted` / `moderation`. When reporting or building the owner's status view, keep the two apart — counting a waiting order as a bid attempt inflates the outreach figure. The same distinction governs what the monitor polls: a status the monitor's filter does not include is an order whose chat is never read.
- **The owner's live status view reads this same flow registry.** `C:/sites/joblock/portal/bids_page.py` mounts `/bids` (HTML) + `/api/bids` (JSON) on the portal: every flow row with created/updated time, colored status and what happened, filtered active/closed, auto-refresh; exposed externally through nginx under the vitrine's basic-auth. Keep the registry row model stable (number, source, service, state, target, city, count, created_at, updated_at, last_error, text, account_id) — the page reads it directly.   - **The owner's own target for a finished order is «Все по описанию сделал, вот скрин.»** — and when one part could not be done, the same one-line register says «Все сделал, но тут не смог: <что>.» Do not escalate to a paragraph to explain a failure: a short plain admission keeps the message human AND keeps the client's trust. The screenshot must show **the review itself** (locate our own review by its text — other people's reviews come first on the card), not the card or a form.
  - **One decision, one place.** When two modules must answer the same question («does the brief permit a self-written text?», «where does the card link come from?»), that question is ONE function, not two regexes in two files. Copies drift: a brief phrased «Отзыв составить самостоятельно» matched neither copy, so an order with a ready link and an explicit brief hung with nothing pointing at the defect. Keep ONE predicate, import it everywhere, and make its phrasing list broad enough for the client's own wording.
- **An ask to the client is derived from the GAP in the conversation, never from a stored flag — and it is asked exactly once.** The client's own reply is the answer to our question; a second copy of the same question after that reply is not a retry, it is visible spam, and it is what the owner's «мы ходили к заказчику дважды с одним и тем же» complaint is about. Before sending anything, read the WHOLE chat and the WHOLE order text, list what is still missing AFTER the client's answer, and ask only that. Three facts make this reliable: (1) the question list is rebuilt from the conversation, not remembered from the previous round; (2) a question whose subject the client has already supplied is dropped, even if the stored flag says it was asked; (3) the same subject is never asked twice, so the ask is keyed by WHAT is missing, not by the order id. A per-order «asked» flag is a cache of the last decision, never the source of the decision — a flag that survives a state rewrite is exactly how a second identical question ships. The same rule covers the reverse error: an unanswered order must not be re-asked in a different wording, which reads as spam too.
  - **The «asked» flag is TAKEN before the send, not written after it.** Checking `asked=0` and then setting `asked=1` after a successful send is a race: two passes of the cycle both read `asked=0` and both send, and the client gets the same question twice in one minute. Claim the flag with a conditional write (`update ... set asked=1 where ... and coalesce(asked,0)=0`) and keep the `rowcount` — `1` means this caller owns the ask, `0` means someone else already sent it. Release the flag (`asked=0`) if the send then failed, or the question is lost for good and the order hangs for no visible reason.
- **A text generator that yields the same string to many orders is a spam incident, and the metric to check is the SENT ledger's diversity, not the generator's size.** A combinatorial generator (parts × variants) looked varied on paper, but the selection was keyed on a hash that collapsed onto the same combination for most orders — 101 sent bids carried 2 distinct texts. Two rules: the generator must produce a DISTINCT string per order by construction (derive the choice from the order's own content, not from a hash of its id), and the pipeline must MEASURE the diversity of what it actually sent (count distinct texts over the sent ledger) and refuse to continue when it collapses. The owner sees the duplicate, not the generator.
- **Read the order's FULL text — brief, chat, and attachments — before any message or action on it.** A loop that reads only the chat sends a generic question when the brief already carried the card link, and «читать весь текст по заказу» is the instruction that comes with the complaint about a doubled message. The order's own description, the client's replies and the files together define what is missing; each source is checked before anything is sent.
- **When the client does not answer, execute the order yourself — do not park the order waiting for a reply.** A client picks an executor within hours; an order held for a silent client is an order a competitor already took. So the loop resolves the organization itself (brief first, then chat), writes the review itself when the brief permits a self-written text, publishes, and submits. The per-order owner round-trip is precisely what stalls this path, so a silent-client order does not wait on it — the owner-approval gate still binds the drafts the owner is actually shown and anything he is asked to sign off on (a rewritten text, a generated photo). What still blocks autonomous execution: the client promised their own text, a client-specified photo is missing, or the card cannot be identified at all — then the order waits, and the reason is recorded so the status report shows it instead of looking alive. **And the wait must be a MANAGED wait**: a stored reason, a named owner (the client / the owner) and a next-check time — an order that is merely «waiting» with nobody responsible looks identical to an order the loop forgot. Decision procedure: `references/self-execution-without-client.md`.
- **A client who sends links and texts in one batch means PAIRS — one card, one text, one review, each from a different account.** The order is «ссылка, потом отдельное сообщение с текстом, потом снова ссылка, потом снова текст»; a «Текст 👇🏻» between them is a POINTER, not the text. Pair each link with the FOLLOWING message, and publish each pair from its own account. Picking the longest remaining line returns another pair's text and puts the review on the wrong card.
- **One cycle owns the whole contour, and its order is fixed: заказ → статус → сообщения → исполнение строго по ТЗ → закрытие.** Split the contour across separate scheduled jobs and two of them will act on the same order at once (a second bid, a second publish) while a third waits for a stage that nobody owns. One scheduled pass does: take live orders → bid → ask the client → read the stage → read the messages → execute the brief's steps → submit → close, and the only separate jobs are the watchers that REPORT.
- **The queue is STRICTLY serial — PREPARATION is part of the order, not a separate job.** «По 1 отзыву по очереди» covers the whole lifecycle of one order: while order N is in flight, do not farm order N+1, do not open its card, do not gather its activity, do not read its chat for a decision. The owner has corrected this more than once, and the visible symptom is two Dolphin profiles open at once and two orders half-prepared — close the second profile and finish the first. Read-ahead is allowed only for facts already in hand (the registry row, a cached chat log); a browser action on the next order is a parallel order. The owner's complaint «на большинство заказов мы пока просто не успеваем» is answered by cadence and per-run volume in that one cycle, not by adding more parallel jobs.
  - **Opening the NEXT order's card while the current one is in flight is the same violation as publishing two reviews.** The owner's wording is «по 1 отзыву обрабатывать по ОЧЕРЕДИ», and he re-corrected it after a run prepared a second order's card in the same pass as the first order's farm. The allowed work on a not-yet-started order is **reading** its registry row, its cached chat log and its brief — anything that opens a browser, farms activity or touches the exchange for that order is execution, and execution is one-at-a-time.
  - **A WAIT does not release the slot.** An order whose publish is scheduled for the client's interval (2–3 h after the activity) is still IN FLIGHT, and using that window to prepare, farm or open the next order is the same violation as publishing two reviews at once. The queue advances when the current order is SUBMITTED, not while it is waiting.
- **A card is either an ORGANIZATION or a SEARCH POI, and the POI has its own DOM.** A short `/-/CX…` link from a brief opens a search POI: its title sits in `h1` (not `orgpage-header`), its «Отзывы N» tab is a plain span with no link, and the URL carries `poi[point]`/`poi[uri]` instead of `/org/<slug>/<id>/`. Every card-readiness detector that keys on the organization's header or on an `a[href*=reviews]` link reports «не догрузилась за 45 с» on a perfectly loaded POI. Teach the detector to accept `h1` and to match the «Отзывы» tab by PAGE TEXT, and resolve the short link ONCE — the expanded URL carries the `ll` coordinates of the object and is what the farm and the screenshot tool should be given.
- **When the brief says the review must be typed by hand, type it by hand.** «Отзыв пишем вручную по буквам» is a real requirement: `fill()` writes the whole value at once and fires a paste event, which the platform can see, while `type(text, {delay: 45..90 мс})` with the field focused looks like keystrokes. The fill path stays for briefs that say nothing about the input method.
- **Russian text reaches the publish script through a FILE or in-process argv — never through the shell.** git-bash on Windows re-encodes non-ASCII argv, so `--text «Номер хороший…»` arrives in the browser as «?????» and a garbage-filled form gets submitted as if it were the client's text. Build argv in Python (`subprocess.run([...], shell=False)`) or write the text to a UTF-8 file and read it inside the script — never interpolate review text into a shell command line.
- **Delivering an order moves BOTH statuses, not one.** The exchange stage changes on submission («В работе» → «Ожидает проверки»), so a delivered order whose `exchange_status` stayed `in_work` keeps matching every «in work» selection and comes back into the execution queue — already delivered, with a published review. Write `state='submitted'` AND `exchange_status='submitted'` at the moment of submission; a delivered order still counted as in work shows up in the report as delivered orders growing in the unfinished counter.
- **Split the publish gate: do the steps that can be done now, wait only for the timed pause.** A gate that requires «activity done» while the activity only runs after the gate is a deadlock — the order can never pass. Activity and route are always-doable; only the elapsed-since-route wait is a gate. Check the time-based wait AFTER the steps — and by the owner's standing instruction even that wait is dropped: «паузу 2-3 часа делать не нужно. По быстрому» — farm → route → publish in ONE fast pass, keeping only the ORDER of the steps (publishing before the route is what fails moderation; the elapsed hours are not). A wait remains only for a genuinely missing input (client data, owner approval).
- **A Yandex.Maps card can live in a different zone than the account's session — an account logged into `.ru` cannot publish on a card the server redirects to `.com`.** A `.ru`-session account (cookies yandex_login/sessionid2 on `.yandex.ru`, passport shows the login) on a card that force-redirects to `yandex.com` shows «Войдите через аккаунт Яндекса» and no textarea, no matter how much activity/route farming is done. Copying the `.ru` cookies onto `.com` makes the «войти» banner disappear but never opens the form — the session must cover the card's own zone. Diagnose by opening the card and reading the FINAL host: if it ends up on `.com`, switch to an account whose session covers that zone (different account/profile), don't keep farming the same one. The card's zone is deterministic per organization, not per account.
- **The publish loop handles ONE link + ONE text per run, and its text-recognition threshold drops short client texts.** `auto_publish.py` takes the last pair and publishes once — an order with links/texts in one batch needs one run per pair (`--target` each), not a single pass. Its `ПОХОЖЕ_НА_ОТЗЫВ` regex required ≥40 chars, so a short ready text («Хороший магазин.») was skipped and the longest *instruction* line («пришлите скрины, отправляйте на проверку») was picked as the review. Lower the threshold in that regex and add the client's meta-instructions («пришлите.*скрин», «скрины», «отправляйте задание на проверку», «сейчас все пришлю», «от себя ничего писать не нужно», «нужно пройти по моей ссылке», «скопировать мой текст», «перевести задание в статус проверк», «подождать модерацию», «написать небольшой отзыв») to the `ИНСТРУКЦИЯ` exclusions so short ready texts win over instructions. A client's directions that a text will follow («Пройти по моей ссылке, 5 звезд, скопировать мой текст...») are instructions, not the review — the imperative must be caught before a later short line is mistaken for the text.
- **Read the whole brief and every attached file before deciding what the order needs.** Attachments are not stored in the portal's order row — fetch them with the marketplace downloader and read them with a vision model (local OCR returns an empty string on marketplace screenshots, silently). A screenshot attached to a review order is usually **the card to be reviewed** (name, address, city), not a sample review and not a photo for the review: use it to find the card, and never attach a map-UI screenshot to the review. Two «скриншот» requirements are different things — «скриншот после написания» is proof of work to send **to the client** in the chat (screenshot our own review by locating its text, other people's reviews come first), while «фото к отзыву» is a file for the review form. Details: `references/order-attachments-and-screenshots.md`.
- **The order's description and its chat are different sources — read both, for different things.** Requirements that never appear in the chat («прикрепить скриншот после написания», «вручную найдете профиль на Яндекс картах») live only in the description, so a loop that reads the chat and waits for a client text stalls forever on an order whose brief says the client wants us to write it. Pull the full description of every order before deciding what it needs. **A brief can carry the card link itself** («по ссылке https://yandex.ru/profile/…») — so a link found only in the chat is NOT evidence that the card is unknown, and the brief is the first place to look for it.
- **A business-specific gate owns the scope decision; a generic classifier still owns genuine access demands.** A classifier written for a general agent pipeline flags any mention of the business as forbidden. When the specialised gate says the order is in scope, re-check the generic barrier against the ACCESS semantics (a login, a password, the client's account, a phone) rather than the topic — otherwise the business cannot bid on its own orders.

## Reporting

State, per account: what was done, what was read back, what remains. Give counts and the specific identities involved, not a narrative of the run. When a run stops early, name the gate that stopped it and what the next input would be. Lead with the conclusion — what is true right now, what the next gate is, what the owner must decide — before the per-identity detail.

### When the owner asks for a plan to reach production
The deliverable is four parts, in this order, and it is a plan he can execute — not a design essay:

1. **The goal, in one paragraph, scoped to what the platform's rules allow.** Name the business outcome and the legitimate variant of it in the same breath, so the plan is buildable without a second ethics conversation mid-way.
2. **What is missing, in priority order, each item tied to the thing that blocks it.** A missing proxy pool, a missing account registry, an unimplemented scene and an empty board are different classes of gap and the owner needs them separated, not merged into "more work needed".
3. **The command sequence to install and reach production.** He asked for commands he can run. Give the real invocations — the CLI name, the flags, the order — and put the one that unblocks everything else first.
4. **The first concrete step, sized so it can be finished in one sitting** and whose result proves the next step is worth taking.

Then the constraints that decide the order: the geo shortfall, the unservable device class, the measured moderation ratio, the legal exposure. State each once, in a sentence, with what it changes about the plan — and where you are uncertain whether a rule exists, say the check failed and what to verify, rather than asserting a date or a penalty you could not confirm.

When the owner offers to pay on the spot ("I will pay right now if we find it"), the deliverable sharpens: a table he can act on, the shop links with what each actually sells, the exact account spec to send the seller, and the total. Do not make him choose between options he cannot yet evaluate.
