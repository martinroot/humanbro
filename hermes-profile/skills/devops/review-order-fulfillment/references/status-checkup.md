# Статус-чекап конвейера (запрос «Статус. Контроль проверки... Чекап памяти. Парсера. Переписки...»)

Разовый полный срез заказов/памяти/парсеров/переписок/порядка за один проход — владелец просит его регулярно пачкой. Отчёт: структурированный, «только факты» (пути, цифры, время логов), каждый пункт с вердиктом ✅/⚠; узкое место и действие владельца называть явно (что от него требуется).

## Порядок сбора (всё параллельно, без ожидания между)
1. **Время + память + процессы**: `date "+%H:%M %d.%m"`; RAM свободно, chrome/anty/bun counts через powershell (см. питфолл про `$_`). Живой bun-список: filter на `parser.ts` (3), `watch-chat.ts` (мониторы чатов), `--minutes 300` (крон-монитор).
2. **Свежесть логов**: `stat -c %y feed-log.jsonl parser-wz.log parser-kw.log parser-is.log` — всё живее ~5 мин = контур работает. **Сначала прочитать `reviews/data/mode.json`**: вне `search` ленты молчат НАМЕРЕННО (4-режимное правило владельца) — старые логи парсеров это НЕ авария, а режим.
3. **Статусы**: `flow` по state (sqlite registry.db) + портал `orders` по status (MariaDB joblock). Ключевые: submitted/on-review/moderation = деньги в работе на проверке; bid/assigned/executing = в очереди исполнения; failed/blocked = сбои. Числа new на портале растут = лента доходит.
4. **Переписки**: regex по `logs-watch-chat-<id>-live.txt` — маркеры «ОТВЕТ ЗАКАЗЧИКА (id)» + счётчики «наших:N». Первое vs последнее N: изменилось = реакция была ✅; то же = ждём. Свежие ответы (<30 мин) пропускать осознанно — монитор ещё отрабатывает.
5. **Согласования**: `python reviews/approve.py` — черновики PENDING = ждут «ОК» владельца (его действие, не наш баг); OK/REJECT история.
6. **Порядок**: мусор `_*.*` в browser-automation — удалять (`find . -maxdepth 1 -name "_*.*" -delete`); профили Dolphin ≤3 (anty count); RAM низкая при живых профилях = рабочая нагрузка, не гасить без причины.

## Питфоллы
- **git-bash съедает `$_` в inline powershell** — команда с `$_`/`$os` внутри кавычек ломается «not recognized». Писать .ps1 файлом (write_file) и выполнять `powershell -ExecutionPolicy Bypass -File`, затем удалить.
- **Молчащая лента ≠ сбой парсера** — сначала mode.json (см. выше); watchdog сам поднимает парсеры в режиме search, руками не перезапускать в chat/execute.
- **Низкая RAM при 3 профилях Dolphin + парсерах + Chrome = норма** — повторно «чинить» память убийством рабочих профилей срывает исполнение; чинить только явные лишние (профили без заказов, старые мониторы >6 ч).
- **Числа растут между чекапами = контур жив** (bid/closed/new растут, портал принимает); застывшие числа при свежих логах = пауза выдачи биржи, не сбой.

## Постоянный статус в ЛИЧКЕ владельца (cron, каждые 10 мин)
Разовый чекап выше — по запросу; постоянно владелец видит короткий статус в ЛИЧНЫХ сообщениях бота: cron `status_sys.py` (hermes scripts/, no_agent, `deliver=telegram:353169388`), ШЕСТЬ рубрик его формулировки: ЗАКАЗЫ · ПЕРЕПИСКА · ВЫПОЛНЕНИЕ · ПОИСК · ЛОГ/ОШИБКИ · АВТОНОМНОСТЬ.
- **Источник «ПЕРЕПИСКИ» — выводы рабочего конвейера** (последние ходы cron «Контур заказов», события в них), НЕ `mtime` старых `logs-watch-chat-*`: мониторы прошлой схемы лежат сутками, и читать их как «переписка молчит 20 часов» — смотреть не туда (владелец: «Ты куда смотришь, у нас был рабочий конвейер»).
- ЛОГ/ОШИБКИ: прогоны cron за час со счётчиком `script failed`, открытые карточки `[EX:]` в `/api/tasks`, heartbeat и incidents maintenance.
- АВТОНОМНОСТЬ: число cron-задач, отработавших за сутки (папки вывода), порты 8701/9222/3001, текущий режим.
- Пустой stdout cron-скрипта ничего не шлёт — статус печатает всегда: это лог процесса, а не алерт.

## Один заказ по запросу («проверь статус <id>»)
1. Параллельно два источника: `bun task_status.ts <id>` (статус, этапы, кнопки, ТЗ на бирже) и `bun chat-read.ts <id>` (хвост чата) + `GET /api/orders` портала для расхождений.
2. **Статус биржи не описывает переписку.** «Ожидает проверки» при днях неотвеченных реплик заказчика (вплоть до «через арбитраж решать?») — обычный вид страницы и провал отношений одновременно. Первым действием закрыть самую свежую неотвеченную реплику — по существу, фактами вместо обещаний, спор/арбитраж не поднимать раньше установления факта; и только потом отчёт владельцу.
3. В отчёте — оба источника и расхождения: этап/даты/деньги биржи, хвост чата с последними репликами (свои — со счётчиком «было N → стало M» как подтверждением доставки), чего ждём от заказчика; отсутствие заказа в `/api/orders` при наличии на бирже — отдельным пунктом (счётчики портала врут).
