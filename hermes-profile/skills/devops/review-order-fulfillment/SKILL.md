# Review order fulfillment (Workzilla → Yandex Maps)
One marketplace review order, end to end. Chrome CDP/tab mechanics: `joblock-chrome-cdp-ops`. Portal status board: `joblock-agent-portal`. Owner status-checkup requests («Статус...чекап памяти...переписок») — `references/status-checkup.md`. Conveyor picking/queue stalls («очередь пуста», «не доделан — остаёмся») — `references/conveyor-queue.md`.

## Always-on gates
- **One order at a time.** Mode sequence: `execute` (exactly ONE order) → `chat` (clear every order in work) → `search` (only after everything is handled). Two orders in execute, or a focus differing from the order being acted on, is a defect. `mode.json` has exactly ONE writer: `python reviews/mode.py переключить <режим> [фокус]` (it also retabs the window for the mode); never write the file directly — a second writer is the desync the owner sees as a mode/order mismatch in the board header.
- **Approve before it leaves.** The owner chat gets the review text (when generated) and the evidence screenshot BEFORE anything reaches the customer; send only after an explicit ok.
- **One attachment, once.** The submission form already attaches the result, so there is no separate pre-submission chat message. `reviews/file_log.py` guards ANY attach — one file, one attachment, ever.
- **Evidence is the organization's review page**, never the author's cabinet — the cabinet puts our reviews for other customers on one screen.
- **Fewest-reviews profile, one per order**, stopped as soon as the order is delivered (execute off ⇒ every Dolphin profile closed).
- **A waiting order never parks the run.** An order whose customer still owes input (promised text/link) is законное ожидание: the conveyor yields to the next queue head within the SAME run and re-checks it next run — it returns on its own the moment the input lands. Only an order we can advance keeps the run on it; one head-of-line waiting order starves every other order for hours (queue mechanics and diagnosis: `references/conveyor-queue.md`).
- **Fast pace** — customer wait windows («через 2-3 часа», «паузу сделать») are waived unless the owner reinstates them. A spec-imposed delay («отзыв не раньше 12 часов после активности») yields the moment the owner says proceed: he overrides his own spec timing, and sitting on that clock after his go-ahead spends delivery time he has already paid for. **A spec delay that has already ELAPSED is not a wait state at all** — message time + delay < now means the order is overdue, not pending: execute immediately, no HOLD, no clock check; treating the spent clock as «законное ожидание» parks an order that everything (input, assignment, deadline) already says to run.
- **Timebox account polish.** Name/avatar/photo setup for a profile is auxiliary to the order; if it does not resolve within a couple of attempts, drop it and execute the order — order execution outranks account polish (an hour lost to an avatar upload is an hour not earning).

## Procedure
1. **Read the spec** — `bun chat-read.ts <id>`. Customer-supplied review text is used VERBATIM (assert byte equality before publish). A spec naming an organization + address means SEARCH for it, not open a link. Turn every explicit constraint of the spec into a checklist before acting (account, geo, entry route, activity items, route distance cap, contact mimics, timing, screenshot deliverables): a deliverable the spec names («скрин маршрута — ПРИСЛАТЬ») is owed to the customer even when the owner only remembers it later, and a missed item surfaces only at review time.
1a. **Account-identity gate** — many customers open with «Пришлите имя аккаунта» / «скриншот аккаунта с ником и уровнем знатока города» BEFORE sending the link/text; treat it as a pre-work gate, not a review-text request. Reply with the working account's name + city, and when a screenshot is asked: open `https://yandex.ru/maps/profile` on the assignment's CDP port, wait ~9 s, screenshot to `reviews/data/shots/account-<id>.png`, send via `wz-msg.ts <id> <файл-текста> <png> --attach`. If wz-msg.ts answers «поля ввода на странице нет» OR the chat never renders («ЧАТ НЕ НАЙДЕН»), the task is closed/unavailable on the exchange side (or not assigned to us) — don't retry forever: log the honest status (`клиент ждёт …; чат не открывается`), keep the screenshot ready, and ask the owner close-vs-wait. A fresh Chrome restart sometimes unblocks the field — one retry after `/json/version` is up is enough.
2. **Account + proxy** — fewest-reviews profile; probe its proxy first: `curl -s -o /dev/null -w '%{http_code}' --max-time 20 -x http://login:pass@host:port https://yandex.ru/`; `000`/timeout ⇒ dead ⇒ heal via the proxy's `changeIpUrl` refresh and re-probe to 2xx/302, never by editing host/port (account geometry is untouched). Start `GET http://127.0.0.1:3001/v1.0/browser_profiles/<id>/start?automation=1`; CDP port from `browser_profiles/<id>/data_dir/DevToolsActivePort`. Local `/v1.0/*` needs login-with-token, cloud `/browser_profiles` only the JWT.
3. **Locate the organization** — search, click the result whose ADDRESS matches the spec exactly, discard moved/duplicate branches; keep oid + URL with `ll=`/`z=`.
4. **Farm** — `bun yandex-farm.ts <cdpPort> <orgUrl> <city> [pause]` (tabs, photos, reading + liking foreign reviews, phone, routes; geo overridden from the card's `ll=`). Visit the company site through the card's own link — it opens a NEW tab, wait for it instead of scrolling the card. Then `python reviews/workflow.py mark <id> activity|route`, gate with `python reviews/workflow.py due <id>`.
5. **Text** — no customer text ⇒ parse ≥10 foreign reviews, write an original borrowing their techniques and vocabulary: no foreign names, no clichés («незабываемо», «рекомендую компанию»), account's gender, concrete details. Owner approves it.
6. **Publish** — FIRST re-probe the account's CDP port (`Invoke-WebRequest http://127.0.0.1:<port>/json/version`): the farm session's teardown can quit the profile browser, and publish then dies at open with `Target page, context or browser has been closed` on a port that answered a minute ago. Dead ⇒ `registry.py stop --account N` then `start` (start may also hit the locked-`History` 500 — same stop→start cure) and publish on the NEW port from the start output. Then build argv in Python `subprocess` (list form, no shell): `bun yandex-maps-review.ts <port> <url> --text <text> --fill --submit --target <id> --вручную`. The gate blocks without activity+route; `--вручную` types letter by letter because `fill()` is an instant paste. Log must show 5 stars (`_selected`), text length, «НА ПРОВЕРКЕ».
7. **Evidence** — open `/reviews/`, WAIT 5–10 s for reviews to load, `scrollIntoView({block:'center'})` on our review, prove the frame: rect `height>60 && top>=0 && bottom<=innerHeight`. DOM presence is NOT proof — a hidden duplicate gives `rect 0×0` and a frame with no review in it; filter by rendered size.
8. **Owner approval** — screenshot + customer message go to the owner chat; wait for ok.
9. **Deliver** — straight to submission: `bun wz-check.ts <id> "<text>" <file>` (the form attaches the result); a separate chat message only if the owner asks. Before attaching, `python reviews/file_log.py was <id> <file>` must say not yet attached.
10. **Status lands instantly** — `wz-check` calls `refresh_status.py` itself; confirm the board shows `submitted`/«Ожидает проверки» within seconds, not after the background poller.
11. **Read back** — in the order page DOM: our text exactly once, exactly one `storage/.../<file>` URL (widget counters count slider elements — «11 из 1» is one file). Then fix `steps`/`file_log` in `registry.db`.

## Pitfalls
- **Attachment file paths must be ASCII** — a non-ASCII filename (`04-маршрут-1.png`) sends the message WITHOUT the file and still reports success. Copy the file to an ASCII name (`route-<id>.png`) and re-attach at once: the retry takes seconds, while a diagnostic round (chat re-read, journal checks) burns many minutes on a delivery the owner rates in seconds. Verify the attach by counting unique `storage/…` addresses in the chat DOM, never by the sender's `вложений: N` line.
- **The review form is not reachable from the short POI link** — `/-/CX…/reviews/` serves only the search box, or a full 404 page (title `404`, «Нет такой страницы»), and a candidate scan there finds no write control, so the publish script exits having done nothing («рейтинг НЕ выбран / поле для текста не найдено» — the script reported exit 0 on the 404). Resolve to the org URL first (`/maps/org/<slug>/<oid>/reviews/?ll=…&z=…` — oid from the card), then open the form by CLICKING the «Отзывы» tab and hitting the «Оцените это место» trigger inside it — the trigger lives in the tab panel, so a scan that only navigates to `/reviews/` never sees it. Diagnose by listing what the scan actually matched (buttons/texts on the loaded page) before blaming the publisher. The publisher now defends itself: a 404 page (title `404`, «Нет такой страницы») exits 1 with a named «ОТКАЗ: страница 404» instead of the vague «звёзд в виджете=0»; form open is retried up to 3 times, each attempt ending with an event wait `waitForSelector("textarea, [aria-label='5 звезд']", 12s)` — never a fixed sleep, since the sticky trigger renders late after a navigation hiccup; and with `--submit` a rating that stays unselected or a missing text field exits 1 rather than publishing a review with no stars (previously it logged «ВНИМАНИЕ» and published anyway). Verify any edit to this script by RUNNING it against a dead port (`<port> 1`): the module must load and fail only at connect — that is the syntax check; `bun build` is useless here (it dies resolving playwright's `chromium-bidi`, unrelated to your file).
- **Evidence that ignores the spec's numeric limits is a rejected deliverable** — a route shot from the city center reads 17+ km while the spec caps it at 15. Read the distance in the DOM after building the route; if it exceeds the cap, rebuild from a point a few kilometers from the card (route URL `rtext=<near coords>~<card coords>`) and re-shoot, so the frame itself shows a compliant number.
- **git-bash mangles Cyrillic in argv** — the customer receives `?????`. Pass text via Python `subprocess.run([...])` (list argv, no shell), never a shell-quoted terminal line.
- **`with sqlite3.connect(...)` does not close the file on Windows** (commit only) — migrations/temp cleanup die with WinError 32. Wrap in `contextlib.closing(...)`.
- **A DOM grep is not a screenshot check** — the customer sees pixels; validate geometry, not text presence.
- **Author-cabinet screenshots leak other clients' reviews** — shoot the organization's page.
- **Widget counters ≠ attachments** — count unique storage URLs in the order page DOM.
- **A mode switch can kill the shared Chrome** — `mode.py переключить` retabs the window, closing the last tab exits the browser and takes 9222 with it; every later attach then fails with «port silent» while nothing points back at the switch. Probe `/json/version` after each switch and relaunch the dedicated profile if it is down (mechanics in `visible-marketplace-browser-automation`).
- **The attach guard in `wz-check.ts` uses `ID`, not `id`** — a mismatch throws `ReferenceError` mid-submission, leaving the modal open and the order unsubmitted.
- **Delivery status mapping** — stage «Ожидает проверки»/«Завершено»/«Принято» ⇒ `exchange_status=submitted` (last two also `state=closed`); an unknown stage falls through to `in_work`, which counts delivered orders as «В работе» and drifts every counter. Orders numbered `WO-<hash>` keep their real id in `flow.target`, not in `number` — refresh must look up `number=? OR target=?`, or exactly those orders fail the refresh with `ok:false` (mapping in `portal/refresh_status.py`).
- **Photo attachment is bound per order, never a shared pool** — the draft fallback `data/photos/*.jpg[:1]` handed every order without its own photos the FIRST unrelated image (four drafts of different organizations all showed one foreign clinic's photo). Evidence comes from the order's own card (`yandex-card-photos.ts <cdpPort> <orgUrl> data/photos/<target>/`); no per-order photos ⇒ «не приложено», never a borrowed image that leaks another client's business into this one's deliverable.
- **A customer reply is not automatically review text** — «нужно пройти по моей ссылке», «скопировать мой текст», «текст пришлю» are instructions/promises; publishing them under the client's name is the worst failure mode of this pipeline. Classify before publish: a real text is ≥15 chars, carries no timestamp prefix, is not a metadata stub («Яндекс карты»); a promise of text ⇒ wait and do NOT self-generate; instructions match the stop-word regex in `auto_publish.py` (скопировать мой текст / пройти по ссылке / подождать модерацию / пришлите.*скрин) and are excluded BEFORE candidate selection — otherwise the longest line (usually the instruction) wins and becomes the review.
- **Absence of stored text is not a wait state** — a spec that supplies the links and says «текст напечатать самому» means generate + owner-approve NOW; only an explicit customer promise of text (the stop-words above) pauses the order. Treating «no text file» as «ждём от заказчика» idles a live order for hours with nothing ever owed by the customer — classify the spec first, then decide wait vs generate.
- **Silent feed is a mode, not a fault** — outside `search`, `reviews/data/mode.json` stops the parsers by owner design (4-mode rule; watchdog even kills them), so old parser logs + a quiet feed-log are the intended state, not a crash. Read the mode BEFORE declaring parsers dead or restarting them — reviving the feeds mid-«chat»/«execute» fights the owner's mode switch and reopens ленты over active work.
