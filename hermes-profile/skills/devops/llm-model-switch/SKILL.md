# Смена модели во всём стеке

Запрос владельца вида «переведи все вызовы на <модель>, убери дефолтный <старый>»; сюда же — «добавь провайдера», «пусть весь трафик идёт к самому дешёвому» (провайдеры и роутинг в config.yaml Hermes). Вызовы LLM живут в четырёх слоях (дефолт Hermes, cron, прямые API-скрипты, ключи); переключение завершено, только когда переехали все четыре и старое имя модели отсутствует в рабочих конфигах. (Общие инварианты Hermes — `hermes-agent`: конфиг правится только CLI.)

## Порядок
1. **Инвентаризация до правок:** grep старого имени в `%LOCALAPPDATA%\hermes\config.yaml`, `%LOCALAPPDATA%\hermes\cron\jobs.json`, коде проектов (`.ts`/`.py` с `chat/completions`), скиллах и промптах. Упоминание в историческом логе/заметке — не вызов, его не трогают.
2. **Дефолт Hermes — только CLI:** `hermes config set model.default <model>`. Прямая правка config.yaml откатывается: живой процесс перезаписывает файл при следующей записи — патч применяется, проверка через минуту показывает старое значение.
3. **Cron:** у каждой задачи в `jobs.json` есть `model_snapshot` (значение на момент создания): `null` — идёт за дефолтом, имя модели — жёсткая привязка, которую смена дефолта не трогает. Найти grep'ом jobs.json, снять `hermes cron edit <id> --model <model>`; CLI-предупреждение при `config set` не заменяет этот grep — после правки сверить, что старое имя не осталось ни у одной задачи.
4. **Прямые API-скрипты проектов** (своя модель/endpoint/ключ): менять модель, endpoint и ключ ОДНОВРЕМЕННО; счётчик расхода привести к новому тарифу (для free — 0, иначе он врёт по деньгам); синтаксис проверять сборкой (`bun build --outdir <валидный путь>` — `/dev/null` на Windows не работает).
5. **Ключи:** хранилище — `.env` каталога Hermes (`%LOCALAPPDATA%\hermes\.env` на этом хосте), но скрипты проектов читают СВОЙ `.env` — дописать туда нужную переменную, не печатая значение.
6. **Смоук реальным вызовом:** минимальный запрос напрямую в endpoint; в ответе проверить и содержимое, и поле `model` — это доказывает ключ, endpoint и идентификатор модели разом.
7. **Контроль:** повторный grep старого имени по конфигам, jobs.json и коду проектов → 0 в рабочих файлах.

## Разные модели в разных Hermes-профилях

Применяй этот путь, когда модели должны отличаться между изолированными Hermes-профилями, а не во всём стеке:

1. Инвентаризируй профили и их настройки: `hermes profile list`, `hermes -p <profile> profile show <profile>`, `hermes -p <profile> config get model`. Не трогай `default`, если владелец явно не выбрал его.
2. Для OpenRouter проверь точный ID и тариф в живом каталоге `/api/v1/models`; секрет читай только из профиля `.env` в скрипте и не печатай. Подтверди, что у целевого профиля есть свой `OPENROUTER_API_KEY`.
3. Меняй только нужный профиль через `hermes -p <profile> config set model.default <provider/model>`. Не используй голый `hermes config set` — он меняет активный/default профиль, а не выбранный целевой профиль. Не трогай provider/base_url, если они уже корректно настроены для выбранной модели.
4. Проверь профиль одноразовым коротким вызовом: `hermes -p <profile> chat -q '<короткий проверочный запрос>' --oneshot -Q --max-turns 1 --source model-smoke-<profile>`. Для сравнения моделей дай им один и тот же запрос и ограничения; сохрани имя профиля, model ID и ответ отдельно.
5. Для Telegram-проверки учитывай два уровня: сначала перезапусти только gateway этого профиля и проверь `✓ telegram connected`, затем начни новую сессию `/new` в целевой группе, чтобы применился новый профильный default-модель. Смена default не гарантирует смену уже открытой сессии; память и навыки профиля остаются его собственными.
6. Перед завершением перечитай `hermes -p <profile> config get model.default` для каждого тестируемого профиля и убедись, что активен только выбранный gateway с данным bot token.

Не делай вывод о качестве модели по одному синтетическому маркеру: после проверки подключения сравни одинаковый короткий рабочий запрос, а оценки качества отдельно отличай от проверки доступности/настройки.

## Провайдер и роутинг в config.yaml (Hermes)

Запросы вида «добавь провайдера X», «пусть весь трафик идёт к самому дешёвому». Порядок:

1. **Запись — только `hermes config set`, по одному dotted-leaf за команду:** вложенные dict набираются листьями: `providers.<имя>.base_url`, `…key_env`, `…api_mode`, `…extra_body.provider.sort price`; глобальный роутинг для openrouter-трафика — `hermes config set provider_routing.sort price`. Форма записи — `website/docs/integrations/providers.md` (`api`/`base_url` алиасы, `key_env`|`api_key`|`key_cmd`, `transport`|`api_mode`, `extra_body`, `enabled: false` чтобы спрятать, не удаляя). `provider_routing` покрывает основной трафик (агент, cron, резюме лимита); auxiliary-вызовы (compression, title) настраиваются отдельно — `auxiliary.<task>.extra_body`.
2. **Проверка — сквозным резолвером, не только `hermes config get --json`:** json доказывает форму файла; что провайдер ЖИВ, доказывает только рантайм: `sys.path.insert(<дерево исходников hermes-agent>)` → `_get_named_custom_provider("<имя>")` (base_url/api_mode/extra_body/provider_key подняты) и `agent_init._custom_provider_extra_body_for_agent(...)` (extra_body доберётся до тела запроса). Наличие ключа доказывать пробой в отдельном subprocess с переменной, переданной в окружение ИЗ `.env` (файл защищён от прямого чтения); печатать только длину/префикс значения.
3. **Роутинг подхватывается при старте процесса** (CLI, cron, TUI и сборка агента в gateway читают конфиг при старте/сборке) — на живой трафик: `hermes gateway restart` ФОНОМ, затем `/status`. Синхронный рестарт из ответа на сообщение убивает текущую сессию — так не делать.
4. **Активация named-провайдера (`hermes config set model.provider <имя>`) — только по явной команде владельца:** это меняет роутинг живого трафика, «на всякий случай» не переключать.

## Pitfalls
- **Считать стоимость ДО оптимизации — по usage, а не на глаз:** в ответе chat/completions лежат `prompt_tokens`/`completion_tokens` (и иногда `cost`), прайс моделей берётся из `GET /api/v1/models` OpenRouter (`pricing` за токен ×1e6 → $ за 1M in/out). Практически всю дорогизну делает OUT: вход статичного промта — тысячи токенов на центы, а reasoning-фаза у thinking-моделей генерит десятки тысяч токенов выхода. Показывать IN/OUT/$ рядом с результатом вызова — владелец требует видеть цену каждого вызова.
- **Reasoning-модель на малом `max_tokens` возвращает `content: null` с `finish_reason: length`** — thinking съедает весь лимит, контент-JSON не появляется, и код, делающий `.strip()` на content, падает в 500 (UI получает HTML и взрывается на JSON.parse). Лечение: лимит с запасом на reasoning (6000 для средних моделей), ретрай до 3 раз на пустой content, пустой ответ — понятная ошибка клиенту (не 500), сырой ответ провайдера (`finish_reason`, тело) — в диагностический журнал; ограничение выхода оправдано только для не-reasoning моделей и стоит своих денег только после замера usage.
- **У `tencent/hy4*` internal reasoning включается, даже если ключ `reasoning` не передан, и съедает весь бюджет.** При `reasoning: {enabled: true}` и даже при `max_tokens` 12000 модель отдаёт `content: None`, `finish_reason: length`, `completion_tokens_details.reasoning_tokens` ≈ всему лимиту; увеличение лимита не лечит. Лечение: передавать ЯВНО `"reasoning": {"enabled": False}` для id с префиксом `tencent/hy4`, и поднять нижнюю границу `max_tokens` (2400 вместо 1600) для батчей. Флаг надо проставить на ВСЕХ call-сайтах проекта, а не в одном: пока остальные шлют модель без него, одни вызовы работают, а другие падают с пустым content. Проверь каждый вызов этой модели по grep и сверь `reasoning_tokens == 0` в каждом. Проверять по `usage.completion_tokens_details.reasoning_tokens == 0` — это доказывает, что reasoning выключен, а не просто «ответ вернулся».
- **Эндпоинт с фишками провайдера не переносится 1:1.** Прямой вызов вроде xAI `/v1/responses` с инструментами поиска переезжает на chat/completions другого провайдера только вместе с телом запроса И разбором ответа: сборка остаётся зелёной, а парсинг молча собирает пустоту. Форма цитат у нового провайдера своя — проверять на первом живом вызове ПОЛНЫЙ выход (текст + источники/аннотации), а не только HTTP 200.
- **Fallback на старый ключ маскирует ошибку:** `OPENROUTER_API_KEY ?? XAI_API_KEY` в скрипте после переноса на новый провайдер тихо шлёт чужую модель на чужой endpoint и получает 400/401 — читать как «ключ не тот», а не «модель недоступна».
- **«not a recognized config key» от `hermes config set` — advisory и бывает ложным:** валидатор не знает все читаемые ключи (`provider_routing.sort` он не узнаёт, хотя читают его CLI, cron, TUI и сборка агента в gateway), а подсказка «Did you mean» уводит мимо. Ключ не удалять и не «чинить» по подсказке — подтвердить реальных читателей grep'ом по исходникам; значение сохраняется и без `--force`, notice глушается `--force`.
- **Модель, на которой уже идёт рабочая сессия, не перепроверяй синтетическим прогоном.** Владелец оборвал проверки: раз агент уже отвечает на этой модели, доступность доказана — «просто в конфиге приписать и всё». Синтетический `прогон()` с включённым reasoning и малым `max_tokens` может вернуть пустой content и создать ЛОЖНОЕ впечатление поломки модели: это каприз тестового тела, не модель. Достаточно записать конфиг и сверить чтением.
- **Пустой content в прогоне — сначала отличить каприз тестового тела от реального прод-бага.** Если пустой ответ даёт тот же самый код, что крутится в бою (например `mll2.оценить_батч`), это не ложная тревога: чинь тело запроса. Если только синтетический вызов с надуманными параметрами — не трогай рабочий конфиг. Диагноз по одному полю: `finish_reason == 'length'` + `reasoning_tokens > 0` = reasoning съел лимит, а не «модель недоступна».
- **Смена модели в JobLock — это места, не одно.** Все профильные `profiles/<name>/config.yaml` (включая служебный мультиплексный `slug`), `profile_templates.model` в БД портала, `mll_models.MODEL_CHOICES` и `mll_models.PRICE_PER_MILLION`, и вложенные секции `mll_settings.json` — `mll2.model`, `mll.model`, при наличии и `bid_reply.model`. Ключ верхнего уровня `модель` может быть другим/отсутствовать: оценщик читает именно `mll2.model`, и если его не поправить, прогон уходит на старой модели, хотя все config.yaml уже новые. Сверяй через `mll2.настройки()['model']`, а не через вывод `mll_settings.json` целиком. Тариф бери из живого `GET /api/v1/models` OpenRouter (`pricing.prompt`/`completion` ×1e6), не выдумывай; без цены в таблице расчёта стоимости оценки врёт. Бэкап конфигов перед правкой.
- **Смена стиля отклика — это тоже смена модели: поправь все копии промпта и валидатор.** `DEFAULT_REPLY_PROMPT` в `mll2.py` перебивается сохранённой копией `mll_settings.json → bid_reply.prompt`; правка только константы молча не применяется. При смене формата отклика обновляй оба места и системный промпт оценки (там может остаться противоречащая строка вроде «Допустимо начать с…»).Проверь также длину `reply_draft` в `mll_models.validate_pass2_item`: короткий отказ или новый короткий стиль упирается в прежний минимум — тогда прогон падает с `reply_draft must be a non-empty bounded string`, хотя модель ответила корректно. Снижай порог до реально короткой фразы и гони прогон после правки.
- **Дороже — только с явного согласования владельца.** Даже если модель дороже «кажется лучше понимает ТЗ», не добавляй её в `bid_reply.model`, `MODEL_CHOICES` или тарифы без прямого разрешения. По умолчанию отклик наследует модель оценки (`mll2.model`); откат — удалить переопределение и его цену, чтобы не осталось скрытого источника расхода.
- **«Ничего не меняется в ленте» — читай полный путь отрисовки, а не только генератор.** Отдельный вызов отклика может возвращать новый текст, но карточка показывает старый: проверь, не перезаписывает ли его downstream-слой (например `tg_notify.послать_ready` → `offer_drafts.ensure_from_pass2`). Пометь сгенерированный отдельным вызовом текст флагом (`reply_from_separate_call`) и запрети перезапись; проверь сквозь рендер через spy, что карточка получила именно сгенерированный текст.
- **Не делай массовую перегенерацию/бэкфилл по умолчанию.** После правки откликов покажи 1–2 свежих образца владельцу и дождись решения, прежде чем трогать всю таблицу.
- **Профили заказов, созданные оркестратором после смены, не наследуют новую модель.** `ord-*` форкается из шаблона со старым `config.yaml`, поэтому живой заказ может уйти на прежней модели. При проверке заказа читать `model.default` именно его конфига и править точечно; на уровне кода — копировать модель шаблона при провизии, иначе разрыв повторится.
