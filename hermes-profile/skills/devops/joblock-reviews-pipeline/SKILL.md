# Контур отзывов (browser-automation/reviews) — эксплуатация

Отзывный конвейер JobLock: монитор чатов → реестр flow → auto_publish (фарм+гейты+публикация) → сдача на бирже. Живёт отдельно от портала (C:/sites/joblock, см. joblock-agent-portal).

## Приоритеты владельца (систематически повторяются)
- Исполнение активных заказов → мониторинг переписок → поиск новых. «Либо делай, либо меняй статус»: заказ, висящий в работе без продвижения, — нарушение.
- Каждый вызов должен улучшать систему/автономность; цель — конвейер работает 24/7 без вызова агента.
- Режимы (mode.py): chat = только монитор, execute/сдача = ни того. В Р_ПОИСК монитор чатов БОЛЬШЕ НЕ гасится (фикс 23.10: правило владельца «переписки важнее поиска» — поиск теперь поднимает и ленты, и watch-chat одновременно; переписка должна жить всегда, ответ клиента не ждёт смены режима). Ручной вызов `применить_режим('search')` со старыми закомментированными/убивающими ветками в других режимах не трогать.
- Watchdog убивает вручную поднятый монитор, запущенный как `watch-chat.ts all ...`: живость он проверяет по `покрывает()` — все номера заказов должны присутствовать в argv. Если монитор нужен вручную, запускай через watchdog/mode (они передают список номеров) либо перезапусти `применить_режим` после смены режима; после ручного подъёма проверь, что процесс выжил через 10-минутный цикл watchdog.

## watch-chat.ts (монитор чатов)
- Список заказов читается из реестра КАЖДЫЙ круг (не из argv — `all` в команде лишь маркер). В главном цикле `for(;;)` вызов обязан быть `await списокЗаказов()`: без await список всегда пуст → вечное «в реестре нет активных заказов — ждём», per-id логи не пишутся, и watchdog убивает живой монитор как «зависший» (авария 23.10: ~20 ч простоя переписок).
- Живость монитора watchdog определяет по свежести ОБЩЕГО лога `logs-watch-chats-all.txt`, НЕ per-id: монитор обходит максимум ЛИМИТ_КРУГА (14) заказов за круг, и при полной очереди старые per-id логи остальных заказов не обновятся за порог живости — проверка «все per-id свежие» убивала живой монитор каждые 10 минут (переписки молчали с ротацией процессов). Per-id лог — доказательство реакции по КОНКРЕТНОМУ заказу (строка «наших:N чужих:M» для хронологии), а не сигнал живости процесса.

## reviews_noreply_alerts.py (алерт «ответ без реакции 30 мин»)
- **Актуализация статус-синка ≠ реакция.** status_sync каждые ~3 ч пишет «актуализацию» и двигает `updated_at` — это не ответ контура клиенту. Реакцией считать только смену `state_changed_at` или статус-ноту без «актуализац»; иначе любой ответ клиента через полчаса помечается «ok» и алерт молчит.
- Сравнение дат: БД пишет `YYYY-MM-DDTHH:MM:SS+03:00` (T), лог монитора — с пробелом. Нормализуй `[:19].replace('T',' ')` перед сравнением — иначе 'T' > ' ' лексикографически и любая старая дата «побеждает» маркер.

## auto_publish.py (распознавание ссылки/текста)
- Ссылочный регэксп обязан покрывать `yandex.ru/profile/` тоже: `(?:maps|profile)/`. При только `/maps/` строка «Название https://…/profile/…» не считается ссылкой и попадает в кандидаты ТЕКСТА отзыва → dry-run «готово к публикации» с мусором, и контур может опубликовать заголовок ТЗ вместо отзыва.
- Фолбэк «первое общее фото из data/photos» убран: заказ без своего фото получает честно «НЕ ПРИЛОЖЕНО», чужие фото не привязываются.
- Тексты, требующие согласования с заказчиком («текст отзыва ОБЯЗАТЕЛЬНО согласовать»), публикуются только после его «ОК» — черновик отправить в чат, ждать ответа.
- **Текст, присланный ЗАКАЗЧИКОМ, публикуется БЕЗ «ОК» владельца** — он его, его и публикуем. «ОК владельца» (approve-черновик) требуется только когда текст придумали МЫ (ветка просит_свой_текст уже делает return). Три места ломали это правило (каскад 23.10, заказ 22388712 — три попытки, «ждёт одобрения владельца»):
  1. auto_publish: условие блокировки — «есть НЕодобренный черновик» (`approve.черновик_есть and not approve.одобрен`), а не «не одобрен» (иначе любой чужой текст стопорится).
  2. order_flow.ход НЕ пишет текст заказчика в approve-черновик (`approve._файл('.txt')`) — это создаёт ложный «черновик ждёт ОК». Черновик approve — только для нашего текста.
  3. Ошибочный черновик от старого бага удалять вместе с drafts/<id>.*.
- **Вложения качать не на каждый заказ**: `if (тз and "прикреп" in тз.lower()) or True` — `or True` делает условие ВСЕГДА истинным → files.ts (таймаут 200с на заказ) вызывается для всех заказов → полный прогон публикации ВИСНЕТ. Качать только когда ТЗ упоминает «прикреп|вложен|скриншот» И ссылки ещё нет (`not r["text"]`). Зависший dry-run — сначала проверить эту строку.
- Диагностика «dry-run говорит готово, но реальный ход не публикует»: не обрезать вывод хода до первых 900 символов (строка про заказ может быть в конце отчёта); судить по steps — отсутствие шага publish = до публикации не дошло; проверить drafts/<id>.txt и approve-статус.

## Перенос review-контура под единый диспетчер

Перед передачей управления составь карту каждого писателя состояния: `pipeline_cycle.py`, `queue.py`, `mode.py`, `order_flow.py`, `auto_publish.py`, `submit_order.py`, chat watchers, JSON/SQLite-файлы и таблицы реестра. Read-only snapshot и API-сводка дают инвентарь, но не передают переходы новому диспетчеру.

- Не считай `pipeline_cycle.py --dry-run` безопасным тестом: выбор фазы может менять режим/вкладки/процессы, очередь — снимать истёкший HOLD, а `order_flow` — писать статусы. Для миграции используй изолированные фикстуры и тестовые адаптеры; не запускай legacy dry-run на боевой базе.
- Не полагайся на `auto_publish(..., only=target)` как на ограничитель: проверяй конкретный target внутри нового адаптера и подтверждай, что соседние заказы не затронуты.
- Разделяй необратимые этапы (ответ клиенту, отклик, публикация, сдача) на отдельные адаптеры. Сохраняй действующие правила одобрения; `approve.py` подтверждает только свой черновик, а не автоматически любой текст клиента. Перед повтором после таймаута перечитай состояние биржи/чата и evidence: локальная идемпотентность не гарантирует exactly-once во внешней системе.
- Перед отключением старого контура сверяй Scheduled Tasks, реальные PID и свежесть heartbeat старого writer-а. Новый Control v3 подтверждай по команде `python control.py serve` и listener `127.0.0.1:8092`; `\\JobLockRuntimeV1` — старый Runtime 1.0, а не новый диспетчер. Сначала докажи per-step acceptance и rollback, затем ограждай старых писателей.
- Атрибуция по имени задачи запрещена: проверяй фактический процесс (listener на порту + командная строка) прежде чем считать поведение признаком контура. `\\JobLockContourV1` — задача легаси-раннера (`hermes/scripts/runner.py`, цикл legacy-обёрток); его запуск НЕ оживляет Control v3.
- Владелец постановил: старый управляющий скрипт (runner / `pipeline_cycle.py` как контроллер) не используется — из `reviews` берутся только инструменты и подключаются в V3 явными адаптерами. Не перезапускай легаси-контур как «срочный» фолбэк; `pause.json` (`{"вкл": bool}` в `reviews/data`) и `\\JobLockContourV1` не трогать без прямого указания владельца. Если пришлось — верни состояние (pause.json, задача) и скажи об этом явно.
- Перед повторной отправкой уточнения проверяй фактическую форму данных, а не сигнатуру по памяти: `dialog.уже_спрашивали` читает `контекст()['наши_вопросы']` как список СТРОК (не пар (время,текст)) — рассинхрон формы даёт ValueError и блокирует безопасный путь; фикси форму и закрывай тестом на guard.
- Для системного лога нового контура показывай только реальные LIVE-события диспетчера и реальные ошибки/исключения; DEBUG/manual runs остаются в выборочной отладке, синтетические idle/heartbeat-строки не добавляй. Частый polling — механизм доставки событий, не повод создавать событие на пустом цикле.
- `paused=false` и очередь LIVE=0 означают «scheduler включён, но простаивает», а не автономный цикл. Диспетчер только потребляет поставленные LIVE-запуски: непрерывность требует durable intake/producer плюс многошаговый LIVE workflow. Привяжи Start к запуску producer и executor, Stop — к запрету новых intake/claims и безопасной остановке текущего шага. Проверяй read-back состояния, появление реального входного заказа, последовательность фактических фаз до done или точного wait-gate и запуск следующей доступной работы. Не зацикливай завершённый одноступенчатый chat-read для имитации непрерывности. В простое оставляй лог пустым (без heartbeat); idle/wait показывай отдельно в статусе UI. Не объявляй интеграцию завершённой после одного chat-read; проверь поиск/intake, общение, статус биржи, исполнение и закрытие/сдачу, включая downstream read-back. Остановись на точном input/status/approval gate; не обходи его legacy `pipeline_cycle.py`.
- Control v3 continuous loop lives in `control-v3/joblock/pipeline.py` (`PipelineLoop` + `ReviewPipelineAdapters`), wired automatically in `web.serve`. It polls read-only review-registry candidates, drives phases (chat/execute/submit via read-only status-chat + `mode.py` tab policy) and gates every external write behind explicit safe adapters. Completed AND gated items get a 10-minute cooldown (`COMPLETION_COOLDOWN_S`) — without it the same order re-runs every poll and the queue never advances to other phases/orders.
- Fully submitted/closed orders must not re-enter the execute queue: in `read_only_candidates`, `all(parts in {published,submitted})` with everything `submitted` means SKIP, not execute. Registry state and exchange display drift independently: the portal dashboard's «В работе» label comes from `flow.exchange_status` (wz_cache), not `flow.state` — when the owner confirms an order was submitted manually, fix BOTH (`state='submitted'` + `exchange_status='submitted'` + `order_parts.state='submitted'`), then read back the dashboard row.
- The decision-only search fallback (`WorkItem('search','',decision_only=True)`) must also honor the blocked/cooldown set — without that check every idle poll re-applies the search mode via mode.py and churns the visible tabs every few seconds.
- Restart the V3 contour by killing the listener on 127.0.0.1:8092 and rerunning `python control.py serve` (workdir `C:/sites/joblock/control-v3`); portal changes need `\jb_portal` restart. Verify `/api/log/system?limit=N` shows fresh `pipeline_phase` rows and advancing orders, not repeats.
- All Telegram status posts from V3 MUST start with the literal marker `[V3]` (`joblock/notify.py`, throttled 20 s + 10-min same-text silence) so the owner can distinguish them from legacy process posts; legacy-labelled posts must not appear after the runner is stopped.
- Owner directive: do the work directly in the main session — do not delegate the V3 build to subagents and report back; he wants to watch the work happen. Use tools inline, keep him posted in one-line statuses.
- Внутри этапов лог должен быть не «чёрным ящиком»: инструменты пишут построчные действия («Нажимаю кнопку», «Ввожу текст») в шину прогресса `reviews/progress.py` → `reviews/data/progress.jsonl`; Control v3 (`joblock/progress.py` ProgressTailer) читает её и публикует строки в единый лог с привязкой к текущей фазе/заказу (`outcome=progress`, tool=источник). Обёртка `progress.выполнить(cmd)` транслирует построчно stdout внешних скриптов (bun/Dolphin). Секреты и длинные тексты в шину не писать — там авто-обезличивание, но не полагайся на него для заказческого текста. Хвостовой читатель НЕ должен брать основной lock шага (он держится весь execute) — читай текущий item по атрибуту (присваивание атомарно).
- Feed-кандидаты из `review_loop.кандидаты()` бывают короткими числовыми id ленты (5 знаков, например 8730) — это НЕ заказы биржи. Фильтруй по 6..10 цифрам до постановки в очередь; иначе цикл каждый poll падает «неверный точный target». Ошибочные и гейтнутые пункты тоже ставь в cooldown — иначе тот же заказ повторяется каждые несколько секунд и очередь не идёт вперёд.
- Legacy `/portal/log` remains the monitor; `/portal/log_v2` is the operator board and must retain the familiar `search → chat → execute → submit` phases. Default the order selector from the live `mode.json` focus and list orders from the live review registry, not the all-record legacy snapshot; an empty or reset snapshot must not make live orders unselectable.
- Use `manual_live` only for an explicitly selected one-order/one-phase diagnostic. Autonomous production must use multi-step `live` scenarios driven by the continuous producer; a completed one-step `manual_live` or `live` run is not a full pipeline. Keep DEBUG/manual traces out of the LIVE system log, and never requeue the same completed chat-read as a substitute for intake or phase progression.
- Switch legacy phases only through `python reviews/mode.py переключить <режим> [фокус]`; mode changes retab and alter process ownership, so require explicit UI confirmation and read back the new mode/focus. Keep the background contour paused during manual phase tests.
- Before execute or submit, read the live exchange status and input/evidence gates. If the order is `need-info`, status is unknown, or the required artifact is absent, show the exact blocker and stop rather than bypassing it. Never use `pipeline_cycle.py --dry-run` as a production probe: it can change modes, queue state, and order records.
- For a clean Control v3 test reset, delete only the exact `legacy_records` snapshot and explicitly identified test runs/events/receipts in its local SQLite database; verify zero afterward and do not auto-sync. Preserve MariaDB orders/projects, `registry.db`, `mode.json`, `pause.json`, heartbeats, and parser dedupe state unless the owner explicitly names those source stores too.
- Before sending a clarification, require the duplicate-send guard to succeed. If its contract fails or raises, stop and repair/test the guard; never bypass it with a direct resend.
- При очистке истории `/portal/log` архивируй только подтверждённые диагностические файлы (`runner.log`, `runner-live.log`, cron `runner-*.txt`). Сохраняй `registry.db` (`flow`, `flow_log`, `steps`, `jobs`), `mode.json`, `pause.json`, heartbeat и телеметрию активного writer-а; не удаляй parser JSONL, который служит дедуп-состоянием. До/после сверяй список архива и числа записей БД.

## Контур отзывов под Control v3 (боевой режим с 25.10)
- Боевой контур живёт в `C:/sites/joblock/control-v3/joblock/pipeline.py` (ReviewPipelineAdapters + PipelineLoop); runner/JobLockContourV1 не используется, `pause.json` держится вкл=true. Старые модули reviews вызываются только через адаптеры V3: chat = dialog+native_text+dedup.отправить_разово (только типовые вопросы), search = review_loop.main() с МАКС_ОТКЛИКОВ=2, execute = order_flow.ход(target), submit = auto_publish.сдать после проверки order_parts.
- Каждый фазовый вызов обёрнут в `_guarded` с жёстким таймаутом (search 900s, chat 240s, execute/submit 600s): зависание → `uncertain` + персистентный гейт в `pipeline_gates`, автоповтор запрещён.
- Телеметрия инструментов: `reviews/progress.py.лог/выполнить` пишет в `reviews/data/progress.jsonl`, хвостовой читатель `control-v3/joblock/progress.py` транслирует строки в единый лог (tool=источник). Registry/Dolphin-шаги уже инструментированы. Секреты и тексты заказчика в шину не писать.
- Telegram-статусы V3 идут через `control-v3/joblock/notify.py` с обязательным префиксом `[V3]` (троттлинг 20с, дедуп текста 10мин).
- Виджет витрины `/portal/` берёт статус из `flow.exchange_status`: после ручной сдачи владелец должен выставлять `state='submitted'` И `exchange_status='submitted'` (и `order_parts` в submitted), иначе заказ «высплывает» в В работе и в очереди V3.

## Закрытие заказа владельцем
- `UPDATE flow SET state='closed', status_note='закрыт по указанию владельца'` + удалить шаги activity/route/publish/submit по target (иначе auto_publish продолжит предлагать закрытый заказ) + удалить черновики `data/drafts/<id>.*`.
- Возврат в работу: state='bid' (auto_publish берёт только bid).

## Dolphin (registry.py)
- `DOLPHIN_API_KEY` — в `browser-automation/dolphin.env`, НЕ в `.env` (там другие токены). Локальный API :3001: login-with-token + Bearer-сессия; облачные вызовы (`api('/proxy')`) без локальной авторизации.
- E_PROXY_CHECK_ERROR = прокси мёртв: refresh по `changeIpUrl` (провайдер asocks), затем повторный start. Порт CDP меняется при каждом старте — брать из вывода `registry.py start`, не из памяти.
