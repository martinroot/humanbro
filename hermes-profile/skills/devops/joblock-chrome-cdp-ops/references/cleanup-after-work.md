# Уборка контура после выполненной работы

Работа на бирже оставляет после себя фоновые процессы и профили: поднятые
профили Dolphin, мониторы чатов, парсеры, временные скрипты. Владелец
требует, чтобы лишнее не копилось: «после выполненной работы, если оно
больше не нужно» — убрать. Ниже — что считать лишним и как это чинить
автоматически.

## Что держится после работы

| Объект | Норма | Признак «лишнего» |
|---|---|---|
| Профиль Dolphin | поднят только под незавершённую работу | нет заказа в состоянии bid / need-info / assigned / on-review / preparing |
| Монитор чата (`watch-chat.ts`) | один на заказ, который ждёт ответа | лог молчит дольше ~12 мин при норме «строка каждые 30 с» |
| Парсер (`parser.ts`) | ровно три: wz, kw, is | процесс есть, но лог не растёт; или процессов больше трёх |
| `tab-guard-chat-*.json` | обновляется живым монитором | файл старше часа — монитор умер, замок вкладки больше не нужен |
| `_*.py` / `_*.ts` / `_*.js` в рабочей папке | удалены | старше часа — разовый диагностический скрипт |

## Профиль Dolphin: как понять, что он запущен

Облачный список кабинета **не показывает признак running** (и `lastRunAt`
читается «ни разу» у живых профилей). Признак запуска — на диске:
`%APPDATA%/dolphin_anty/browser_profiles/<id>/data_dir` существует, пока
профиль поднят; после остановки остаётся только `<id>.datadir.zip`.

Папки профилей, которых **нет в кабинете**, — сироты: профиль удалили, папка
осталась. Она жрёт диск и создаёт ложное впечатление, что профиль «запущен»,
из-за чего их нельзя остановить. Удаляются при сверке с облачным списком.

Стоп/старт профиля — через локальный API `:3001`:
`GET /v1.0/browser_profiles/<id>/start?automation=1` (возвращает порт CDP)
и `GET /v1.0/browser_profiles/<id>/stop`. Локальный API отвечает на эти
методы, но **GET списка профилей отдаёт 401** даже после
`POST /v1.0/auth/login-with-token` с `{"success":true}` — список бери из
облака (`https://dolphin-anty-api.com/browser_profiles`), а локальный
используй только для старта/стопа.

## Зависший монитор чата: признак по логу, а не по CPU

Монитор в норме печатает «ждём ответа...» каждые ~30 секунд. Лог молчит
дольше ~12 минут — процесс завис (обычно на `connectOverCDP` к общему
Chrome), и он не выйдет по своему дедлайну. Убивать и поднимать заново.

Почему зависает: общий Chrome обслуживает ещё и парсеры, и когда к нему
одновременно ломятся несколько мониторов, `connectOverCDP` без явного
таймаута упирается в дефолтные 30 с и падает с
`Timeout 30000ms exceeded` — процесс «залипает» молча. **Всегда давай
`connectOverCDP` явный таймаут (60 с)**, иначе висят и мониторы, и
одноразовые скрипты чтения чата.

## Один монитор на ВСЕ заказы, а не по процессу на заказ

Отдельный процесс монитора на каждый заказ — это несколько одновременных
CDP-сессий к одному окну. Сессии копятся, и порт начинает **не отвечать
вовсе**: `curl http://127.0.0.1:9222/json/version` и `/json/list` пустые,
хотя Chrome жив и процессов десятки. Тогда падают все мониторы сразу
(`goto: Timeout … exceeded`), и весь контур ответов заказчикам слепнет
целиком — выглядит как «вчера отработали несколько отзывов, а дальше пошёл
большой технический лог».

Правильное устройство: **один процесс монитора, который принимает список
id через запятую и опрашивает заказы по очереди** — одно CDP-подключение,
одна вкладка, `goto` по очереди, у каждого заказа своя строка в своём
per-id логе. Подключение — с явным таймаутом 60 с.

Диагностика порта — три разных состояния, и их путают:

| `/json/version` | что это значит | что делать |
|---|---|---|
| отвечает, `connectOverCDP` цепляется | здоров | ничего |
| отвечает, `connectOverCDP` виснет после `<ws connected>` | рассинхрон драйвера/версии или зависшая сессия | обновить playwright, перезапустить окно |
| **пусто**, а Chrome жив | порт забит одновременными CDP-клиентами | убить лишние клиенты, драйвер не трогать |

Монитор, опрашивающий много заказов, всё равно должен писать строку-пульс
в лог **каждого** заказа: свежесть per-id лога — единственный сигнал
живости по конкретному заказу, и один общий свежий лог ничего не говорит
о том заказе, который перестал отвечать.

## Дедуп по тексту, без времени в ключе

Ключ дедупа для уже напечатанного сообщения и для только что найденного
должен строиться **одной и той же функцией**. Если при чтении старого лога
в ключ попадает время сообщения («14:12 текст»), а при добавлении нового
— нет, ключи никогда не совпадут, и уже доставленные ответы будут
печататься заново по кругу. Ключ — только по тексту, без ведущего времени
и без служебного префикса.

## Парсер: одна упавшая лента не должна убивать процесс

Стартовая вкладка ленты открывалась без `try/catch` и без таймаута на
`goto`: `ERR_ABORTED` / таймаут навигации валили весь процесс, и биржа
молча выпадала до ручного перезапуска. Правила:

- `page.goto(url, { waitUntil: "domcontentloaded", timeout: 45_000 })` —
  таймаут обязателен, иначе навигация висит бесконечно;
- стартовая вкладка — через `.catch(() => null)`, чтобы падение одной
  биржи не гасило процесс;
- в основном цикле: если вкладка ленты равна `null`, пробуй открыть её
  заново — иначе биржа молчит до перезапуска.

## Watchdog: живость процесса, а не свежесть лога

Проверка «лог свежий ⇒ парсер жив» неверна: упавший процесс оставляет лог
свежим на минуты (он умер только что), и watchdog считал биржу живой, пока
она молчала. Условие должно требовать **и** процесс, **и** свежий лог:
`len(парсеры) != 3 or len(живые_логи) != 3`.

## Автоматическая уборка

Скрипт уборки (режим `no_agent`, пустой stdout = убирать нечего) проверяет
по пунктам выше и глушит лишнее. Требования к нему:

- работать по **признакам состояния** (data_dir на диске, свежесть лога,
  состояние заказа в реестре), а не по «мне так кажется»;
- останавливать профиль через локальный API, читать список — из облака;
- удалять сиротские папки профилей только если облачный список доступен
  (иначе рискуешь снести живое);
- не считать мусором то, что менялось недавно;
- **не трогать** фоновые службы, которые владелец держит постоянно
  (портал, парсеры, общий Chrome) — уборка чистит только то, что создано
  под конкретную задачу.

## Пул в реестре ≠ профиль, который надо держать поднятым

Аккаунт в статусе `active` **не** означает «профиль нужен»: реестр помнит
активным аккаунт, который уже отработал свою карточку. Профиль держим
только если этот аккаунт **назначен на заказ в незавершённом состоянии**
(`bid` / `need-info` / `assigned` / `on-review` / `preparing`) — это и есть
признак «есть работа». Остальные профили глушатся, даже если в реестре
стоят `active`.

## Сколько профилей одновременно допустимо

Ограничение владельца: **не больше 3 поднятых профилей Dolphin** (каждый
держит ~9 процессов `anty.exe` и ~200 МБ). Плюс 4 новых аккаунта на
закупку — это 4 профиля, которые **создаются, но не поднимаются**:
создание профиля в кабинете не требует запуска. Поднимать надо только те,
под которыми идёт работа прямо сейчас.

## Уборка мусора: что именно чистить

- `tab-guard-chat-*.json` старше часа — монитор умер, замок вкладки больше
  не нужен;
- `_*.py` / `_*.ts` / `_*.js` в рабочей папке старше часа — разовые
  диагностические скрипты;
- папки профилей, которых **нет в облачном кабинете** (сироты).

Сироты удаляются **только если облачный список доступен**: при недоступном
кабинете сверка пуста, и удаление снесло бы живые профили с их сессиями.

## Вкладки — тоже ресурс, и у них свой потолок

Общий Chrome держит вкладки, а не соединения. Копятся они двумя разными
путями, и оба дают один и тот же симптом — порт перестаёт отвечать, весь
контур слепнет:

1. **Незакрытая вкладка на каждом вызове.** Хелпер `ctx.newPage()` → работа →
   `return` без закрытия оставляет вкладку навсегда. Если хелпер зовётся по
   расписанию, вкладок набираются десятки, а процессов Chrome — десятки.
   Лечение: `try { … } finally { await page.close() }` в каждом хелпере,
   работающем с общим окном.
2. **Дубли одного адреса.** Обычная чистка «неактивных» их не ловит — дубли
   выглядят активными. Считать вкладки по адресам и удалять повторы.

Проверять надо **вкладки, а не соединения**: перегрузка порта видна по
пустому `/json/list` при десятках живых `chrome.exe`, а утечка вкладок видна
только по их счётчику.

## Уборка вкладок — одна точка, один лимит, три вызова

Владелец просит **централизованного управления** контуром. Значит уборка
вкладок имеет один вход и один лимит, а вызывается из трёх мест: цикла
парсера, cron-задачи и сторожа. Хелпер: закрывает неактивные до лимита,
удаляет дубли адресов, умеет режим «только счётчик» для диагностики, печатает
итог. Пол вкладок — аргументом, не константой в трёх местах.

Пол должен покрывать ленты парсеров, вкладку монитора и вкладку формы
отклика. Больше — память уходит, а порт зависает.

**Замок не должен выключать уборку целиком.** Замок от отклика прикрывает
свою вкладку: если свежий замок заставляет чистку ничего не делать, то при
откликах каждые несколько минут уборка не выполнится ни разу. Замок
добавляет свой id в список защищённых, чистка идёт по остальным. Имя файла
замка обязано совпадать с glob, который чистка сканирует, — иначе он не
защищает ничего.

## Монитор жив ≠ монитор опрашивает нужные заказы

Процесс жив и логи свежие — а перечень id в его командной строке устарел, и
новый заказ не опрашивает никто. Сторож сравнивает перечень id в запущенном
мониторе с текущим множеством заказов, ждущих ответа, и перезапускает монитор
при расхождении.

## Учёт откликов — отдельным реестром

Автоконтур откликов обязан помнить, куда уже откликнулся: иначе он шлёт
дубль и, хуже, помечает неудачную попытку как отказ и убирает заказ из
мониторинга — ответ заказчика теряется. Учёт — отдельным файлом по внешнему
id биржи. **Закрывает заказ только биржа** («задание больше недоступно»);
отказ по нашему гейту заказ не закрывает — он живой, его стоит пересмотреть
позже. После успешного отклика заказ сразу заводится в состояние «ждём
ответа», иначе монитор его не подхватит.

## Порядок работы

1. Остановить то, что больше не нужно (профили — первыми, они держат
   сотни мегабайт каждый).
2. Пересчитать фоновые процессы и объяснить, что каждый делает (на
   вопрос «почему их N» отвечать списком, а не молчанием).
3. Починить причину залипания, а не только перезапустить процесс: иначе
   через час всё повторится.
4. Завести механизм (скрипт + cron), чтобы уборка не зависела от
   памяти агента.
