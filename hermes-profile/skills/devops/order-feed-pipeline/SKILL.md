# Order-feed pipeline (JobLock unified base)

Order feed is the money funnel of JobLock: exchange connectors scrape feeds into ONE standardized base (MariaDB joblock), the portal renders a filterable feed, and a strictly sequential cycle (search → chat → execute) drives the work. парный навык: joblock-agent-portal (portal codebase, engine/gate/runner).

## Always-on rules (owner, 2026-11)
- **One state at a time.** search (tick 60 s) / chat (tick 300 s, only if unread dialogs) / execute (one focus order) — never parallel. Every mode switch goes ONLY through `python reviews/mode.py переключить <режим>` (single writer of mode.json) and is logged with its trigger to the sequential journal (`portal/cycle_journal.jsonl`). VERIFY THE ACTUAL mode.json STATE, not the subprocess return code: mode.py writes the mode before finishing process/tab cleanup and can die afterwards; a nonzero RC after a successful write must not roll back a live response. Poll the file briefly for the write before declaring failure.
- **Standardized base, dumb connectors.** A connector's only job: scrape the exchange feed (visible Chrome CDP :9222) → normalize the card → POST /api/ingest. Classification, statuses, assignment are central (portal), never in a connector.
- **Choose the collection transport from the live page, not convention.** Compare the visible feed/detail page with a normal GET before wiring a source. If listing and detail data are complete, server-rendered, and public, direct HTTP collection is appropriate and avoids browser contention without bypassing authentication. If login, cookies, or client-side hydration are required, use ONE persistent visible Chrome tab per exchange (find by DOMAIN in URL, not a URL marker). For browser-driven feeds, bring the existing tab to front and read its live DOM; do not bounce through blank pages or navigate it on every tick. For the Workzilla client tab, refresh the feed through the site's own AJAX call, not via a full reload. Click the «Новые» anchor from `page.evaluate` with `dispatchEvent(new MouseEvent('click',{bubbles:true,cancelable:true}))` and capture the real response with `page.waitForResponse(r => r.url().includes('/api/order/v6/list/open'))` OUTSIDE the page; flatten all `data.*` arrays (~60 cards with subject/description/price/modified). A direct `fetch()` of that URL from page context returns only a counter `{"result":102}` — never use it as the card source. Convert `modified` from milliseconds to readable time. Keep the DOM parser as fallback. Do not reload the tab to refresh the feed: reload blinks the tab, drops CDP state, and is what makes the feed look stuck. A guarded reload remains acceptable only for a genuinely detached/dead tab. Verify by the tab URL staying at the feed root, `feed-log.jsonl` mtime advancing, and `market_projects` rows growing. Stop a running parser before opening diagnostic tabs — it closes unaccounted tabs — then restart it to pick up edited code.
- **Tab governance via pure CDP HTTP** (`portal/tabs_http.py`): allowed = monitor tab + one tab per exchange domain + user's exchange tabs (work-zilla/kwork/insolvo/fl.ru/freelance.ru/profi.ru/fabra). Before resuming any added exchange, add its host to BOTH `portal/tabs_http.py` and `reviews/mode.py` keep-tabs; otherwise cycle cleanup or mode changes can close the authenticated tab. Every 5th cycle tick close unaccounted and duplicate-role tabs. Cycle CDP-down backoff: after 3 consecutive feed failures pause 120 s instead of spawning bun every 60 s.
- **Portal feed pages auto-refresh by fetch + tbody redraw every 60 s** — full `location.reload()` reads as flicker and is banned. Heavy bun-spawn loops (refresh_all per live order) stay off while testing search.
- **Keep ONE monitoring tab open** in the visible Chrome (`/orders?state=all&monitor=1`).
- **Chrome 157 ignores `--remote-debugging-port` unless `--user-data-dir` is passed explicitly** (even the default path, spelled out explicitly, works; spelled out = `--user-data-dir=C:/chrome-profile` or the literal User Data path). Launch Chrome for the operator through a Scheduled Task with `/IT` — agent processes live in session 0, so a Chrome started directly from the agent opens INVISIBLE to the user on their desktop (verify with the process SessionId vs explorer.exe SessionId). The standing task `Chrome-CDP` (ONLOGON, /IT, `--remote-debugging-port=9222 --user-data-dir=C:/chrome-profile --start-maximized --no-first-run --no-default-browser-check`) is the canonical launcher.

## Ingest contract (exact keys, verify after wiring)
POST `http://127.0.0.1:8701/api/ingest` with `source/external_id/title/description/price/url` and optional `attachments` list of `{name,path,url,mime_type,size}`. Preserve this list unchanged across connector → cycle → app.ingest_card → ingest → market_projects.raw_json; the portal normalizer must not silently discard it. If a connector calls the field `attach`, map it to `attachments` at the API boundary. The API handler reconstructs a field allowlist, so source metadata (category, deadline, experience, counts, etc.) is silently dropped unless explicitly passed through there; extend that allowlist and test the stored `raw_json`/detail response. Normalize UI display fields with pure source-boundary helpers before ingest: card metadata and footers can concatenate names, activity text, booleans, and duplicate amounts. Test realistic multiline fixtures and verify the serialized `raw_json`, not only the DOM selectors. On duplicate upserts, do not erase a previously non-empty attachment list or metadata when a later feed snapshot omits it; merge/preserve existing values and update raw_json explicitly. Test with a mocked ingest call, then read back the exact `(source, external_id)` from BOTH tables. Wrong names (Cyrillic or `price_rub`) silently default `source='manual'` (handler reads `b.get('source','manual')`) and drop the price → duplicate MA-* orders, zero rubles. After wiring any connector verify: `/api/unified-orders` counters by source + `market_projects` rows with price>0. At the parser→cycle boundary, verify the actual top-level array key emitted by the connector (`orders` vs `заказы`) and test the adapter against that serialized shape; a mismatch can silently turn a successful scrape into zero ingested cards. Log feed/profile/ingest counts without project text and read back the exact source-qualified rows.

## Attachments across exchanges
- Pass order files through one contract: `attachments: [{name,path,url,mime_type,size}]` from each connector through `cycle.py`, `/api/ingest`, and `market_projects.raw_json`. Before choosing selectors, inspect a real authenticated detail page for each source; scope image collection to explicit attachment containers or the order-description block, and never fall back to `document.body` for images. Avoid broad selectors such as `[class*="file"]`: they can match unrelated classes (for example `profile`) and pull page chrome into the order. Accept only confirmed download endpoints, `Content-Disposition: attachment`, or a verified non-HTML file MIME; exclude profile images, HTML, CSS, SVG, and fonts. Add a marketplace-specific route only when observed in the detail page (FL links shaped like `/download/files/...` are high-signal candidates, but still require an authenticated download check); filter known static-asset paths such as `st.fl.ru/images/` unless the file is inside an explicit attachment container. Resolve redirects and fetch in the authenticated browser context with cookies and the order-detail referrer; a stale 404 or HTML response is not a successful download. Save verified files with safe deterministic names under a source-qualified order folder, keep the size cap explicit, and include MIME/size. On duplicate ingest, merge existing attachments first, then sanitize known site chrome so preservation does not keep false positives. Verify the actual local file exists and read back `raw_json.attachments`; then test that Telegram sends it with the correct native media method. Mark a source verified only after a live authenticated sample completes this entire path—unit tests and compilation alone do not prove source DOM coverage.

## One interface for every enabled exchange
When several exchanges are enabled, expose them through ONE adapter, not per-source branches scattered across feed, cards and buttons. The adapter owns the normalized card (`source`, external id, human-readable marketplace name, project URL, application URL), the button set, and the step sequence. Older helpers that build an application URL must delegate to the adapter; otherwise a newly enabled source has no application link while the others look healthy, and the same exchange can end up with two different URL shapes in different surfaces. Read the enabled set from settings (`mll_settings.json["биржи"]`), never from a hardcoded list — wiring a source that the owner has disabled is an out-of-band action.

## Execution quality gates (when an order reaches an agent)
- A QA result is a TOOL result, not agent prose. After each major step run the real validator (`ffprobe`, a `validate` script, `pdfinfo`, a spreadsheet read) and write a machine-readable trace to `qa/checks.json`; the handoff contract is `qa/deliver.json` with the artifact path, `checks_passed` and three 0–100 scores. No contract = not done, even when the agent says so in chat. Any score below threshold returns to the step that produced it.
- Inventory assets BEFORE searching the web: list the work folder and `sources/` first. Search-first burns minutes on 403/404 while usable files already sit on disk.
- Never edit the profile's own skills mid-order — rewriting `SKILL.md` during execution is drift, not work. Skills change between orders through template graduation.
- A useful skill or reference discovered in an order belongs in the SOURCE template and the portal registry too, not only in that one order profile; check it is absent first and back up the template.

## Cycle engine (portal/cycle.py, daemon thread of the portal)
- Keep source failures isolated inside the sequential search tick. Poll fast public HTTP sources before slower visible-browser connectors; a timeout, malformed output, or ingest error from one exchange must be logged and must not `return` from `тик_поиска` before later sources run. Keep CDP-backed connectors serial, add bounded timeouts, and test that a first-source failure still allows a later source to poll. Current order: Freelance.ru public feed → Profi.ru authenticated visible tab → Workzilla → FL.ru → Kwork. Freelance.ru reads the newest page and caches successful detail parses by task ID; do not sweep older pages as an implicit backfill. Profi.ru reads only rendered order cards from the already-authenticated backoffice tab and must never click its hide/refuse control. Neither source has a verified automated offer path; keep direct project links and internal response-status marking separate from marketplace submission.
- Gate EVERY connector launch (legacy and new) on `/portal/settings` (`settings_page._прочитать()` / `mll_settings.json["биржи"]`) before spawning its subprocess or touching CDP. A helper that exists but is not called does not protect a blocked exchange. When a user reports an access-denied/DDoS block, turn that source off and verify the next search tick records a skip without launching its parser; never retry through another IP/proxy to evade the block. When adding a key to an existing config, default a missing new key on without overriding an explicitly saved false value; test both enabled and disabled paths.
- `print()` inside the portal task process MUST be Unicode-guarded (try/except UnicodeEncodeError) — the Scheduled Task console is cp1252 and an unguarded Cyrillic print kills the daemon thread silently right after «старт» (journal shows start but no ticks = this bug).
- Fabra is NOT in the activity-toggle set (owner removed it; PARSER_SINK=joblock already).
- For stalled-flow reports, follow `references/intake-vs-funnel-diagnosis.md` to separate source liveness, new unique IDs, pass-1/pass-2 progress, and notification destination; an ingest count alone is not a new-order count.

## Nginx /portal/ prefix (external view)
All portal pages behind nginx live under `/portal/`; internal links built as absolute `/orders`, `/api/...` break there. Pages take the base from the `X-Forwarded-Prefix` request header (nginx location sets it) and the page JS derives its api prefix from `location.pathname.indexOf("/portal/")`.
- The root route `/` MUST pass the REAL request through (`def index(request): return orders_page.orders_page(request)`) — a wrapper building a fake Request loses the header, and the module/echo shadowing bites: `orders_page` is the MODULE, the function is `orders_page.orders_page`.
- Debug the path with the temporary `GET /api/echo-headers` (returns received headers) before touching page code.
- Multiple nginx masters can bind :8080 simultaneously (both answering round-robin with DIFFERENT configs) — when a config change does not take effect, kill ALL nginx processes and start exactly one; a plain `-s reload` may only touch one of them.

## Feed page pitfalls
- Never embed JS inside an f-string page: `${}` template literals and `#` comments break f-string parsing. Prefer a standalone `.js` asset; if inline JS is necessary, use a raw Python string. Normal triple-quoted Python strings consume backslash escapes such as `\\\"`; render the actual page, extract every `<script>`, and run `node --check -` before restart. If syntax validation fails, do not restart or report the UI complete.
- Use the shared topnav (`portal_nav.render_nav`) on every page; remove self-referencing legacy link rows («← портал» from the page that IS the portal). `portal_nav.NAV_CSS` is bare CSS — wrap it in `<style>` tags when inlining, or it prints as visible text and the nav renders as raw blue links.
- Multi-page JS (panel logic with fetch/handlers) goes in a standalone `.js` file read at render time and embedded via `<script>` — never inline through a Python patcher: heredocs mangle `\\n`/quotes and f-string templates break on `${}`/`#`.
- A DOM click handler (e.g. details expander) must live at TOP LEVEL of the page script, not inside the refresh function — inside it registers only after the first refresh tick (button dead for the first minute) and re-registers every tick (listener leak).
- Row-level status pills must show the label WITHOUT the summary counter — counters belong to tabs/header only; per-row «Статус · 105» reads as garbage.
- JS that renders API data must type-guard every field: `const esc = t => (typeof t === "string" ? t : (t == null ? "" : String(t)))...` — a number/object in `description` throws `.replace is not a function`, and if the click handler's `catch` is silent the expander button dies with no visible error (always `console.error` inside catch and test expanders headlessly).
- The app DB config opens DictCursor — never index fetchone() results by position (`r[0]` → KeyError swallowed by any try/except); use `list(row.values())[0]`.
- JSONResponse chokes on `Decimal` (prices from MariaDB) — `float(price)` before building the response.
- Status filters (see the pass-2 section): все/black/white/оценка_блек/оценка_вайт with counters; the tabs must accept `all`. Old canonical statuses (active/waiting/done/failed/blocked/closed) are REMOVED from the feed — do not re-add them; map legacy DB values when rendering (needinfo/new→new, running/done/ok→white, junk→black).
- `orders.status` was converted from ENUM to VARCHAR(24) — when a connector writes a new status value, prefer VARCHAR; an ENUM column silently truncates unknown values (DataError 1265).
- Cross-table joins between portal tables can hit `Illegal mix of collations` (utf8mb4_general_ci vs utf8mb4_uca1400_ai_ci) — add an explicit `COLLATE utf8mb4_general_ci` on the join column instead of rebuilding tables.

## MLL pass 2 — «Оценка» (portal/mll2.py, страница /mll)
Применяется к white. Отдельная модель (select на странице), отдельный системный промпт «техлид Hermes»: риски/время/план-чеклист/оценка стоимости ₽/вопросы заказчику/score 0-100, только суть. Воронка: score ≥ текущего порога в `mll_settings.json` → `ready`; всегда читать configured value, не предполагать устаревший default. При изменении порога уже оценённые pass2-строки не пересчитываются сами; вердикт в `analysis_json` под ключом `pass2`. Канон вкладок ленты: все/black/white/оценка_блек(pass2 reject)/оценка_вайт(ready) — сводку считать ДО фильтра-continue, иначе счётчики чужих статусов обнуляются.
- **Оба прохода — фоновые startup-треды портала, не только кнопка.** Цикл: гнать пакеты без паузы пока очередь непуста, потом спать интервал. Владелец считает «оцениваются все поступающие» обязательным поведением.
- **Батч одним вызовом:** все карточки пакета в одном промпте, ответ JSON-массив коротких `[{id,v,why}]`; дели стоимость вызова на число карточек в per-order логе. Маршрутизацию моделей, обработку OpenRouter error payload, проверку JSON/ID-покрытия и stateless-контекст веди по единой процедуре в `joblock-orders-pipeline` → «Статусы и MLL-воронка», не дублируй здесь правила парсинга.
- **MariaDB не знает `CAST(x AS JSON)`** — JSON-объект в LONGTEXT писать read-modify-write в Python (loads→dumps→UPDATE), иначе `$.pass2.score` по JSON_EXTRACT возвращает NULL навсегда. Строку-значение, записанную ранее, чинить разово в Python, не SQL-CAST.
- **Pass-2 prompt philosophy (owner directive):** target profile = agent-type IT work (web dev/CMS: WordPress, Opencart, Tilda, Bitrix, CRM/panels, VPS/deploy, integrations/API, Telegram bots, parsers, scripts, automation, content). NEVER reject for missing materials, accesses, budget or ТЗ details — clarifications with the customer are technically realizable (dialog/files/accesses are part of the process): a profiled task without details = HIGH score, missing info goes to questions/risks. Low score only for principally non-agentable work: physical/offline, manual routine over thousands of rows, taste-driven design without criteria, unlicensable software, legal liability, scam. score = agentability × ТЗ clarity (how much we can clarify by questions).
- Дедупликация объявлений — часть MLL-прогона: перед оценкой группа по биржа+LEFT(title,120)+цена → все кроме первой (MIN(id)) получают `dublicate` и выпадают из ленты и из оценки; работает по ВСЕМ статусам (дубль оценённого — тоже дубль), факт пишется в лог («дедупликация: закрыто N»).

## Telegram bots: two roles, thread-scoped config (portal/tg_bot.py + agent_presets.py)
- **Role split:** bot 1 (orders token/chat) owns order cards, menus, profile management, per-order training and MLL draft callbacks in the orders-control group; bot 2 is only the native Hermes gateway in the executor group. Keep menus and management out of the gateway. «Откликнуться» is a callback that generates a saved MLL draft with edit/approve actions, never a URL shortcut; training opens a per-order profile picker with an explicit «➕ Создать новый профиль» action. See `joblock-orders-pipeline/references/telegram-profile-control.md` for callback gates and test/live behavior.
- **Executor bot = native Hermes profile gateway, never a custom echo/long-poll worker.** Use real named profiles for agent sessions and order assignments. Retire presets as a second profile registry; profiles own their config, model, memory, skills and history. Only one gateway task/process may poll the shared executor token.
- **One long-poller per token — two pollers deadlock in 409:** duplicate portal instances (double autostart + manual `/Run` of the same task) each poll the same token and Telegram answers `409 Conflict` to both forever. Symptom: the queue is readable by a manual getUpdates (= nobody is polling) while the portal log floods with 409. Kill ALL app.py processes, start exactly one.
- **Thread-scoped, never module-global bot config:** with both feed and executor threads in one process, a startup thread that switches a module-global role variable starves the other thread (it then reads the wrong token). Key the config off `threading.current_thread().name` ('tg-bot' vs 'tg-exec') — and make the string SET equal the string CHECKED: the thread names itself from its role argument, so the config check must accept exactly what the thread sets (accept both spellings, e.g. `in ("tg-exec", "exec")`), otherwise the executor silently polls the feed token and every command in the gateway group goes unanswered.
- **Full Telegram diagnostic chain, in order:** 1) manual `getUpdates?timeout=0` — queued updates = nobody is polling; 2) `getWebhookInfo` — a registered webhook diverts all updates (url must be empty); 3) `getChatMember` — confirm the bot is actually in the target group (administrator ⇒ privacy mode is irrelevant, it reads everything); 4) send a test `sendMessage` — posting permission; 5) only then suspect code. Log every consumed update to a file (update keys + chat + text) so 'bot silent' resolves to 'nothing arrives' vs 'arrives and fails' in one look.
- **Confirm polling health by the queue, not by the log:** manual `getUpdates?timeout=0` returning N queued messages = the bot is NOT consuming; an empty queue = healthy. Inline menus (`/menu` with callback_data buttons) need an `answerCallbackQuery` per tap and a `menu:root` back button on every submenu.
