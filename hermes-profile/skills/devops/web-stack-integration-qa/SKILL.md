# Web-stack integration QA

Use for web applications whose browser frontend crosses a reverse proxy, API gateway, or multiple backend services. Treat the public browser path as the product: a healthy localhost backend is not proof that the user-facing app works.

## Procedure

1. **Reproduce at the user's exact origin.** Fetch the public HTML and expected public API routes with the same authentication and path prefix. Compare with direct backend responses. Record status, content type, and response shape; a `200` page does not prove its JavaScript or API calls work. Before adding a product/marketing subsite, inspect the existing site root, DNS A/AAAA records, certificate, and active virtual host; add an isolated route instead of replacing an existing landing or app root. A working IP:port route does not prove the named domain is live. For a product page about an existing multi-service stack, inventory each module against source/dispatcher code, live adapters, and working tests before writing copy; separate code presence from live availability and label “in use”, “partial/blocked”, and “not connected/roadmap” separately. When asked for the current project structure, return a compact tree of major modules with those state labels, known blockers, and the concrete revival actions. Verify marketplace intake, messaging, execution, and delivery adapters independently—listing a marketplace name is not proof of an end-to-end integration. For live module/activity dashboards, expose a dedicated read-only public status projection and keep operator APIs authenticated; omit order IDs, titles, briefs, messages, and raw errors. For Worker.Skin product pages, use restrained, credible design with complex project-level examples; omit exchange branding when requested. Label randomized synthetic examples as DEMO and keep them separate from live orders and service status. Build live activity only from real logs, never demo events. Compare `last_seen` to the current time and label stale separately—an old `ok` flag is not an online service. Derive each composite module state from its full dependency set and report `partial` when only part is healthy; an online API alone does not prove a browser-backed chat or agent runtime can execute.
2. **Validate what the browser receives.** Extract inline JavaScript from the returned HTML and run the language parser (`node --check` for JavaScript); when HTML is generated from Python, test the emitted script rather than the source and keep the containing literal raw or move the script to a static file. Re-fetch and parse the public response after deployment too. Check stylesheet/resource URLs and browser console. Python compilation cannot validate JavaScript embedded in a Python string.
3. **Trace request paths end-to-end.** Map browser URL → proxy rewrite → application route → downstream service. Probe each seam separately and through the exact public prefix, including proxy calls to every backend. Build frontend URLs from the deployment base path; absolute `/api/...` calls can escape a mounted `/portal/` path, while relative URLs depend on the page's trailing slash. Compare public and direct-backend status/content so a local `200` cannot mask an external `404`.
4. **Exercise controls, not labels.** Confirm navigation selectors match real DOM IDs, each tab changes the visible section, and each section's required data is populated when opened directly from a fresh page. A lazy-loaded catalog can leave a dependent form empty if its loader only runs in another tab. Exercise action buttons through the intended request. Build dynamic controls with escaped `data-*` attributes and delegated listeners instead of interpolating JavaScript into quoted inline `onclick` HTML. For order workflows, verify the requested entry gesture itself (clicking a row must open that order's chat when specified; the monitor must assign or reuse a chat). For chat-first template workbenches, keep context and tool settings in a separate settings tab rather than making the editor the default view.
5. **Trace business transitions read-only first.** Verify intake/listing, order persistence, template lookup/assignment, runtime availability, session/run creation, events/chat, artifacts, and final status. For editable agent templates, trace saved context all the way into each runtime request; a persisted catalog change alone does not prove execution uses it. Treat draft/published state as an execution gate: only a successfully synced trained version belongs in execution selectors, and verify selected tool names against the runtime registry rather than trusting YAML metadata. Enforce tool allowlists fail-closed: an empty or wholly unknown list must expose no tools, never widen to the full registry. Key portal assignment idempotently by source order ID, require a complete brief, and create/assign without auto-starting the agent. When chat history is split across services, join the runtime transcript by persisted session ID with the app's events and artifacts, and keep order state readable if the runtime is unavailable. Confirm downstream health and API contract before claiming end-to-end execution.
6. **Isolate stateful tests.** Run create/assign/start tests against a disposable service/data directory or a uniquely tagged test-owned fixture with guaranteed cleanup. Record the generated ID, resolve its directory from service configuration, and before deleting verify that exact record still carries the test tag; never bulk-delete by a broad title/status filter. Do not repeatedly create QA orders in persistent production storage, and do not inject fake marketplace listings merely to validate intake.
7. **Fix one root cause and keep the regression test.** For generated assets, test the emitted artifact, not only the source. Prefer raw Python strings or separate static files for embedded HTML/JS so Python escape processing cannot turn JavaScript `\\n` into literal line breaks.
8. **Deploy and re-verify publicly.** Restart only the intended service under its actual supervisor; identify the listener and its launcher/child processes instead of killing by broad process-name match. On Windows, inspect a scheduled task with `schtasks /Query /TN "<task>" /V /FO LIST`; for Nginx, set its working directory to the prefix and pass explicit `-p <prefix> -c conf/nginx.conf` when startup would otherwise resolve relative paths from `System32`. Run `<nginx.exe> -t -p <prefix> -c conf/nginx.conf`, then start/reload through the task and verify the task result, listener owner (`Get-NetTCPConnection -LocalPort <port> -State Listen`), and exact HTTP route; syntax success alone does not mean a running master reloaded. Verify local and public health, public-prefixed API calls, exact deployed HTML/JavaScript, browser console, loaded data, and essential click flows after deployment. When resuming an interrupted task, continue from the first unverified acceptance criterion; do not close with an interim report while known fixes remain.
9. **Report evidence and blockers precisely.** Name exact paths and flows that passed. If a downstream runtime is absent or unreachable, mark that segment blocked and identify the boundary; an expected error or local API `200` is not proof of a full run.

## Common pitfalls

- A valid Python module can serve invalid JavaScript when string escapes are processed before delivery; syntax-check the extracted response body.
- A direct backend route can return `200` while the public reverse-proxy prefix returns `404`; test the URL the browser actually constructs.
- A button can render but remain inert because its generated inline handler is malformed; exercise its event path, not only HTML presence.
- When removing a UI input, remove every reference to it from the generated script too: a leftover assignment in the success branch raises after the action completed, so the UI reports failure for a successful operation.
- For destructive controls, verify the exact endpoint the page constructs through the public prefix; a plain backend route can 404 behind the proxy while the handler itself works. See `references/portal-destructive-actions.md` for the backup/proof recipe.
- An order can remain marked `running` when the runtime fails before startup; test failure transitions and make unavailable dependencies explicit and recoverable.
- A template editor can save a new prompt without changing agent behavior if the bridge still sends only the customer message; test the composed runtime input after every context edit.
- Chat history often spans separate stores: do not treat bridge events as the full transcript or make the whole detail page fail when the runtime session API is unavailable.
- A background launcher exit code does not establish service state; verify the active listener and HTTP behavior.
- Verify layout utilities against the exact shipped framework stylesheet, especially alpha releases.

## Completion standard

Call the pipeline complete only after the browser-visible entrypoint, every user-specified click path, and downstream business transitions pass against the deployed system. For multi-part UI work, turn each requested entry gesture into an acceptance checklist and close every item with post-deploy evidence; if any item is unfinished or blocked, report the task as incomplete rather than presenting prepared code or a subset as done. Separate verified segments from unavailable or unverified ones in the final report. For an explicitly requested ZIP, build it from final files after the last edits, exclude credentials and customer data, verify the entry list and `ZipFile.testzip()`, and attach the archive with `MEDIA:/absolute/path`; a live-site URL is not a substitute for the ZIP. State clearly when the archive is a Worker.Skin component package rather than the full JobLock repository.
