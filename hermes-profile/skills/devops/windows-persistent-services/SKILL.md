# Постоянные сервисы на Windows Scheduled Task

Класс: поднять/проверить/перезапустить долгоживущий Python-процесс (контур, runtime, gateway, портал) как задачу Windows. Задача нужна для автоперезапуска после падений и ребута — не для периодического срабатывания.

## Регистрация
- Писать `.ps1`-файл и запускать `powershell -NoProfile -ExecutionPolicy Bypass -File x.ps1`. НЕ собирать команду как `-Command "..."` внутри bash-терминала: bash съедает `$`, `$_`, `$(...)`, и команда ломается на `term is not recognized`.
- Скелет: `New-ScheduledTaskAction -Execute <python.exe> -Argument '"<полный путь>" [args]' -WorkingDirectory <каталог>`; триггер `-AtStartup`; настройки `RestartCount 999`, `RestartInterval 1 мин`, `ExecutionTimeLimit ([TimeSpan]::Zero)`, `MultipleInstances IgnoreNew`, `StartWhenAvailable`; principal `-LogonType S4U -RunLevel Limited` (без пароля).
- Путь к Python брать `(Get-Command python).Source` — в другой оболочке PATH может отличаться.

## Проверка (Start-ScheduledTask ничего не доказывает)
1. Команда возвращается успешно и при мёртвом действии. `State=Ready` почти всегда = «действие завершилось, потомок умер» — это не запуск. Для долгоживущего сервиса не оборачивайте Python в `start /min` внутри `.cmd`: Task Scheduler может завершить отсоединённого потомка после выхода wrapper. Запускайте Python foreground из действия задачи или удерживайте wrapper до остановки сервиса, чтобы задача оставалась `Running`.
2. Проверять три факта: `State=Running`, свежий heartbeat самого сервиса (файл или запись в БД/журнале), и что PID/владелец нужного порта действительно относится к ожидаемой команде.
3. Перед остановкой/стартом сверять `Task To Run` через `schtasks /Query /TN <task> /V /FO LIST` и CommandLine процесса: имя задачи не доказывает, какой контур она запускает; на JobLock-хосте `\\JobLockRuntimeV1` запускает старый Runtime 1.0, а Control v3 — отдельный `python control.py serve` из `C:/sites/joblock/control-v3`. При поиске процесса из bash не фильтровать `cmdline` только по подстроке пути: оболочка может содержать текст диагностического скрипта и дать ложное совпадение; сверяйте исполняемый файл, фактический аргумент скрипта и PID listener-порта.
4. Старый процесс может пережить `Stop-ScheduledTask`: сверять владельца порта (`netstat -ano | grep ":PORT" | grep LISTEN`) и `taskkill /PID <его>` перед стартом — иначе новый экземпляр не поднимется, а старый продолжит работать со старым кодом.
5. Перед стартом убивать ВСЕ процессы по CommandLine, а не один «похожий»: оставленный рядом ручной экземпляр = двойное исполнение шага.
6. **Правка файла не означает новый код в процессе.** Модуль, импортированный работающим сервисом, живёт в `sys.modules`; после правки трейсбейс печатает НОВЫЕ строки файла (linecache), а имя берётся из старого bytecode — картина «NameError на имя, которое видно в этой же строке». Доказательство нового кода = новый PID после рестарта + очищенный `__pycache__`.

## После ребута хоста проверять ВСЕ порты контура — автозапуск есть не у всего
После перезагрузки сервера часть сервисов НЕ поднимается сама (у nginx может вообще не быть задачи/службы, jobsy запускался руками). Процедура: `netstat -ano | grep LISTENING | grep -E ":(8701|8080|8000|8788|9222)"` → всё, что молчит, поднимать по одному и проверять curl'ом снаружи (не только localhost). Запуск nginx из терминала С `&`/подоболочкой подвешивает сессию (nginx форкнет воркеров и держит stdout) — только через PowerShell `Start-Process`/отсоединённо; после старта проверять и основной путь (`/portal/` с basic-auth), и конкретную страницу, которую назвал владелец.

## Остановка / вывод из эксплуатации
- Прежде чем убивать, перечислить ВСЕ векторы автозапуска трёх видов: `schtasks /query /fo csv | grep -i <имя>` (задачи), cron-guard'ы (`cronjob_manage list` — no_agent-скрипты с коротким тиком), супервизор-процессы (keeper-класс, `.bat` с `:loop`). Остановка = disable у КАЖДОЙ задачи (`schtasks /change /tn X /disable`) + пауза cron-guard'а + kill процессов; одного `taskkill` недостаточно.
- **Re-verify через интервал самого быстрого guard'а и добивать воскресшее.** Guard с тиком 2 мин успевает перезапустить процесс, пока ты дожимаешь остальные векторы: сначала ставить guard'у паузу, потом kill'ить, потом ждать один интервал тика и проверять по CommandLine ещё раз — иначе убитый сервис тихо живёт дальше.
- **Файл состояния сервиса — не доказательство, что процесс жив.** Watchdog/супервизор может перезаписать state-файл (например `active_profile`) в пользу остановленного инстанса. Определять живой инстанс по `CommandLine` процессов (`--profile X`, аргумент скрипта, PID listener'а); при расхождении с файлом сначала отключить guard, затем остановить процесс, затем исправить файл и проверить ещё раз через интервал тика. Иначе каждый следующий шаг будет адресоваться к несуществующему процессу.
- После остановки проверять, что НЕ убито нужное: у каждого хоста есть «охраняемые» процессы (портал, БД, nginx, песочница) — сверять итоговый список процессов с этим списком, а не с «похоже на старое».

## Пользователь-владелец сервиса: задача от его имени
- Если сервису нужен доступ к пользовательским процессам (CDP-браузер, bun-коллекторы, пользовательский PATH) — НЕ поднимать задачу под SYSTEM: системный контекст не видит пользовательские процессы и переменные. Использовать ONLOGON-задачу без `-RU` (бежит от текущего пользователя, пароль не нужен, `/RL HIGHEST /IT`).
- Путь к Python в `.cmd`-обёртке писать ПОЛНЫМ до конкретного venv-интерпретатора, а не голым `python`: системный python может не иметь зависимостей приложения (например pymysql у FastAPI-портала) — процесс умирает на импорте через секунды после старта, а `State=Ready` выглядит «нормально».

## Pitfalls
- **Консоль задачи — ANSI (cp1252):** первый же `print` с кириллицей в дочернем процессе падает `UnicodeEncodeError`, шаг возвращает код 1 с ПУСТЫМ stdout — причина остаётся только в stderr. Фикс: env детей `PYTHONUTF8=1` + `PYTHONIOENCODING=utf-8`, у себя `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`, а stderr шага писать в журнал. Без stderr падение в среде задачи не диагностируется вообще. Если процесс запускается лаунчером без перенаправления (`.bat` с одной строкой), stderr вообще не сохраняется — тогда ловить необработанные исключения САМОМУ приложением (middleware/except-hook) и писать traceback в свой журнал-файл; иначе клиент видит только «500 Internal Server Error» без причины.
- **Не смешивать %-форматирование и strftime:** `strftime("%H:%M:%S код %s" % x)` бросает `ValueError: unsupported format character` — `%`-подстановка снимает шаблон до strftime; строковые состояния собирать конкатенацией.
- **Heartbeat писать при старте, до первого шага** — иначе «сервис мёртв» не отличим от «первый шаг ещё идёт», и мониторинг даёт ложные «не пульсирует».
- **Инлайн-патчи с бэкслэшами через bash-heredoc ненадёжны на этом хосте:** heredoc/терминал искажает `\n`/`\"` в литералах (реальный newline внутри строкового литерала → SyntaxError в прод-файле). Любую правку с escape-последовательностями делать скриптом-патчером через write_file (он пишет байты как есть), и после патча — обязательный `ast.parse`/`py_compile` до рестарта сервиса.
- **nginx как долгоживущий сервис перезапускать с его prefix:** мастера запущены `-p C:/nginx -c conf/nginx.conf`; `nginx -t`/`-s reload` без того же `-p` падают на относительных temp/pid путях («CreateDirectory … failed», «invalid PID number»). Несколько мастеров-зомби дают reload-ошибку OpenEvent — тогда taskkill ВСЕХ nginx.exe и старт заново с тем же `-p`; после рестарта проверять и auth-локацию (401/200), и проксируемый бэкенд.
- **Процесс умирает после ПЕРВОГО успешного шага** — искать исключение в обработке результата между шагами собственного цикла, а не в падении самого шага (шаг в это время отработал ok и написал журнал).
- **Фоновый (daemon) тред с исключением умирает ТИХО: процесс продолжает отвечать, а тред просто перестаёт тикать.** Симптом «цикл стартовал и висит» при живом HTTP — это не зависание, а мёртвый тред: неперехваченное исключение в threading.Thread не роняет процесс; traceback оседает только в логе сервиса строкой «Exception in thread». Диагностика «тред перестал тикать» = искать «Exception in thread» в логе сервиса ПЕРВЫМ делом; тело цикла треда оборачивать в try/except с записью ошибки в ЖУРНАЛ ЦИКЛА (не print — print на cp1252 сам падает и становится причиной, а не симптомом).
