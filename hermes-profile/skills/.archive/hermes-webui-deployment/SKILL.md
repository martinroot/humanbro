# Hermes web UI deployment

Use for installing, configuring, localizing, and exposing a companion web UI that reads or writes Hermes Agent state. Keep the operation bounded to the requested UI; do not change Hermes profiles, dispatchers, workers, or databases unless explicitly requested.

## Procedure

1. **Inspect before installing.** Read the repository README, install guide, `pyproject.toml`, lockfile, platform requirements, auth code, data-source imports, and service entrypoint. Check the actual OS, Python, package manager, Hermes CLI, existing checkout, target port, and Hermes Kanban DB path. For a remembered CRM or port, search recent context when useful, then map listeners and firewall rules to the process, launcher/config, app, and database before naming a URL; don't infer the project store from the most familiar port. Compare every Hermes symbol the UI calls with the installed Hermes version; inspect current canonical APIs, not only the UI repo's assumptions. Clone into a new dedicated directory; preserve existing Hermes and project trees.
2. **Respect platform support.** If the documented installer assumes Linux/macOS/WSL, do not run its shell/systemd scripts on native Windows. Use the documented manual path and lockfile when present; pin the UI environment to the Python version used by installed Hermes, because `uv` can otherwise choose a newer compatible interpreter with a different dependency set. Verify Hermes imports in that environment before launching. Add a platform-specific launcher only after foreground startup works; do not auto-upgrade Hermes or its dependencies.
3. **Protect the shared state.** Confirm the WebUI's exact Hermes import root and database path before first start. Determine whether it reuses the canonical SQLite database, whether startup initializes/migrates it, and whether any default board is created. Before cleanup, inspect schemas and row counts read-only across plausible targets; distinguish project records from Kanban tasks/events/runs and sandbox data from live intake, and confirm the exact target. Never infer the project database from only one app's schema. Use only a documented delete API or supported DB-maintenance path; if target or semantics are unclear, do not guess a DELETE or purge adjacent history—report counts and ask. Do not point tests at production data; use fake adapters or a copied fixture database. Record pre/post hashes for read-only smoke tests.
4. **Localize the complete interface.** Inventory dictionary keys and every direct user-visible string in HTML, placeholders, ARIA labels, `textContent`, toasts, prompts, dialogs, loading/error states, and status renderers. Add a complete locale, set `<html lang>` and the first-run default, preserve language choice, and test switching in dialogs/dynamic components. If ES modules use version query strings, bump the shared i18n module URL consistently across all importers and the HTML entrypoint to avoid duplicate language state or stale cache.
5. **Secure before exposing.** Keep loopback as the default. Before remote access, require a high-entropy API token, restrict Host headers, and ensure the browser UI has a password/token entry path that sends the token in headers only; use session-scoped storage rather than query strings or hard-coded frontend values. Prefer Tailscale or a trusted TLS reverse proxy. Do not publish a token-protected API over plain public HTTP as if the token were confidential: HTTP exposes it to network observers. If the user explicitly requests direct public-IP access, state this risk and use the strongest available transport/auth controls before adding a narrowly scoped firewall rule.
6. **Verify in layers.** Run the repository's offline tests first. On native Windows, classify shell-installer tests as platform-specific when they depend on Unix executable bits or systemd; run the portable application tests and verify the manual Windows path instead of changing source permissions to force those tests through. Start only the requested web process; confirm health and static page, protected API behavior, then verify localization and same-origin mutations. Also query the intended project-data endpoint read-only and check source/row counts: a healthy root or an unrelated DB does not prove the CRM is showing the intended projects. Only after the protected path passes should remote routing/firewall be changed; verify the exact public URL from outside and read back firewall/listener state. Never stop or rebind unrelated services.
7. **Persist only after acceptance.** Add a startup task/service only when requested and after a successful manual run. On native Windows, do not leave Uvicorn attached to an agent terminal. Launch it detached and, when reboot/login persistence is requested, register an idempotent user-logon task. Start the child with `Start-Process` and explicit stdout/stderr redirection: PowerShell `$ErrorActionPreference='Stop'` can promote Uvicorn's normal stderr startup logs into a terminating native-command error. Verify the child stays alive, exactly one expected listener appears, the task returns success, and health responds before reporting success. The launcher should read the protected env file into the child process without echoing secrets, check the target port first, exit if the expected app already owns it, and fail clearly if another process owns it. Verify Task Scheduler's last result, exactly one expected listener, local health, unauthenticated API 401 plus authenticated API 200, and the external URL after startup. A firewall allow rule with no listener does not mean the service is running. Keep secrets in a protected local environment file, not command history, source, logs, or chat. Report the URL only after external verification; report authentication requirements without revealing the token.

## Hard pitfalls

- A successful `git clone` is not an installation or a runnable service; dependency sync, Hermes import resolution, database path, auth, and health checks are separate gates.
- Hermes UI repos can lag the installed Hermes API; verify the real module surface and prefer a small UI-side adapter over downgrading Hermes or relying on deprecated plugin-compat aliases.
- Do not run a repository's `install.sh` or systemd unit merely because it is present; scripts can create startup tasks, mutate environment files, or bind publicly.
- Token auth on `/api/*` does not protect static HTML by itself. Ensure the frontend can collect a token safely and attach it to every protected request before publishing the port.
- Never claim "open by IP" from a local `200` alone. Check the listener bind, firewall rule, Host allowlist, auth behavior, and a request from an external network.
- Before replacing a known-good UI listener, stage and health-check the replacement or preserve a rollback path; do not stop the working process until the replacement passes, and restore service before ending if startup fails. Don't restart an omnibus keeper just to restore one page until you know whether it also starts parsers, monitors, or workers; start only the requested web components when those must stay stopped.
- For profile test-chat panels, validate `--toolsets` against the installed Hermes registry instead of assuming `none` is a no-tools sentinel; unknown names warn, and a supported set such as `safe` may still include web, vision, or image-generation tools. Keep terminal/browser tools out of preview chats, and communicate any remaining capabilities.
- Persist profile model/provider changes through `hermes -p <profile> config set <key> <value>` and read the values back; back up profile instruction files before a UI save.
- The UI can still be partly Korean/English after translating its dictionary; direct strings in prompts, toasts, placeholders, dialogs, and status labels need a separate inventory.
- Do not paste generated auth tokens into Telegram or a URL. Keep them in a local protected file and describe where the user can retrieve them.
