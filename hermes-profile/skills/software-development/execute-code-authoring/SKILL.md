# Authoring executable Python for execute_code

`execute_code` compiles the WHOLE cell before running anything: one syntax error discards every intended side effect, including the steps that "already ran" in your head. Author code so the cell compiles first time, and guard file writes so a bad patch cannot damage the target.

## Procedure
1. **Latin identifiers, always — and each one a single token.** In generated cells keep every variable, function and keyword in ASCII; Cyrillic belongs only inside string literals. This host's generation path substitutes nearby English keywords next to Cyrillic text (`in` becomes the Cyrillic preposition), which alone produced repeated whole-cell `SyntaxError`s. String literals may be Cyrillic — `print('патч применён')` is safe; `for файл в список:` is not. Multi-word Cyrillic names fail doubly: even spelled right, typing one with a space (`для печати = блоки[-3:]`) is a syntax error that voids the whole cell — identifiers are single ASCII tokens (`items_to_print`); multi-word phrasing lives in string content, never in the name.
2. **Compile before you write.** When patching an existing file, build the new source in memory and run `compile(new, path, 'exec')` FIRST; write to disk only on success. This guard prevented corrupting a dozen wrapper scripts when insertions carried literal backslash-n characters.
3. **Newlines in replacement payloads must be real.** Use triple-quoted strings (actual line breaks) or `chr(10)`; `"\n"` inside a normal string yields a literal backslash-n in the pasted code and the target file fails with `unexpected character after line continuation character`. Raw-string paths need single backslashes — `r"C:\dir"` — or the file records doubles. When the **generated file itself is Python source containing a `\n` escape**, the backslash must survive two interpretation layers: write `'\\n'` in the generating cell or build it with `chr(92) + 'n'`; a single `'\n'` becomes a real line break inside the target string literal and breaks compilation. `py_compile` the generated file in the same cell.
4. **Anchor patches on full multi-line blocks, not single lines.** `except X:` alone repeats across a file; the anchor plus its body line is unique and survives indentation checks.
5. **Verify, then report.** After a cell that edits files: `py_compile`/`compile` over every touched file, then re-run the functional check (import, call). A `SyntaxError` in the cell means NOTHING ran — do not report partial progress from that cell; re-issue the whole sequence.
6. **Split long cells at natural seams** (write module → patch targets → smoke test) so a failure lands on one small step instead of replaying the whole batch.

## Pitfalls
- **One compile error voids the entire cell** — "the first part printed" cannot happen; on any `SyntaxError`/`NameError` from the harness, assume zero side effects and re-run.
- **A patch that silently matched nothing leaves `no change`** — print per-file outcomes (`OK` / `anchor MISSING` / `SYNTAX-FAIL`) and check them; a green cell with all-anchor-missing is a failed patch.
- **Write-protect with compile, not with hope** — direct `open(...).write()` after a failed compile is how a broken replacement reaches production scripts; the try/compile/write order is the entire safety.
- **Do not hand-type long file contents into a cell** — use `write_file`/`patch` tools for full files and keep cells for glue; cells are also re-sent on every retry.
- **After any cell failure, continue from the LAST VERIFIED step, not the last intended one** — re-read the on-disk state (does the hook block exist? was the file written?) before assuming an earlier operation landed.
- **Cyrillic/Latin lookalike identifiers die only at run time.** In files whose identifiers are Cyrillic (`с`, `д`, `РЕ_ШАГ`), a patched or hand-typed line that picks the Latin twin (`s`, `d`, `_РЕ_ШАГ`) passes `compile()`/`py_compile` and raises `NameError` only when that function is actually called — so after editing such a file, CALL the touched function once (smoke); syntax checks prove nothing about identifier spelling. The same trap covers this codebase's module APIs, whose public functions are Cyrillic (`workflow.план`, `queue.снять_hold`, `auto_publish.основной`): a guessed Latin or translated name compiles fine inside the cell and fails at call time with `AttributeError: module has no attribute` — read the `def` line (or grep the module) before calling, never translate the exported name.
- **`dict(row)` from sqlite3 without `row_factory` fails at run time, not compile time** — `connect(...)` returns tuple rows by default: `dict(r)` raises `dictionary update sequence element #0 has length N; 2 is required`, and `r['поле']` raises `IndexError`. Build the connection with `row_factory=sqlite3.Row` in the SAME cell where any named/dict access is planned: the UPDATE usually already committed by the time a trailing `print(dict(row))` runs, so the crashed print looks like a crashed write even though the write succeeded — never diagnose a write from a print that has its own way to fail.
- **In `patch`/`write_file` payloads a backslash before `r`/`n`/`t` is escape-interpreted — never write Windows paths with single backslashes there.** `new_string` containing `C:\dir\reviews\file.py` arrives as a real CR/LF inside the string literal, splits the line, and the target ends as `SyntaxError: unterminated string literal` even though the tool reports success — and if a live process executes that file, it starts failing on its very next tick, before any human notices. Use forward slashes (`Path("C:/dir/file.py")` accepts them on Windows) or double every backslash in payloads, and `py_compile` the target immediately after the edit: the tool's success/lint report is not proof the file compiles.
- **Windows console tools emit OEM/non-UTF-8 bytes — `text=True` can leave you with `stdout=None`.** Reading `tasklist` (or similar) as text can kill the subprocess reader thread with `UnicodeDecodeError … byte 0xff`; the captured stdout is then `None`, and your own `.splitlines()`/`in` check crashes with `NoneType has no attribute …` — a process-liveness probe that dies or reports "no processes" purely because of decoding. Capture bytes and search bytes (`b'python' in out`), or query processes via PowerShell `Get-CimInstance` (structured, encoding-safe); treat decode crashes as probe failures, never as evidence the process is gone.
- **The persistent kernel caches `sys.modules` — verify a patched module in a FRESH process.** After editing a `.py` file, a later `execute_code` cell that does `import that_module` may get the pre-patch module loaded by an earlier cell, so constants/functions read stale — this masquerades as "my patch vanished" or "the old value is still on disk". Confirm every patch with a one-shot `terminal` run (`py_compile` + `python -c "import …; print(constant)"`), and re-read the file (`read_file`/grep) before "re-applying" a patch that already landed — a stale kernel value is never evidence about the file on disk.
